# 文本语音动作同步播放编排设计

本文描述第一版“文本 / 语音 / 动作”同步播放编排方案。

## 1. 目标

当前链路已经具备明确完成判定：

```text
文本已送达
音频已结束或失败
动作已结束
=> 本轮完成
```

但完成判定只能解决“什么时候结束”，不能解决“什么时候一起开始”。

本轮目标是新增前端起播编排层，让同一轮的文本、语音、动作尽量像同一个整体一起发生。

## 2. 第一版范围

第一版做“软同步”，不做音素级同步。

包括：

- 按 `turnId + orchestrationId` 聚合文本、音频、动作
- 文本先到时先缓存，不立刻进入舞台最终文本
- 音频先到时先缓存，不立刻播放
- 动作先到时先缓存，不立刻进入 `ModelEngine`
- 三者都到齐时立即释放
- 如果音频已到但动作晚到，则等待一个短窗口
- 如果超过窗口动作仍未到，先释放文本 + 音频
- 动作更晚到时，按当前剩余音频时长补播
- 无音频轮次在短等待后释放文本，动作如果到达则同步释放

不包括：

- 音素级口型同步
- 字幕逐词对齐
- 音频 RMS / phoneme 分析
- 逐帧动作节奏控制
- 新的 Live2D motion mixer

## 3. 模块边界

新增：

```text
frontend/src/composables/useTurnPlaybackOrchestrator.ts
frontend/src/composables/turnPlaybackOrchestratorCore.ts
```

职责：

- `turnPlaybackOrchestratorCore` 收集同一轮的 pending 文本、pending 音频、pending 动作
- `turnPlaybackOrchestratorCore` 决定什么时候释放起播
- `useTurnPlaybackOrchestrator` 负责把 Vue watch、adapter 和 ModelEngine 接到 core 上
- 调用 adapter release 文本 / 音频
- 调用 `ModelEngine.ingestInboundPayload()` 释放动作

不负责：

- WebSocket 收发
- 音频播放细节
- 动作编译细节
- Live2D 写参
- 播放完成判定

现有模块职责保持：

- `useAdapterConnection`：收协议消息，保存 pending 文本 / 音频 / 动作，提供 release 方法
- `useModelEngine`：动作排队、编译、等待音频、起播
- `usePlaybackCompletionCoordinator`：文本、音频、动作完成后的收尾判定

## 4. 编排策略

### 4.1 三者到齐

```text
textReady && audioReady && motionReady
=> 立即释放文本、动作、音频
```

动作释放到 `ModelEngine` 后仍会等待音频起播事件，因此真正起播会贴近音频开始。

### 4.2 文本 + 音频先到，动作未到

```text
textReady && audioReady && !motionReady
=> 等待 AUDIO_MOTION_SYNC_WAIT_MS
```

如果窗口内动作到达：

```text
释放文本 + 动作 + 音频
```

如果窗口超时：

```text
释放文本 + 音频
```

后续动作晚到：

```text
直接释放给 ModelEngine
```

此时 `ModelEngine` 会依据已经起播的音频计算剩余时长。

### 4.3 文本先到，音频未到

```text
textReady && !audioReady
=> 等待 TEXT_ONLY_RELEASE_WAIT_MS
```

如果短等待后音频仍未到，则先释放文本。

这样可以避免无音频回复被 `turn_finished` 卡住。

### 4.4 无音频确认

收到以下终态时视为无音频：

```text
audioPlaybackTerminalState === "not_requested"
```

如果此时文本已 ready：

```text
有动作 => 释放文本 + 动作
无动作 => 释放文本
```

## 5. 当前实现常量

```ts
const AUDIO_MOTION_SYNC_WAIT_MS = 820;
const TEXT_ONLY_RELEASE_WAIT_MS = 260;
```

说明：

- `820ms` 用于等待晚到动作，避免语音和动作明显错开
- `260ms` 用于文本-only 场景的短暂聚合，不让纯文本回复被明显延迟

这些值是第一版体感参数，后续可以进入设置或调试面板。

## 6. 当前数据流

```text
output.text
-> useAdapterConnection.queueAssistantTextForPlayback()
-> pendingAssistantTextNonce
-> useTurnPlaybackOrchestrator
-> releaseAssistantTextForPlayback()
-> assistantTextDeliveryNonce
-> usePlaybackCompletionCoordinator
```

```text
output.audio
-> useAdapterConnection.queueAudioForPlayback()
-> pendingAudioNonce
-> useTurnPlaybackOrchestrator
-> releaseAudioForPlayback()
-> playAudioAndAcknowledge()
-> audioPlaybackStartedNonce / audioPlaybackTerminalNonce
-> usePlaybackCompletionCoordinator
```

```text
engine.motion_intent / engine.motion_plan
-> applyInboundMotionPayload()
-> inboundMotionPlanNonce
-> useTurnPlaybackOrchestrator
-> modelEngine.ingestInboundPayload()
-> usePreviewMotionPlayer.playPlan()
-> usePlaybackCompletionCoordinator.recordMotionPlayback()
```

## 7. 与完成判定的关系

`useTurnPlaybackOrchestrator` 只负责开始。

`usePlaybackCompletionCoordinator` 继续负责结束：

- 文本 delivery
- 音频 terminal
- 动作 finished
- playback_finished 回传
- turn_finished 后清理

这两个模块不能合并，否则起播策略和完成策略会互相污染。

## 8. 测试覆盖

当前已补前端纯逻辑测试：

- 三者到齐同步释放
- 动作在等待窗口内到达时同步释放
- 动作超过等待窗口后补播
- 音频等待窗口超时后先释放文本 + 音频
- 文本-only 短等待后释放
- 无音频确认后释放文本 + 动作
- 不同 orchestration 组不会互相释放

测试入口：

```powershell
cd frontend
npm run test:orchestration
```
