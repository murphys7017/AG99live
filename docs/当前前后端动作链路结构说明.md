# 当前前后端动作链路结构说明

本文描述 AG99live 当前“文本 / 音频 / 动作”主链路的真实结构。

重点不是回顾历史，而是回答三个问题：

1. 现在一轮播放在前后端是怎么流动的
2. 前端现在靠什么对象组织这轮播放
3. 每个核心模块分别负责哪一段

## 1. 当前结构判断

结论：当前前端主链路已经从“局部实现能跑”进入“整体协作基本成形”的阶段。

现在最核心的统一概念是：

```text
TurnPlaybackSession
```

也就是一轮回复从收到文本 / 音频 / 动作，到本地播放完成，再到后端确认收口的统一前端对象。

因此，下一阶段的重点不再是继续大拆文件，而是：

- 补更高价值的时序测试
- 补更清楚的调试投影
- 在真实模型上校准同步体感

## 2. 主链路总览

### 2.1 从用户发送到整轮结束

1. 前端 `useAdapterConnection.sendText()` 发送 `input.text`
2. 后端 `TurnCoordinator` 建立新 turn，并发 `control.turn_started`
3. 后端主回复输出：
   - `output.text`
   - 可选 `engine.motion_intent`
   - 可选 `output.audio`
   - `control.synth_finished`
4. 前端 `useAdapterConnection` 接收协议消息，并把事件写入 `TurnPlaybackSession`
5. `useTurnPlaybackOrchestrator` 观察 session，决定文本 / 音频 / 动作何时释放起播
6. `useModelEngine` 接收释放后的动作，必要时再等待音频起播片刻后执行
7. `usePreviewMotionPlayer` 真正驱动 Live2D 写参播放
8. `usePlaybackCompletionCoordinator` 观察 session，判断前端本地播放何时完成
9. 当前端本地播放完成时，前端回发 `control.playback_finished`
10. 后端收到该回执后，发出 `control.turn_finished`
11. 前端收到 `turn_finished` 后，把该 session 标记为 `completed` 并清理上下文

### 2.2 当前完成语义

当前代码里的“这一轮结束”分成两层：

#### 第一层：前端本地播放完成

需要满足：

- 文本已 delivered
- 音频已进入终态
  - `completed`
  - `failed`
  - `absent`
- 动作已 `completed`，或者动作已明确 `absent`

这一步成立后：

```text
前端发送 control.playback_finished
```

#### 第二层：整轮协议收口完成

还需要：

```text
后端回发 control.turn_finished
```

只有这一步也到了，前端才会：

- 把 session phase 置为 `completed`
- 清理该轮播放上下文

这两层现在已经被明确拆开，不再混成一个条件。

## 3. 前端统一对象：TurnPlaybackSession

当前实现位置：

- `frontend/src/turn-playback/session.ts`
- `frontend/src/turn-playback/selectors.ts`
- `frontend/src/composables/useTurnPlaybackSessionStore.ts`

### 3.1 Session 内部大致内容

一条 session 至少会持有四组状态：

- `text`
- `audio`
- `motion`
- `backend`

以及一个总体 `phase`：

- `collecting`
- `ready`
- `playing`
- `settling`
- `completed`
- `failed`

### 3.2 当前主键策略

前端播放轮次当前优先用：

```text
orchestrationId
```

回退顺序：

```text
orch:<orchestrationId>
-> turn:<turnId>
-> ephemeral:<serial>
```

这让一轮文本、音频、动作、播放回执都能挂到同一个 session 上。

## 4. 前端模块职责

### 4.1 `useAdapterConnection.ts`

作用：协议接入层 + 旧运行态兼容层。

当前职责：

- 建立 WebSocket 连接
- 处理 `output.* / control.* / system.* / engine.*`
- 维护一些运行时字段
- 把协议事件写入 `TurnPlaybackSession`
- 提供文本 / 音频释放接口给 orchestrator

当前它已经不是播放轮次真源。

播放轮次真源在 session store。

### 4.2 `useTurnPlaybackSessionStore.ts`

作用：前端播放轮次状态中心。

当前职责：

- 创建 session
- 按 `orchestrationId / turnId` 找到正确 session
- 写入：
  - text received / released / delivered
  - audio received / started / terminal
  - motion received / released / started / completed / absent
  - backend turn started / turn finished / interrupt
- 维护 active session
- 维护 phase 合法迁移

如果想知道“这一轮现在走到哪一步了”，这里是第一查看点。

### 4.3 `useTurnPlaybackOrchestrator.ts`

作用：起播编排层。

它只管开始，不管结束。

当前职责：

- 遍历 session store 中的 session
- 判断是否可以释放：
  - 文本
  - 音频
  - 动作
- 触发 adapter release
- 把动作交给 `ModelEngine`

它现在的判断基础已经是 session，而不是旧的散装 nonce。

### 4.4 `turnPlaybackOrchestratorCore.ts`

作用：纯逻辑起播策略核心。

当前保留两类等待窗口：

- `AUDIO_MOTION_SYNC_WAIT_MS = 820`
  - 文本+音频已到，等待动作短暂加入
- `TEXT_ONLY_RELEASE_WAIT_MS = 260`
  - 文本先到，短暂等待音频

它负责决定：

- 三者都到齐时一起放
- 音频先到、动作晚到时先放文本+音频
- 无音频时如何放文本和动作
- 动作更晚到时如何作为 late motion 补播

### 4.5 `useModelEngine.ts`

作用：动作引擎编排层。

当前职责：

- 归一化动作载荷
- 对 `engine.motion_intent.v2` 做本地编译
- 调 `usePreviewMotionPlayer` 执行参数计划
- 在动作已进入引擎后，必要时短暂等待音频起播

重要点：

- 现在它读取音频 timing 时，优先读 session
- 它仍保留 pending payload 队列，但不再自己定义整轮播放语义

### 4.6 `usePreviewMotionPlayer.ts`

作用：真正的 Live2D 参数计划播放器。

当前职责：

- 解析 `engine.parameter_plan.v2`
- 按需要重定时
- 调用 Live2D runtime 写参
- 支持 soft handoff
- 支持重复计划去重与重启节流

### 4.7 `usePlaybackCompletionCoordinator.ts`

作用：播放完成编排层。

它只管结束，不管开始。

当前职责：

- 观察 session store
- 判断前端本地播放何时已经 settled
- 在本地完成时发送 `control.playback_finished`
- 等后端 `control.turn_finished`
- 最终把 session 标成 `completed` 并清理上下文

这块现在最重要的结构改动是：

```text
local playback settled
!= backend turn finished
```

两者已经拆开。

### 4.8 `usePetDesktopController.ts`

作用：桌宠运行时总装配器。

它把下面这些拼到一起：

- `useAdapterConnection`
- `useTurnPlaybackSessionStore`
- `useTurnPlaybackOrchestrator`
- `usePlaybackCompletionCoordinator`
- `useModelEngine`
- `usePreviewMotionPlayer`
- `useDesktopBridge`

它负责总装配，不负责自己发明新的播放语义。

### 4.9 `usePetRuntimeSnapshotPublisher.ts`

作用：把运行态投影给其他窗口。

当前已经会投影 active session 摘要：

- `activeSessionId`
- `activeSessionPhase`
- 文本是否 ready
- 音频终态
- 动作是否 started / completed
- 后端是否 turn_finished

这让辅助窗口至少能看到当前播放轮次的大致推进。

## 5. 后端模块职责

### 5.1 `runtime/session_state.py`

作用：后端单连接 turn 状态机。

当前职责：

- 管理 `current_turn_id`
- 管理 `current_orchestration_id`
- 区分：
  - thinking
  - synthesizing
  - playing
- 在有音频时等待前端 `playback_finished`

### 5.2 `runtime/turn_coordinator.py`

作用：后端协议和轮次编排中枢。

当前职责：

- 接收入站协议
- 建立 turn
- 广播 `output.text / output.audio / engine.motion_*`
- 在音频轮次下等待前端 `control.playback_finished`
- 收到后发送 `control.turn_finished`

当前顺序要点：

```text
output.*
-> control.synth_finished
-> 前端播放
-> control.playback_finished
-> control.turn_finished
```

## 6. 当前结构还需要改哪里

当前不建议再做大规模“为了拆而拆”的重构。

更值得继续做的是：

1. 补更强的 session 调试投影
2. 补 interrupt / stale turn / rapid turn switch 时序测试
3. 在真实模型上验证同步体感
4. 继续收口数据边界文档，让结构方向和当前代码同步
