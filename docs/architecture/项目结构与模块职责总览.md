# 项目结构与模块职责总览

本文是 AG99live 的长期维护型结构总览文档。

目标不是讨论某一条时序细节，而是稳定回答下面这些问题：

1. 这个项目当前有哪些一级目录和一级模块
2. 每个模块负责什么，不负责什么
3. 模块之间的大致依赖方向是什么
4. 后续重构时，应该优先把变更落在哪个模块

本文应持续更新。只要项目结构、模块归属、职责边界发生变化，都应该同步修订本文。

## 1. 仓库一级结构

当前仓库主要由以下部分组成：

```text
AG99live/
  .ai/
  analysis/
  astrbot_plugin_ag99live_adapter/
  docs/
  frontend/
  tools/
```

一级目录职责：

| 路径 | 职责 |
| --- | --- |
| `.ai/` | 项目内 AI 代理治理入口和状态文件 |
| `analysis/` | 分析材料、实验或临时研究产物 |
| `astrbot_plugin_ag99live_adapter/` | 后端 AstrBot 适配器、运行时、协议和动作服务 |
| `docs/` | 架构、协议、路线图和设计文档 |
| `frontend/` | Electron + Vue 前端桌宠运行时和工具窗口 |
| `tools/` | 仓库级开发辅助脚本和校验工具 |

## 2. 系统总体分块

从职责上看，当前项目可以先理解为四个大系统：

```text
前端桌宠运行时
后端适配器与服务
动作与模型能力体系
文档与治理体系
```

更贴近数据流的表达：

```text
用户 / 辅助窗口
-> 前端运行时
-> 后端适配器
-> 模型与动作服务
-> 前端回放与渲染
```

## 3. 前端结构

前端位于 `frontend/`，是当前桌宠系统的运行时 owner。

### 3.1 `frontend/electron/`

职责：桌面宿主层。

当前子目录：

```text
frontend/electron/main
frontend/electron/preload
```

模块职责：

| 路径 | 职责 |
| --- | --- |
| `frontend/electron/main/` | Electron 主进程，负责窗口、菜单、系统级事件、IPC |
| `frontend/electron/preload/` | 向渲染进程暴露受控桌面 API |

不负责：

- 后端协议语义
- 动作编译
- Turn 播放编排

### 3.2 `frontend/src/views/`

职责：窗口级视图入口。

当前主要窗口：

| 视图 | 职责 |
| --- | --- |
| `PetDesktopView.vue` | 主宠物窗口 |
| `PetOverlayView.vue` | overlay 窗口 |
| `SettingsWindowView.vue` | 设置窗口 |
| `HistoryWindowView.vue` | 历史窗口 |
| `ActionLabWindowView.vue` | 动作实验室 |
| `ProfileEditorWindowView.vue` | semantic profile 编辑窗口 |

这些视图负责组织页面，不负责底层协议和播放时序。

### 3.3 `frontend/src/composables/`

职责：前端主要业务组合层。

这是当前前端最重要的装配区域。

当前可分为几类：

| 类型 | 代表文件 | 职责 |
| --- | --- | --- |
| 运行时总装配 | `usePetDesktopController.ts` | 装配适配器、播放编排、动作引擎、桥接等主模块 |
| 适配器 facade | `useAdapterConnection.ts` | 对上层暴露后端连接和运行时控制接口 |
| 播放状态与编排 | `useTurnPlaybackSessionStore.ts` `useTurnPlaybackOrchestrator.ts` `usePlaybackCompletionCoordinator.ts` | 管理一轮回复内的文本、音频、动作和完成条件 |
| 动作运行时接入 | `usePreviewMotionPlayer.ts` `useLive2dRenderer.ts` | 播放 plan、驱动 Live2D |
| 多窗口桥接 | `useDesktopBridge.ts` `usePetRuntimeSnapshotPublisher.ts` `useDesktopRuntimeCommandHandler.ts` | 广播 snapshot、接收 command |
| 模型能力同步 | `useModelSync.ts` | 维护当前模型、profile 和运行时能力事实 |
| 工具与设置 | `useSettingsWindow.ts` `useParameterExcludeKeywords.ts` | 辅助窗口交互和本地偏好控制 |

当前判断：

- `usePetDesktopController.ts` 是前端 composition root。
- `useAdapterConnection.ts` 已退到适配器 facade 雏形：仍负责组合和对外 API，但麦克风、音频、入站分发、出站动作等实现细节已经迁出。

### 3.4 `frontend/src/adapter-connection/`

职责：前端适配器实现细节。

这是“与后端连接的适配部分”的代码核心区域。

当前目录结构：

```text
frontend/src/adapter-connection/
  core/
  inbound/
  outbound/
  runtime/
  features/
```

子目录职责：

| 路径 | 职责 |
| --- | --- |
| `core/` | 与具体 feature 无关的适配器基础能力：地址、协议 envelope、协议常量、偏好、transport |
| `inbound/` | 后端入站消息解析、payload 校验、事件映射和分域 dispatch |
| `outbound/` | 前端向后端发送的出站动作；当前已开始通过统一 `AdapterOutboundClient` 收口 |
| `runtime/` | 音频、麦克风、播放释放队列、连接关闭清理等运行时副作用 |
| `features/` | history、model sync、motion tuning 等适配器 feature 数据转换 |

当前主要文件：

| 路径 | 职责 |
| --- | --- |
| `core/transport.ts` | WebSocket 连接打开与事件绑定 |
| `core/envelope.ts` | 协议 envelope 构造 |
| `core/address.ts` | 地址派生与连接候选处理 |
| `core/preferences.ts` | 适配器相关本地偏好存储 |
| `core/protocolMessageTypes.ts` | 协议消息类型常量 |
| `inbound/inboundProtocol.ts` | 入站 envelope 校验 |
| `inbound/inboundProtocolDiagnostics.ts` | 入站协议错误与未接入消息诊断 |
| `inbound/inboundPayloads.ts` | 各类 payload 解析与守卫 |
| `inbound/inboundEvents.ts` | 协议消息映射为内部事件 |
| `inbound/inboundDispatcher.ts` | 入站内部事件路由器 |
| `inbound/inboundConnectionDispatcher.ts` | 处理 server info 和连接后运行信息 |
| `inbound/inboundFeatureDispatcher.ts` | 处理 model sync、history、motion tuning、semantic profile save result 等数据型 feature event |
| `inbound/inboundMotion.ts` `inbound/inboundMotionDispatcher.ts` | 处理 engine motion payload 的验收、归一化与 session 写入 |
| `inbound/inboundOutputDispatcher.ts` | 处理 output text/audio/image/transcription 等输出 event |
| `inbound/inboundRuntimeDispatcher.ts` | 处理 turn lifecycle、interrupt、start mic、synth finished、control error 等运行时控制 event |
| `outbound/outboundClient.ts` | 统一出站发送端口：socket 状态检查、envelope 构造、JSON 发送 |
| `outbound/outboundActions.ts` | 出站消息发送动作；当前已依赖统一 outbound client |
| `runtime/audioRuntime.ts` | 音频运行时编排：pending queue、release、播放启动/停止、terminal 标记、active segment 查询 |
| `runtime/audioPlayback.ts` `runtime/audioPlaybackActions.ts` | 输出音频底层播放与播放动作状态回写 |
| `runtime/microphoneRuntime.ts` | 麦克风运行时编排：启动/停止、设备切换重启、PTT origin、输入段 identity、发送积压保护 |
| `runtime/microphoneCapture.ts` `runtime/microphoneDevices.ts` | 麦克风底层采集与设备枚举 |
| `runtime/playbackReleaseQueue.ts` | 文本/音频释放前的缓存队列 |
| `runtime/adapterAudioBridge.ts` | 音频状态与 session 桥接 |
| `runtime/connectionRuntimeState.ts` | 连接关闭时清理运行时状态 |
| `features/motionTuningPayload.ts` | 动作调参样本协议归一化 |
| `features/historyPayload.ts` | 后端 history payload 归一化 |
| `features/modelSyncRewrite.ts` | 资源 URL 重写 |

按你当前的设想，这里已经开始按职责分层。后续可以继续明确为：

```text
Adapter Core
Adapter Inbound / Outbound
Adapter Runtime
Adapter Features
Adapter Facade
```

建议理解：

- `data adapter`：协议、payload、inbound/outbound、history/profile/model sync/motion tuning 数据同步
- `runtime adapter`：音频播放、麦克风、PTT、播放队列、运行时状态 reset

### 3.5 `frontend/src/turn-playback/`

职责：文本、音频、动作统一播放轮次建模。

这是前端播放主链路的事实来源。

当前模块：

| 路径 | 职责 |
| --- | --- |
| `session.ts` | `TurnPlaybackSession` 和 `TurnPlaybackSegment` 数据模型 |
| `selectors.ts` | 当前 active segment、释放条件、settled 条件等选择逻辑 |
| `ports.ts` | 播放编排与外部模块交互的端口类型 |

它解决的问题是：

- 一轮回复如何聚合
- 文本/音频/动作如何挂到同一个 segment
- 什么时候算本地 settled

### 3.6 `frontend/src/model-engine/`

职责：动作引擎核心区。

这是你后面准备集中精力做的部分。

当前主要文件：

| 路径 | 职责 |
| --- | --- |
| `useModelEngine.ts` | 引擎运行时入口，接收 payload，决定编译和播放 |
| `compiler.ts` | `engine.motion_intent.v2 -> engine.parameter_plan.v2` 编译核心 |
| `normalize.ts` | 动作 payload 归一化 |
| `timing.ts` | timing 决策与参数计划时长处理 |
| `planParser.ts` | 参数计划解析 |
| `settings.ts` | 引擎设置和强度倍率 |
| `contracts.ts` | 引擎输入输出契约 |
| `constants.ts` | 等待和播放相关常量 |

当前判断：

- 这里已经是独立模块
- 但内部还没有完全拆成“参数生成 / 动作优化 / 连贯优化”等子模块
- 现在先不集中拆它，是合理的

### 3.7 `frontend/src/action-lab/` 与 `frontend/src/components/`

职责：动作库与调参工具层。

当前相关模块：

| 路径 | 职责 |
| --- | --- |

| `components/BaseActionPreviewPanel.vue` | 参数动作原子浏览、筛选、组合测试 |

这一层当前更像“动作库 / 调参工作台”，不是运行时主链路。

按你现在的决定：

- 这部分暂时不优先调整
- 后面等适配器和引擎外部边界稳定后再回头收

## 4. 后端结构

后端核心位于 `astrbot_plugin_ag99live_adapter/`。

这是当前“后端适配器与服务”主区域。

### 4.1 主要目录

| 路径 | 职责 |
| --- | --- |
| `runtime/` | turn 状态、主运行时编排、协议收口 |
| `protocol/` | 协议消息与契约 |
| `transport/` | 网络传输和连接层 |
| `services/` | 后端服务组合和上层能力 |
| `motion/` | 动作相关后端处理 |
| `middleware/` | 中间处理层 |
| `prompts/` | 提示词或模型相关文本资源 |
| `live2d/` `live2ds/` | Live2D 相关后端资源或模型数据 |
| `assets/` | 静态资源 |
| `tests/` | 后端测试 |

### 4.2 当前后端职责判断

后端当前至少承担这些职责：

- 维护 turn 生命周期
- 接收前端 `input.*`
- 广播 `output.* / control.* / engine.*`
- 同步模型能力和 profile
- 提供动作调参样本存储与读取

从整体架构上看，它不是“单纯 API 服务”，而是前端桌宠运行时的协作编排后端。

## 6. 当前推荐的模块边界

按现在你的设想，我建议把整个项目先稳态理解成下面这几块：

```text
Frontend
  Desktop Host
  Adapter
    Data Adapter
    Runtime Adapter
    Adapter Facade
  Turn Playback
  Motion Engine
  Action Library / Authoring Tools
  Avatar Runtime
  Desktop Bridge

Backend
  Runtime Coordinator
  Protocol / Transport
  Motion Services
  Persistence / Resource Services
```

其中前端最值得后续继续明确的边界是：

### Adapter

负责：

- 和后端连接
- 解析协议
- 归一化事件
- 管理输入输出音频等运行时 IO

不负责：

- 动作编译
- 动作审美决策
- 调参工具逻辑

当前拆分与优化方案见：

- [前端适配器拆分与优化方案](./前端适配器拆分与优化方案.md)

当前进度：

- `outbound/outboundActions.ts` 已经开始依赖 `AdapterOutboundClient`。

当前下一优先级：

- 继续迁移 history、motion tuning 等 feature 发送到 `AdapterOutboundClient`。

### Motion Engine

负责：

- 接收动作 payload 或 plan
- 编译 intent
- 做动作运行时调度

不负责：

- WebSocket 协议
- 工具窗口桥接
- 桌面窗口控制

### Action Library / Authoring Tools

负责：

- 动作原子浏览
- 参数试验
- 调参样本管理
- profile 编辑

允许：

- 向动作引擎发送测试请求

不负责：

- 主链路运行时事实管理
- 后端协议直连

## 7. 当前最值得持续维护的判断

截至目前，项目结构有几个明确判断：

1. 前端已经不是普通页面应用，而是桌面运行时系统。
2. `frontend/src/composables/usePetDesktopController.ts` 是前端主装配根。
3. `frontend/src/adapter-connection/` 是适配器核心实现区，当前已拆为 `core/`、`inbound/`、`outbound/`、`runtime/`、`features/`。
4. 适配器已开始收敛 `outbound/`，下一步应迁移 feature clients 到统一出站 client。
5. `frontend/src/model-engine/` 已经是动作引擎独立区域，但内部还没到最终拆分形态。
6. `frontend/src/action-lab/` 与相关组件是动作库/调参工具区，当前可以暂缓调整。
7. `astrbot_plugin_ag99live_adapter/` 是后端主业务区，不只是简单桥接壳。

## 8. 维护规则

后续维护本文时，建议遵守下面几条：

1. 只写“当前真实结构”，不要把未来设想伪装成现状。
2. 每当新增一级模块或一级职责，就补到本文。
3. 每当一个模块职责明显变化，就更新“负责什么 / 不负责什么”。
4. 每当重构完成一个大边界，就把旧判断删掉，不保留过期描述。
5. 如果某个文档更偏时序或实现细节，就写到其他架构文档，不要把本文写成大杂烩。
