# 前端系统模块架构说明

本文描述 AG99live 前端当前的模块边界、主数据流和后续收口方向。

这里的“模块”不是按文件夹机械划分，而是按系统职责划分。当前代码已经基本形成这些模块，但部分边界仍处在渐进收口阶段。

## 1. 总体判断

当前前端是一个桌宠运行时系统，不只是普通 UI。

它的核心链路是：

```text
Adapter Protocol 接收后端消息
-> Turn Playback Pipeline 编排文本 / 音频 / 动作
-> Motion Engine 编译或调度动作
-> Avatar Runtime 驱动 Live2D
-> Runtime Bridge 同步状态给多窗口工具
```

当前结构方向是合理的：

- 主宠物窗口是运行时 owner。
- 辅助窗口通过 command / snapshot 与主窗口通信。
- 文本、音频、动作已经统一写入 `TurnPlaybackSession`。
- 起播编排和完成判定已经分离。
- 动作引擎不直接处理 WebSocket 协议。

当前仍需继续收口的地方：

- `useAdapterConnection.ts` 仍是适配器 facade / composition root，但核心实现已经拆入 `adapter-connection/` 的分区目录。
- Audio IO 仍保留当前播放缓存和 UI 投影，但完成判定已经以 `segment.audio` 为事实来源。
- Runtime snapshot publisher 直接读取较多模块内部状态。
- 前后端协议契约还没有单一生成源。
- Motion Engine 已独立成模块，下一步应审阅其内部职责，而不是继续把适配器拆分当成主阻塞项。

## 2. 模块总览

当前建议把前端理解为 8 个一级模块，外加 2 个横切层。

```text
Desktop Host
Runtime Bridge
Adapter Protocol
Turn Playback Pipeline
Model Capability
Motion Engine
Avatar Runtime
Authoring Tools

Audio IO
Contracts
```

整体关系：

```text
Desktop Host
  -> Runtime Bridge
      -> Pet Runtime Controller
          -> Adapter Protocol
          -> Turn Playback Pipeline
          -> Model Capability
          -> Motion Engine
          -> Avatar Runtime
          -> Authoring Tools projection
```

更贴近运行时的数据方向：

```text
Adapter Protocol
  -> Turn Playback Pipeline
      -> Motion Engine
          -> Avatar Runtime

Model Capability
  -> Motion Engine
  -> Authoring Tools

Pet Runtime Controller
  -> Runtime Bridge
      -> Authoring Tools
```

## 3. Desktop Host

职责：提供 Electron 桌面宿主能力，不参与业务协议和播放语义。

主要位置：

- `frontend/electron/main/index.ts`
- `frontend/electron/main/window-manager.ts`
- `frontend/electron/main/menu-manager.ts`
- `frontend/electron/preload/index.ts`

当前负责：

- 创建宠物窗口、overlay、设置、历史、Action Lab、Profile Editor。
- 管理透明窗口、鼠标穿透、窗口拖动。
- 提供右键菜单。
- 提供桌面截图。
- 暴露 preload API：`window.ag99desktop`。

边界要求：

- 不理解 Adapter V2 协议。
- 不理解 `TurnPlaybackSession`。
- 不直接参与动作编译和 Live2D 参数计划。

## 4. Runtime Bridge

职责：负责多窗口之间的 snapshot 同步和 command 转发。

主要位置：

- `frontend/src/composables/useDesktopBridge.ts`
- `frontend/src/composables/usePetRuntimeSnapshotPublisher.ts`
- `frontend/src/types/desktop.ts`
- `frontend/src/desktop-bridge/snapshot.ts`

当前负责：

- 主宠物窗口发布 `DesktopRuntimeSnapshot`。
- 主宠物窗口发布 `DesktopModelProjectionSnapshot`，供工具窗口读取模型能力投影。
- 辅助窗口发送 `DesktopRuntimeCommand`。
- Profile Editor 使用独立的 profile authoring command / snapshot。
- 使用 `BroadcastChannel` 做实时同步。
- 使用 `localStorage` 做部分 snapshot 的窗口间兜底和初始恢复。

当前 snapshot ownership：

| Snapshot | Owner | 是否持久化 | 用途 |
| --- | --- | --- | --- |
| `DesktopRuntimeSnapshot` | Pet 主窗口 | 是 | 运行时状态、连接状态、当前 active session / active segment 摘要 |
| `DesktopModelProjectionSnapshot` | Pet 主窗口 | 否，当前为 runtime-only projection | 当前模型、profile、动作库等工具只读投影 |
| `DesktopProfileAuthoringSnapshot` | Profile Editor / Pet 主窗口协作 | 是 | Profile 编辑草稿、保存状态和编辑工具态 |
| motion tuning samples projection | Pet 主窗口 | 否，正式样本事实在后端 | 动作调参窗口读取的样本投影和诊断 |

当前 owner 关系：

```text
Pet 主窗口：运行时 owner
辅助窗口：工具窗口，只发 command / 读 snapshot
```

边界要求：

- 辅助窗口不直接持有 Adapter WebSocket。
- 辅助窗口不直接修改 Turn Pipeline 内部状态。
- 主窗口负责解释 command 并调用对应运行时模块。

当前结构风险：

- `usePetRuntimeSnapshotPublisher.ts` 直接读取大量模块内部字段，耦合面较宽。
- 当前 runtime snapshot 仍偏轻量调试摘要，尚未覆盖 release reason、ack sent、awaiting turn_finished 等更厚的时序诊断字段。

后续收口方向：

- 让各模块提供自己的 snapshot projection，再由 publisher 合并发布。

- `frontend/src/composables/useAdapterMotionTuning.ts`

当前入站流程：

```text
WebSocket raw message
-> parseInboundEnvelope
-> mapInboundEnvelopeToEvent
-> dispatchInboundEvent
-> session / model / audio / history / motion tuning 状态写入
```

当前出站流程：

```text
runtime action
-> buildMessageEnvelope
-> WebSocket send
```

常见出站协议：

- `input.text`
- `control.interrupt`
- `control.playback_finished`
- `system.history_*`
- `system.semantic_axis_profile_save`
- `system.motion_tuning_sample_*`
- `engine.motion_intent` / `engine.parameter_plan` preview

边界要求：

- 协议 envelope 和 payload 校验应尽量在这一层完成。
- 进入运行时的事件应尽量是已经定型的内部事件。
- Adapter 层不应该直接包含动作编译逻辑。

当前结构风险：

- `useAdapterConnection.ts` 仍然承担装配、facade API 和 projection 聚合职责，但 transport、入站 dispatcher、音频、麦克风、出站动作等实现已经迁出。
- 部分 message type 字符串仍散落在模块中。
- `useAdapterHistory.ts`、`useAdapterMotionTuning.ts` 等 feature client 还可以继续接入统一 outbound port。

后续收口方向：

```text
Adapter Core: transport / address / envelope / protocol constants
Adapter Inbound: protocol parse / event mapping / domain dispatcher
Adapter Outbound: AdapterOutboundClient / outbound actions / feature sends
Adapter Runtime: audio / microphone / release queue / reset cleanup
Adapter Features: history / motion tuning / model sync payload normalization
```

当前判断：适配器第一轮边界已经足够清楚，后续 feature client 迁移属于局部优化；项目主焦点可以转向 Motion Engine。

## 7. Turn Playback Pipeline

职责：组织一个 user input 对应 turn 内的多个 assistant output segment，并决定每个 segment 的文本、音频、动作起播和整轮完成回执。

主要位置：

- `frontend/src/turn-playback/session.ts`
- `frontend/src/turn-playback/selectors.ts`
- `frontend/src/composables/useTurnPlaybackSessionStore.ts`
- `frontend/src/composables/useTurnPlaybackOrchestrator.ts`
- `frontend/src/composables/turnPlaybackOrchestratorCore.ts`
- `frontend/src/composables/usePlaybackCompletionCoordinator.ts`

核心对象：

```text
TurnPlaybackSession
  -> backend / phase / interrupted
  -> segments: Map<messageId, TurnPlaybackSegment>
       -> text
       -> audio
       -> motion
```

建模原则：

```text
一个 user input
-> 一个 TurnPlaybackSession
-> 多个 TurnPlaybackSegment
-> 每个 segment = text + audio + motion
```

核心 ID：

- `orchestration_id`：优先的 session 聚合 ID。
- `turn_id`：后端 turn 生命周期 ID，缺少 orchestration 时作为 fallback。
- `message_id`：segment ID，用于绑定 text / audio / motion。

当前 session key 解析顺序：

```text
orch:<orchestration_id>
-> turn:<turn_id>
```

ID 契约：

| ID | 归属层级 | 作用 | 缺失时策略 |
| --- | --- | --- | --- |
| `orchestration_id` | 播放编排层 | 优先 session 聚合 ID | 缺失时退到 `turn_id` |
| `turn_id` | 后端 turn 生命周期 | 连接后端 turn_started / turn_finished / interrupt | 缺失时只能依赖当前 active session；新 session 不再匿名创建 |
| `message_id` | 单条回复 segment | 绑定同一片段的 text / audio / motion | 新协议路径必须携带；缺失时作为协议错误处理 |

当一轮先以 `turn_id` 创建 session，后续补到 `orchestration_id` 时，session store 负责把 `turn:<turn_id>` 提升为 `orch:<orchestration_id>`，避免同一轮被拆成两个 session。

### 7.1 Session Store

职责：保存事实状态。

主要负责记录：

- segment.text received / released / delivered
- segment.audio received / started / terminal
- segment.motion received / released / started / completed / absent
- backend turnStarted / turnFinished / success / reason
- session phase
- active session

### 7.2 Release Orchestrator

职责：决定什么时候释放文本、音频和动作。

它只管开始，不管结束。

核心等待窗口：

- `AUDIO_MOTION_SYNC_WAIT_MS = 820`
- `TEXT_ONLY_RELEASE_WAIT_MS = 260`

典型策略：

- text/audio/motion 都 ready：一起释放。
- text/audio ready 但 motion 未到：短等 motion。
- 只有 text ready：短等 audio。
- audio absent：按无音频路径释放。
- late motion：后续仍可交给 Motion Engine 补播。

### 7.3 Completion Coordinator

职责：判断后端输出队列是否关闭、本地播放是否全部结束，并回传 `control.playback_finished`。

它只管结束，不管开始。

本地 settled 条件：

- text delivered
- audio 进入 `completed` / `failed` / `absent`
- motion `completed` 或明确 `absent`

当前实现中的协议收口条件：

```text
synth_finished received
and all segments locally settled
=> send control.playback_finished

then backend turn_finished received
=> session completed
```

信号职责：

- `control.synth_finished`：后端输出队列关闭，不会再追加新的 segment。
- `control.playback_finished`：前端已经播放完该 turn 内所有 segment。
- `control.turn_finished`：后端收到 playback_finished 后确认整轮闭环收口。

注意：`control.synth_finished` 不要求早于所有播放完成。前端可以边收边播，直到队列关闭且所有 segment settled 后再发送 `playback_finished`。

边界要求：

- Pipeline 不应该理解 WebSocket 原始消息。
- Pipeline 不应该编译动作。
- Pipeline 只应该通过窄接口通知 Adapter 发送 `playback_finished`。

当前结构状态：

- `useTurnPlaybackOrchestrator` 已通过 `PlaybackReleasePort` 和 `MotionPayloadPort` 接入外部能力。
- `usePlaybackCompletionCoordinator` 已通过 `PlaybackAckPort` 接入 Adapter 出站回执。
- 播放管线不再直接依赖完整 adapter 返回对象。

建议端口形态：

| Port | 调用方 | 提供方 | 作用 |
| --- | --- | --- | --- |
| `PlaybackReleasePort` | Turn Playback Pipeline | Adapter / Audio IO / ModelEngine facade | release text/audio/motion |
| `PlaybackAckPort` | Completion Coordinator | Adapter outbound client | 发送 `control.playback_finished` |
| `MotionPayloadPort` | Turn Playback Pipeline | Motion Engine facade | 交付动作 payload |
| `RuntimeSnapshotPort` | 各 runtime 模块 | Snapshot publisher | 提供模块级 projection |

## 12. Audio IO 横切层

职责：处理音频播放和麦克风输入。

主要位置：

- `frontend/src/adapter-connection/runtime/audioRuntime.ts`
- `frontend/src/adapter-connection/runtime/audioPlayback.ts`
- `frontend/src/adapter-connection/runtime/audioPlaybackActions.ts`
- `frontend/src/adapter-connection/runtime/microphoneRuntime.ts`
- `frontend/src/adapter-connection/runtime/microphoneCapture.ts`
- `frontend/src/adapter-connection/runtime/microphoneDevices.ts`
- `frontend/src/composables/useAdapterConnection.ts`

输出音频方向：

```text
output.audio
-> queue audio
-> release audio
-> start local playback
-> markAudioStarted / markAudioTerminal
-> Completion Coordinator
```

输入麦克风方向：

```text
microphone capture
-> allocate active mic input segment identity
-> input.raw_audio_data
-> input.mic_audio_end
```

当前明确语义：

- 一段采集期内的所有 `input.raw_audio_data` 与最后的 `input.mic_audio_end` 共用同一个新的 `input:*` orchestration id
- 这条输入 identity 不再复用当前 assistant playback session 的 `orchestration_id`
- PTT 停止现在也走完整 stop 流程，会发送 `input.mic_audio_end`
- 麦克风设备切换现在也会先完整结束旧 capture segment，再重启新的 capture runtime
- 如果发送缓冲积压，前端会把该段标记为 broken，并在 `input.mic_audio_end` 中带 `dropped: true`
- 后端收到 `dropped: true` 后直接清空缓冲并拒绝继续转写该段
- 收到 `control.interrupt` 时，如果某个 segment 音频已经进入本地播放释放流程，前端会先把该 segment 写成 `audio.terminal = "failed"`，再清理播放 runtime

当前结构风险：

- adapter state 仍保留当前音频播放缓存和 UI 投影。
- 后续维护时不能再把 adapter pending queue 当成本地播放完成事实来源。

后续收口方向：

- 继续保持 `segment.audio` 是事实来源。
- adapter audio fields 只作为 Audio IO 当前播放缓存和 UI 投影。

## 14. 关键主流程

### 14.1 文本对话主流程

```text
辅助窗口输入文本
-> DesktopRuntimeCommand: send_text
-> usePetDesktopController
-> adapter.sendText
-> input.text
-> 后端
-> control.turn_started
-> output.text / output.audio / engine.motion_*
-> useAdapterConnection dispatch
-> TurnPlaybackSessionStore
-> useTurnPlaybackOrchestrator release
-> text display / audio playback / motion engine
-> control.synth_finished closes segment queue
-> all segments locally settled
-> control.playback_finished
-> control.turn_finished
-> session completed
```

### 14.2 模型同步主流程

```text
后端扫描模型
-> system.model_sync
-> useAdapterConnection
-> useModelSync
-> selectedModel / selectedSemanticAxisProfile
-> Motion Engine / Authoring Tools / Runtime Snapshot
```

### 14.3 动作测试主流程

```text
Action Lab / Profile Editor
-> preview_motion_payload
-> usePetDesktopController
-> modelEngine.playPreviewPayload 本地播放
-> adapter.sendMotionPayloadPreview 发给后端记录或验证
```

## 15. 推荐依赖方向

建议后续维护时坚持以下方向：

```text
Authoring Tools -> Runtime Bridge -> Pet Runtime Controller

Pet Runtime Controller -> Adapter Protocol
Pet Runtime Controller -> Turn Playback Pipeline
Pet Runtime Controller -> Model Capability
Pet Runtime Controller -> Motion Engine
Pet Runtime Controller -> Avatar Runtime

Adapter Protocol -> Turn Playback Pipeline
Turn Playback Pipeline -> Motion Engine
Motion Engine -> Avatar Runtime
Model Capability -> Motion Engine
Model Capability -> Authoring Tools
Turn Playback Pipeline -> Adapter Protocol(playback_finished only, via narrow port)
```

不建议出现：

- Avatar Runtime 直接访问 Adapter Protocol。
- Authoring Tools 直接修改 Turn Playback Session。
- Motion Engine 直接发送 WebSocket 消息。
- Adapter Protocol 内部编译动作计划。
- Desktop Host 理解业务协议。
