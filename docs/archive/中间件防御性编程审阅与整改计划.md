# 中间件防御性编程审阅与整改计划

快照日期：2026-05-08

## 一句话结论

当前项目的中间层里，确实存在一批本可以通过更清晰的分层和职责边界避免的“防御性编程”。

但问题不是“`if` 太多”，而是有两层承担了过多职责：

- 前端 `useAdapterConnection.ts`
- 后端 `turn_coordinator.py`

相比之下，`TurnPlaybackSession`、起播编排器、播放完成编排器里的大部分判断，属于正常的状态机逻辑，不应被误当成坏味道一起删除。

## 本文目标

本文用于回答四个问题：

1. 这次审阅到底看了哪些中间层模块
2. 哪些防御是健康且必须保留的
3. 哪些防御是在为混乱职责兜底
4. 接下来应该按什么顺序逐项处理

本文不是历史回顾文档，而是当前代码结构的整改工作底稿。

## 审阅范围

本次重点审阅了下面这些“中间层 / 协调层 / 边界层”模块：

- `frontend/src/composables/useAdapterConnection.ts`
- `frontend/src/composables/useDesktopBridge.ts`
- `frontend/src/composables/useTurnPlaybackSessionStore.ts`
- `frontend/src/composables/turnPlaybackOrchestratorCore.ts`

- `frontend/src/composables/usePetDesktopController.ts`
- `astrbot_plugin_ag99live_adapter/runtime/turn_coordinator.py`

## 本文里的“防御性编程”怎么区分

### 1. 合理的边界防御

这类防御应该保留。

典型场景：

- WebSocket / BroadcastChannel / localStorage 输入不可信
- 前后端协议消息可能损坏、缺字段、版本不符
- 跨窗口同步消息可能陈旧、格式错误或顺序异常

这类判断的作用是：

- 拒绝脏输入
- 做 schema / version 校验
- 防止外部错误直接污染内部状态机

### 2. 架构补偿型防御

这类防御不是完全不该存在，而是“数量和位置”说明架构边界还没有收口好。

典型信号：

- 同一层同时做协议解析、状态写入、兼容映射、播放编排、UI 状态回填
- 反复 `normalize + fallback + 再猜当前轮次`
- 下游 store 被迫帮上游补身份
- 一个类既管生命周期，又管动作生成策略，又管协议发包

这类判断越多，越说明系统内部语义没有尽早定型。

## 总体判断

### 结论一：不是所有防御都该被“优化掉”

像下面这些模块里的大部分判断，属于健康状态机或健康边界防御：

- `useDesktopBridge.ts`
- `turnPlaybackOrchestratorCore.ts`
- `usePlaybackCompletionCoordinator.ts`

这些模块虽然也有不少条件分支，但它们多数是在表达：

- 输入是否合法
- 当前 phase 是否允许迁移
- 文本 / 音频 / 动作是否已经满足起播或结束条件

这类判断不能简单砍掉。

### 结论二：当前真正“拧巴”的地方集中在两层

#### 前端：`useAdapterConnection.ts`

它目前同时承担：

- WebSocket 协议接入
- 协议版本校验
- envelope 解析与错误报告
- 当前 turn / orchestration 识别
- 旧字段到新语义的兼容桥接
- session store 双写
- 文本 / 音频 release 接口
- 一部分 UI 文案与运行态字段维护

这导致大量判断并不是在表达单一职责，而是在替“多职责混装”兜底。

#### 后端：`turn_coordinator.py`

它目前同时承担：

- turn 生命周期推进
- interrupt 处理
- playback finished 收口
- inline anim 提取
- realtime motion 生成调度
- motion payload normalize / validate
- stale turn 丢弃
- 协议广播

这使得很多 guard 看起来像“必要小心”，但其实是因为一个类里同时住了太多时序和语义。

## 逐文件审阅结论

## 1. `useAdapterConnection.ts`

### 当前问题性质

这是当前前端最重的架构补偿型防御集中区。

### 典型表现

#### 1. 协议解析、兼容映射、运行时状态写入混在一起

典型位置：

- `handleSocketMessage()` 附近
- `control.turn_started / control.synth_finished / control.turn_finished` 分支
- `engine.motion_*` 分支

例如：

- 协议版本检查：`useAdapterConnection.ts:586-597`
- 当前轮次写入：`useAdapterConnection.ts:651-669`
- `not_requested -> absent` 映射：`useAdapterConnection.ts:224-227`
- `synth_finished_without_audio_playback` 兜底：`useAdapterConnection.ts:692-700`

这些逻辑单看都说得过去，但它们被塞在同一层之后，就会让这一层变成“协议兼容 + 轮次推断 + 播放协调”的混合体。

#### 2. 当前播放组匹配逻辑分散在接入层

典型位置：

- `releaseAssistantTextForPlayback()`
- `releaseAudioForPlayback()`
- `matchesPlaybackGroup()`

参考：

- `useAdapterConnection.ts:960-985`
- `useAdapterConnection.ts:1011-1032`
- `useAdapterConnection.ts:1134-1150`

这里的问题不是“不能匹配”，而是：

- release 层还在自己决定这是不是同一轮
- 说明 session / orchestration 作为统一真源还没有完全把这件事收上去

#### 3. 同一层反复做 ID 回退推断

典型写法：

```text
normalizeOrchestrationId(envelope.orchestration_id) ?? state.currentOrchestrationId
```

这在多个消息分支中反复出现，说明：

- 协议边界进来以后，内部事件还没有立即变成“身份完整的 typed event”
- 于是后续每一步都得继续补一次身份

### 根因判断

根因不是某一段代码写得粗心，而是这层还没有拆成更清楚的三段：

1. 纯协议 ingress 层
2. 内部 typed event 映射层
3. 运行时状态写入 / release 协调层

### 整改方向

建议后续把它拆成三个明确职责：

1. `protocol ingress`
   - 只负责 parse / version / schema / basic normalize
2. `adapter event mapper`
   - 把 `ProtocolEnvelope` 变成内部定型事件
3. `runtime adapter facade`
   - 只负责把内部事件写入 session 和运行态

### 这一项的目标不是

- 不是删除所有 guard
- 不是把所有逻辑拆成很多小函数就算完成

真正的目标是：

- 让同一层不再同时做“解析 + 推断 + 编排 + 兼容”

## 2. `turn_coordinator.py`

### 当前问题性质

这是后端最重的架构补偿型防御集中区。

### 典型表现

#### 1. turn 生命周期与动作生成策略混在一起

典型位置：

- `finalize_turn()`：`turn_coordinator.py:309-336`
- `_commit_inbound_message()`：`turn_coordinator.py:338-352`
- `schedule_motion_after_reply()`：`turn_coordinator.py:643-692`
- `_generate_and_broadcast_realtime_motion_plan()`：`turn_coordinator.py:706-786`

当前一个类既要判断：

- 当前是否还在等待前端 playback complete
- 新输入是否应该先 finalize 老 turn
- 是否重复调度 realtime motion
- 当前 motion payload 是否有效
- 当前 turn 是否已经 stale

这会直接推高 guard 密度。

#### 2. inline motion 解析、normalize、validate 仍在协调器内部

典型位置：

- `_extract_inline_motion_plan()`
- `_parse_inline_anim_tag()`
- `_normalize_inline_anim_payload()`
- `_validate_motion_payload()`

这几段逻辑是有价值的，但它们不应该长期跟 turn lifecycle 紧耦合在一个巨类里。

#### 3. recovery 逻辑与主路径逻辑交织

例如：

- stale turn 丢弃
- generator 无 payload 时回退
- schema 不合法时 drop
- interrupted 时提早结束

这些 recovery 是应该有的，但现在分散在主干流程里，会持续增加阅读和维护成本。

### 根因判断

根因是后端目前缺一个更明确的分层：

1. `turn lifecycle`
2. `motion generation pipeline`
3. `protocol egress`
4. `inline motion parser / validator`

现在这些都集中在 `TurnCoordinator` 里。

### 整改方向

建议后续把后端协调层继续收口成：

1. `TurnSessionLifecycle`
   - begin / interrupt / await playback / finalize
2. `MotionPlanDispatchService`
   - schedule realtime motion
   - de-dup
   - stale check
3. `InlineMotionParser`
   - extract / parse / normalize / validate
4. `ProtocolEmitter`
   - 统一 output / control / engine 发包

### 这一项的目标不是

- 不是把所有 `if` 平铺成更多函数
- 而是让 lifecycle 不再关心 motion payload 的细节

## 3. `useTurnPlaybackSessionStore.ts`

### 当前问题性质

这层整体方向是对的，但还有一部分“身份补全职责”压得太深。

### 健康的部分

下面这些判断应保留：

- phase 合法迁移校验：`useTurnPlaybackSessionStore.ts:322-337`
- interrupt 只操作 active session：`useTurnPlaybackSessionStore.ts:302-318`
- text / audio / motion 的幂等状态写入

这些是正常状态机规则。

### 仍然存在的问题

`ensureSession()` 几乎成了所有写操作的必经入口：

- `markTextReceived()`
- `markAudioReceived()`
- `markMotionReceived()`
- `markTurnFinished()`
- `markPhase()`

这说明 store 除了“维护 session 状态”，还在承担：

- session 身份补全
- 临时 session 创建
- fallback 到 ephemeral id

这不是马上会炸的 bug，但它会让上游层更容易继续偷懒，把不完整身份一路传下来。

### 根因判断

当前内部事件还没有在更上游就保证：

- 这个事件属于哪一个 session
- 这个 session 是否允许被新建

于是 store 只能兜底。

### 整改方向

建议逐步做到：

1. 大多数内部事件进入 store 前已经带稳定 session key
2. 只有极少数“首个事件早到”的场景才允许创建 ephemeral session
3. `markInterrupt()`、`markTurnFinished()` 这类终局事件不再走隐式新建路径

## 4. `useDesktopBridge.ts`

### 当前问题性质

这层防御不少，但大部分是合理边界防御，不属于本轮主要问题。

### 应保留的原因

它面对的是：

- `BroadcastChannel`
- `storage` 事件
- `localStorage`

这些天生就是不可信边界。

典型位置：

- 初始化与通道存在性判断：`useDesktopBridge.ts:80-88`
- `broadcast` snapshot normalize：`useDesktopBridge.ts:95-118`
- `storage` 事件反序列化与 reject：`useDesktopBridge.ts:163-180`
- 本地持久化恢复：`useDesktopBridge.ts:199-247`

### 这里真正需要注意的点

不是“guard 太多”，而是：

- 不要继续把更多长期事实塞进 bridge snapshot

否则这层会从“合理边界防御”慢慢恶化成“工具域事实中台”。

## 5. `turnPlaybackOrchestratorCore.ts`

### 当前问题性质

这层的条件判断主要是业务时序，不是坏味道主体。

### 应保留的原因

这层本质上在表达：

- 文本到了没
- 音频到了没
- 动作到了没
- 是不是要等一小段窗口
- 是不是 late motion

典型位置：

- `evaluateGroup()`：`turnPlaybackOrchestratorCore.ts:196-240`

这类分支是“规则本身”，不是补洞。

### 当前唯一需要继续留意的点

如果未来 session id 已完全稳定，这层对 ephemeral group 的容忍空间还可以继续收缩，但这不是当前第一优先级。

## 6. `usePlaybackCompletionCoordinator.ts`

### 当前问题性质

这层大体健康，主要在表达“结束条件是什么”。

### 应保留的原因

这层承担的就是：

- 本地播放是否 settled
- 是否应该发送 `control.playback_finished`
- 是否已等到后端 `control.turn_finished`

典型位置：

- `maybeFlushPlaybackCompletion()`：`usePlaybackCompletionCoordinator.ts:87-142`
- `schedulePlaybackSettlementWindow()`：`usePlaybackCompletionCoordinator.ts:144-166`

这些 guard 是结束状态机的一部分，不建议误删。

### 当前需要关注的点

如果上游 session 身份解析进一步收口，这层可以继续减少对 sessionId / orchestrationId 转换的依赖，但整体已经不属于“重灾区”。

## 7. `usePetDesktopController.ts` 与 `usePetRuntimeSnapshotPublisher.ts`

### 当前问题性质

这两层不是当前防御性编程问题的主战场。

### 结论

- `usePetDesktopController.ts` 的问题更偏“装配面过大”，不是 guard 过多
- `usePetRuntimeSnapshotPublisher.ts` 当前条件判断很少，主要是投影层

这两层暂时不建议先动。

## 当前问题的根因归纳

把这轮审阅收束成一句话，就是：

```text
边界没有尽早定型，身份没有尽早收口，职责没有尽早拆开
```

于是系统只能在中间层不断补这些东西：

- 重新 normalize
- 重新 fallback
- 重新判断这是谁的一轮
- 重新判断现在能不能推进

最终给人的主观感受就是：

- 局部都能讲通
- 但拼起来不像一个自然的整体

## 整改优先级

建议按下面顺序逐一处理。

## 第一优先级：收口前端协议接入层

目标：

- 先把 `useAdapterConnection.ts` 从“混装层”收成“边界层 + 事件映射层 + 运行态写入层”

建议拆分方向：

1. 协议 ingress / parse / version guard
2. 协议到内部事件的 mapping
3. 内部事件写 session 与 runtime state
4. playback release facade

验收标准：

- 内部大多数逻辑不再直接读 `ProtocolEnvelope`
- `normalizeOrchestrationId(...) ?? state.currentOrchestrationId` 这种写法显著减少
- `not_requested -> absent` 兼容映射只保留在一个边界点

## 第二优先级：收口后端 TurnCoordinator

目标：

- 把 turn 生命周期和动作生成管线拆开

建议拆分方向：

1. lifecycle
2. motion dispatch
3. inline motion parser / validator
4. protocol emitter

验收标准：

- lifecycle 层不再直接处理 motion payload normalize / validate
- inline anim 解析不再散落在 turn 主路径中
- stale turn / duplicate schedule 规则有独立边界

## 第三优先级：把 session 身份解析继续前移

目标：

- 让 `useTurnPlaybackSessionStore.ts` 更像纯状态机，而不是兜底工厂

建议动作：

1. 明确哪些事件允许隐式新建 session
2. 明确哪些事件必须命中已有 session
3. 让更多内部事件带稳定 session key 再进入 store

验收标准：

- `ensureSession()` 的使用场景明显收窄
- interrupt / terminal 事件不再隐式依赖 fallback 创建

## 第四优先级：守住 bridge 边界，不让它继续膨胀

目标：

- 保持 `useDesktopBridge.ts` 是投影层，不让它重新演化成事实层

验收标准：

- bridge 只传运行态与必要工具态
- 长期事实仍归后端

## 本轮不建议做的事

### 1. 不建议为了“减少 if”而机械重构

如果只是把一个大函数拆成十个小函数，但职责边界没变，问题不会消失。

### 2. 不建议把健康状态机判断一起删掉

像播放起播条件、播放完成条件、phase 合法迁移，这些 guard 是业务规则，不是坏味道。

### 3. 不建议先动编排核心和完成判定核心

当前最拧巴的不是：

- `turnPlaybackOrchestratorCore.ts`
- `usePlaybackCompletionCoordinator.ts`

而是它们上下游的边界层和身份层。

## 建议的逐项处理清单

后续可以按这个清单一项项推进：

1. 先拆解并收口 `useAdapterConnection.ts`
2. 再拆解并收口 `turn_coordinator.py`
3. 然后继续前移 session identity 解析
4. 最后检查 bridge / controller 是否还需要进一步瘦身

## 最终目标

理想状态不是“没有防御性编程”，而是：

```text
边界层负责防御
状态机层负责规则
编排层负责时序
事实层负责真源
```

做到这一点之后，中间件里的代码会自然变得更顺，而不是靠不断补 guard 才勉强成立。
