# 当前实现与交互表现基线

本文是当前源码的交互表现基线，关注角色如何从输入、对话和 Persona 结果形成可感知的动作。它不替代协议契约，也不描述 Prompt 文本、Live2D/Cubism 内部实现或 C++ 运行时。

## 一条回复如何变成表现

```text
用户文字 / 麦克风
  -> Adapter Turn 与 Persona 生命周期
  -> Persona Effect 或独立动作 Provider
  -> engine.motion_intent.v4 校验
  -> output.segment.v6 / output.segment_motion
  -> SessionStore 记录段事实
  -> PlaybackTimeline 协调文本、音频、动作和口型
  -> ModelEngine 编译语义动作
  -> Live2D 参数混合与绘制
```

Adapter 负责身份、段关联、取消和交付收口；前端负责时间线、动作计划和参数执行。动作结果不会直接写入 Live2D 参数，也不会创建第二个播放时钟。

## 当前已经具备的表现保护

- Persona 多段输出按段索引绑定 TTS 和动作，后到结果不能覆盖其他段。
- 连续动作使用内部 `ContinuityEnvelope` 传递前一段的活动轴、方向和参数所有权。
- `PerformanceGovernor` 限制活动轴数量和序列步数，并降低连续相同方向的强度，避免每段都以同一姿态打满。
- 抢占或段间切换会为前一段未被下一段接管的参数生成 neutral 释放衔接。
- 音频完成后仍可接收动作，但只保留 1.8 秒的动作尾部窗口；过期动作失败，不重播音频。
- 待音频起播的动作缓存最多 30 秒、64 条；超过容量按最旧项降级。
- 动作 Provider 的通用流式文本收集最多 16,000 字符；超限会关闭流并将该动作段降级为失败，核心文本和 TTS 继续。
- 轻量预动作、独立动作和 Performance Curve 均属于可选增强，失败不阻塞核心文本和 TTS。

## 交互表现的主要风险

静态代码可以确认边界和状态转移，不能确认角色是否“自然”。当前最需要现场观察的不是协议正确性，而是以下体验：

1. 首个音节出现时，字幕、口型和第一段姿态是否同时进入。
2. 多段回复中，上一段的余势是否自然交给下一段，是否出现突然归零或重复点头。
3. 用户打断时，当前姿态是否快速收势，下一轮是否从合理的中间状态开始。
4. 动作 Provider 迟到、超时或失败时，角色是否保持可用的低强度表现，而不是停在半动作上。
5. 相同情绪连续出现时，重复方向抑制是否仍保留人格辨识度，没有把表达压得过平。
6. 待机、桌面观察和正式回复切换时，前台动作是否始终拥有优先级。

## 后续优化优先级

第一优先级是建立“动作质量”观测：记录动作首帧延迟、音频相对偏移、段间衔接、抢占释放和迟到丢弃原因，并与实际截图或录屏人工对照。第二优先级是继续调整 Governor 的预算和重复方向衰减，让不同 Persona 和不同模型 Profile 有可控的表现差异。MotionLab 原始事件的保留策略仍需单独处理。

## 验收边界

当前实现已经完成源码级的容量、身份、清理和失败路径收口；以下内容仍需在真实 AG99、TTS、Electron、目标 Live2D 模型和音频设备上确认：首帧延迟、语音随动、段间连续性、抢占收势、待机切换和 Provider 失败后的观感。
