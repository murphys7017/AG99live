# 当前前后端动作链路结构说明

本文描述 AG99live 当前“文本 / 音频 / 动作”主链路的真实结构。

重点不是回顾历史，而是回答三个问题：

1. 现在一轮播放在前后端是怎么流动的
2. 前端现在靠什么对象组织这轮播放
3. 每个核心模块分别负责哪一段

## 1. 当前结构判断

结论：当前前端主链路以播放会话为核心组织文本、音频和动作。

现在最核心的统一概念是：

```text
TurnPlaybackSession
```

也就是一轮回复从收到文本 / 音频 / 动作，到本地播放完成，再到后端确认收口的统一前端对象。

因此，当前更值得持续关注的是：

- 补更高价值的时序测试
- 补更清楚的调试投影
- 在真实模型上校准同步体感

## 2. 主链路总览

### 2.1 从用户发送到整轮结束

1. 前端 `useAdapterConnection.sendText()` 发送 `input.text`
2. 后端 `TurnCoordinator` 建立新 turn，并发 `control.turn_started`
3. 后端在同一个 turn 内可能输出多个 assistant segment：
   - segment A: `output.text` / 可选 `output.audio` / 可选 `engine.motion_*`
   - segment B: `output.text` / 可选 `output.audio` / 可选 `engine.motion_*`
   - segment C ...
   - 每个 segment 都必须带非空 `message_id`
4. 前端 `useAdapterConnection` 接收协议消息，并按 `message_id` 把事件写入 `TurnPlaybackSession.segments`
5. `useTurnPlaybackOrchestrator` 观察 active segment，决定文本 / 音频 / 动作何时释放起播
6. `useModelEngine` 接收释放后的动作，必要时再等待音频起播片刻后执行
7. `usePreviewMotionPlayer` 真正驱动 Live2D 写参播放
8. 后端发出 `control.synth_finished`，表示本 turn 的 segment 队列逻辑关闭，不应再追加新的输出片段
9. `usePlaybackCompletionCoordinator` 观察 session，判断队列已关闭且所有 segment 本地播放完成
10. 前端回发 `control.playback_finished`
11. 后端收到 `playback_finished` 后，发出 `control.turn_finished`
12. 前端收到 `turn_finished` 后，把该 session 标记为 `completed` 并清理上下文

注意：`control.synth_finished` 不要求早于所有播放完成。因为一个 turn 内可能有多个输出 segment，前端可以边收边播；`synth_finished` 是“不应再追加新 segment”的队列关闭信号。

现实传输里可能出现 `synth_finished` 先到、同一 segment 的 `output.audio` 后到的竞态。前端允许这种晚到音频补齐已知 segment，但它不能创建匿名 session，也不能创建新的 segment；如果该 segment 的音频已经 release、started 或进入终态，重复 / 晚到音频会被忽略，避免同一段回复播放两次。

后端按上述语义提供 `close_turn_output_queue()`，`synth_finished` 是 turn 级队列关闭信号，而不是单条音频生成完成信号。

### 2.1.1 麦克风输入入口

麦克风输入也先由前端创建新的 `turn_id`，但音频块不再走 JSON 数组主路径：

1. 前端发送 `input.audio_stream_start`
2. 前端通过 WebSocket binary frame 发送 PCM16LE 音频块
3. 前端发送 `input.audio_stream_end`
4. 后端 `SpeechIngressService` 按 `stream_id` 汇总 PCM16LE bytes，并在 end 时进入 STT
5. 转写成功后，后端把转写文本作为该 `turn_id` 的用户输入提交给 TurnCoordinator

`input.raw_audio_data` / `input.mic_audio_end` 是兼容旧前端和调试脚本的路径，不是当前 Electron 前端主路径。

### 2.2 当前完成语义

当前代码里的“这一轮结束”分成三层：

#### 第一层：后端输出队列关闭

后端发出：

```text
control.synth_finished
```

含义是：

- 当前 turn 不应再追加新的 `output.text`
- 当前 turn 不应再追加新的 `output.audio`
- 当前 turn 不应再追加新的 `engine.motion_intent`
- 前端可以把当前已知 segment 集合视为完整队列

这不是“整轮完成”，也不要求发生在所有 segment 播放之前。

`synth_finished` 之后只接受同一 `turn_id / message_id` 的晚到媒体补齐，用于容忍网络和事件调度顺序；它不改变队列已关闭的事实，也不允许引入新的回复片段。

#### 第二层：前端本地播放完成

需要满足：

- `control.synth_finished` 已到达，segment 队列已经关闭
- 文本已 delivered
- 音频已进入终态
  - `completed`
  - `failed`
  - `absent`
- 动作已 `completed`，或者动作已明确 `absent`

所有 segment 都满足上述本地 settled 条件后，前端发送：

```text
control.playback_finished
```

#### 第三层：整轮协议收口完成

后端收到 `control.playback_finished` 后，发出：

```text
control.turn_finished
```

只有本地播放完成和后端收口两个条件都成立后，前端才会：

- 把 session phase 置为 `completed`
- 清理该轮播放上下文

这三层现在必须明确拆开，不再混成一个条件。

## 3. 前端统一对象：TurnPlaybackSession

当前实现位置：

- `frontend/src/turn-playback/session.ts`
- `frontend/src/turn-playback/selectors.ts`
- `frontend/src/turn-playback/useTurnPlaybackSessionStore.ts`

### 3.1 Session / Segment 内部大致内容

当前是 segment-aware 结构。Session 不持有 turn 级 `text/audio/motion` 单槽。

一条 session 持有：

- `backend`
- `phase`
- `interrupted`
- `segments: Map<messageId, TurnPlaybackSegment>`
- `segmentOrder`

每个 segment 持有：

- `text`
- `audio`
- `motion`

session 总体 `phase`：

- `collecting`
- `ready`
- `playing`
- `settling`
- `completed`
- `failed`

### 3.2 当前主键策略

前端播放轮次当前只用：

```text
turnId
```

会话主键：

```text
turn:<turnId>
```

这让一轮文本、音频、动作、播放回执都能挂到同一个 session 上。

当前协议路径不再生成匿名 playback session。如果 `turnId` 缺失，session store 会拒绝创建 session；segment 级文本、音频、动作消息还必须携带非空 `message_id`。

### 3.3 Segment 主键策略

`message_id` 是 segment ID。

同一条回复片段的：

- `output.text`
- `output.audio`
- `engine.motion_intent`

应该携带同一个 `message_id`。前端用这个 ID 把三者写入同一个 `TurnPlaybackSegment`。

## 4. 前端模块职责

### 4.1 `useAdapterConnection.ts`

作用：协议接入层 + 运行态 facade。

当前职责：

- 建立 WebSocket 连接
- 处理 `output.* / control.* / system.* / engine.*`
- 维护一些运行时字段
- 把协议事件写入 `TurnPlaybackSession`
- 提供文本 / 音频释放接口给 orchestrator

当前它不是播放轮次真源。

播放轮次真源在 session store。

### 4.2 `useTurnPlaybackSessionStore.ts`

作用：前端播放轮次状态中心。

当前职责：

- 创建 session
- 按 `turnId` 找到正确 session
- 写入：
  - segment.text received / released / delivered
  - segment.audio received / started / terminal
  - segment.motion received / released / started / completed / absent
  - backend turn started / turn finished / interrupt
- 维护 active session
- 维护 phase 合法迁移

如果想知道“这一轮现在走到哪一步了”，这里是第一查看点。

### 4.3 `useTurnPlaybackOrchestrator.ts`

作用：起播编排层。

它只管开始，不管结束。

当前职责：

- 遍历 session store 中的 session
- 判断是否可以释放：
  - 文本
  - 音频
  - 动作
- 触发 adapter release
- 把动作交给 `ModelEngine`

它的判断基础是 session。

### 4.4 `turnPlaybackOrchestratorCore.ts`

作用：纯逻辑起播策略核心。

当前保留两类等待窗口：

- `AUDIO_MOTION_SYNC_WAIT_MS = 820`
  - 文本+音频已到，等待动作短暂加入
- `TEXT_ONLY_RELEASE_WAIT_MS = 260`
  - 文本先到，短暂等待音频

它负责决定：

- 三者都到齐时一起放
- 音频先到、动作晚到时先放文本+音频
- 无音频时如何放文本和动作
- 动作更晚到时如何作为 late motion 补播

### 4.5 `useModelEngine.ts`

作用：动作引擎编排层。

当前职责：

- 归一化动作载荷
- 对当前主协议 `engine.motion_intent.v3` 做本地编译
- 调 `usePreviewMotionPlayer` 执行参数计划
- 在动作已进入引擎后，必要时短暂等待音频起播

重要点：

- 现在它读取音频 timing 时，优先读 session
- 它仍保留 pending payload 队列，但不再自己定义整轮播放语义

当前动作轴设计口径：

- 主轴不是简单等同于 `control_role=primary` 的旧直觉，而是角色动作骨架。
- 头部偏转、身体扭转/摇晃、眼睛开闭属于动作主轴体系。
- 嘴巴开闭是动作成立的重要轴，但说话时由 runtime/lip sync 优先管理。
- 嘴角笑意、眉毛和视线偏移属于表情辅轴，用于补充态度和细节。
- Live2D motion 用于反推主轴和辅轴选择；前端仍执行 ModelEngine 编译出的参数计划，不直接播放 motion 文件作为主链路动作协议。

### 4.6 `usePreviewMotionPlayer.ts`

作用：真正的 Live2D 参数计划播放器。

当前职责：

- 解析 `engine.parameter_plan.v2`
- 按需要重定时
- 调用 Live2D runtime 写参
- 动作完成事件由 SDK 回调驱动（`DirectParameterPlanTerminalEvent`），通过 `runId` 归属到对应 segment
- 前端 setTimeout 只作为 watchdog 超时保护（`+800ms`），不再作为主完成路径
- 支持 soft handoff
- 支持重复计划去重与重启节流

### 4.7 `usePlaybackCompletionCoordinator.ts`

作用：播放完成编排层。

它只管结束，不管开始。

当前职责：

- 观察 session store
- 判断前端本地播放何时已经 settled
- 判断何时具备发送 `control.playback_finished` 的条件
- 发送 `control.playback_finished`
- 在后端 `control.turn_finished` 回来后，把 session 标成 `completed` 并清理上下文
- 动作完成不再全局 watch `motionPlayer.state.status`，改为由 `usePreviewMotionPlayer` 的 `onFinished` 回调直接调 `completeMotionPlayback(event)`，携带 `runId` 精确归属 segment
- 当前动作段通过 `currentMotionRun: { runId, segmentKey }` 跟踪，`completeMotionPlayback` 先校验 `event.runId` 再定位 segment
- `stopped` + `reason="interrupted"` 标记 motion failed，避免 segment 卡在 `motion.started=true`

这里的关键语义是：

```text
local playback settled
!= backend turn finished
```

两者保持拆分。

### 4.8 `usePetDesktopController.ts`

作用：桌宠运行时总装配器。

它把下面这些拼到一起：

- `useAdapterConnection`
- `useTurnPlaybackSessionStore`
- `useTurnPlaybackOrchestrator`
- `usePlaybackCompletionCoordinator`
- `useModelEngine`
- `usePreviewMotionPlayer`
- `useDesktopBridge`

它负责总装配，不负责自己发明新的播放语义。

### 4.9 `usePetRuntimeSnapshotPublisher.ts`

作用：把运行态投影给其他窗口。

当前会投影 active session 摘要：

- `activeSessionId`
- `activeSessionPhase`
- 文本是否 ready
- 音频终态
- 动作是否 started / completed
- 后端是否 synth_finished / turn_finished

这让辅助窗口至少能看到当前播放轮次的大致推进。

## 5. 后端模块职责

### 5.1 `runtime/session_state.py`

作用：后端单连接 turn 状态机。

当前职责：

- 管理 `current_turn_id`
- 区分：
  - thinking
  - synthesizing
  - playing
- 在有音频时等待前端 `playback_finished`

### 5.2 AstrBot motion middleware

作用：默认动作意图来源和 prompt 能力注入层。

当前动作生成链路统一为 middleware-first：

- 主聊天模型只负责正常回复文本，不输出动作标签
- `AG99liveMotionPromptContributor` 向 AstrBot interaction prompt 注入动作能力和运行态上下文
- 注入内容包含当前 `semantic_axis_profile` 的 `primary/hint` 轴、`intent_tags` 语义提示、`ag99live.motion` Persona Effect 的 arguments 示例和动作风格指令
- `AG99liveMotionResultContributor` 从 interaction result 的 `view.effect_calls` 中消费 `ag99live.motion`，归一化为动作载荷后以 `client_objects` 下发
- 后端继续只广播 `engine.motion_intent`，当前自动链路 payload 为 `engine.motion_intent.v3` flat axes，前端 ModelEngine 负责编译为参数计划
- 自动链路不让 LLM 选择 catalog motion、motion3、exp3 或 `motion_id`；旧素材能力只保留在动作实验室、预览和手动调试等独立路径
- `<@anim {...}>` 仅作为官方 AstrBot 兼容传输壳保留：只有运行环境缺少 Persona Effect 注入函数时才由 prompt 要求追加，并且标签内部仍必须是 `engine.motion_intent.v3`；如果 `ag99live.motion` 主链路生成了无效 payload，不会回退到 `<@anim>`。

动作入口判定：

| 运行时能力 | prompt 要求 | 后端消费入口 | 失败处理 |
| --- | --- | --- | --- |
| 支持 Persona Effect 注入 | 填写 `ag99live.motion` arguments | `view.effect_calls` -> `client_objects` | payload 无效时记录错误，不转 inline |
| 不支持 Persona Effect 注入 | 回复末尾追加官方 `<@anim>` 包装 | `raw_reply_text` 中的 `<@anim>` | JSON/schema/v3 payload 无效时拒绝，不生成替代动作 |

这张表只描述自动动作链路。动作实验室、预览调试和手动素材播放仍是独立工具链，不应被拿来兜底自动回复动作。

### 5.3 `runtime/turn_coordinator.py`

作用：后端协议和轮次编排中枢。

当前职责：

- 接收入站协议
- 建立 turn
- 广播 `output.text / output.audio / engine.motion_intent`
- 在音频轮次下等待前端 `control.playback_finished`
- 收到后发送 `control.turn_finished`

当前顺序要点：

```text
output.*
-> control.synth_finished
-> 前端播放
-> control.playback_finished
-> control.turn_finished
```

这里的 `control.synth_finished` 是 turn 级输出队列关闭信号，而不是 segment 级音频完成信号。

`output.audio.audio_url` 指向适配器 HTTP 静态缓存资源，常见路径是：

```text
/cache/audio/*.wav
```

该 HTTP 服务绑定到适配器配置里的 `host / http_port`。前端连接适配器后可能把音频 URL 的 host 重写为当前 WebSocket 可达 host，再交给浏览器音频和 lip sync fetch 使用。因此，音频 URL fetch 失败属于“音频交付 / 静态资源服务”问题，不应直接归因于 TTS 生成失败。

## 5.4 麦克风输入链路

当前麦克风输入也是 segment-aware：

```text
start microphone capture
-> create fresh turn id
-> input.audio_stream_start
-> WebSocket binary AG99 PCM16LE chunks
-> input.audio_stream_end
-> backend STT ingress
```

关键约束：

- 一段录音内的 start、binary chunk 元数据和结束信号共享同一个新的 `turn_id` 与 `stream_id`
- 不再借用当前 assistant playback 的任何额外编排 ID
- 后端 STT ingress 以 `stream_id` 作为音频流缓冲键，避免不同录音段互相串音
- 设备切换时，前端会先发送旧输入段的 `input.audio_stream_end(reason=\"device_change\")`，再开启新输入段
- 如果前端检测到发送积压，该段会被标记为 broken
- `input.audio_stream_end.payload.dropped === true` 时，后端直接丢弃该段，不做残缺音频转写

Windows / Electron 桌面端当前有两条本地采集来源：

- 原生路径：主进程 `native-microphone.ts` 调用 ffmpeg DirectShow 列出真实输入设备，并用选中的 DirectShow alternative name 采集 `s16le` 单声道 16 kHz 音频。preload 把 PCM16LE chunk 转发给渲染进程。
- Web fallback：原生设备不可用或未选择原生设备时，前端通过 `navigator.mediaDevices.getUserMedia` 和 AudioWorklet 采集，并在 renderer 内转成 PCM16LE。

按键说话模式只控制采集生命周期，不改变音频流协议形态：

- 设置窗口写入 `pttModeEnabled` 和 `pttKeyBinding`。
- 主宠物窗口持有 adapter runtime，并监听 DOM 键盘事件和主进程 `desktop:ptt-keydown / desktop:ptt-keyup`。
- 主进程通过 `uiohook-napi` 做全局键盘 hook；能映射到 `uiohookKeycode` 的按键可在窗口失焦时触发。
- keydown 开始一段新录音，keyup 以 `reason=\"ptt_release\"` 结束同一段录音。

### 5.5 interrupt 与音频终态

当前 `control.interrupt` 的前端处理语义：

- 如果当前有 segment 音频已经进入本地播放释放流程，不管它是“正在播放”还是“已释放但尚未真正开始播放”，都会先写入：

```text
segment.audio.terminal = "failed"
segment.audio.reason = "audio_playback_interrupted"
```

- 然后才清理本地 audio runtime 和 active turn 上下文

这样 session / segment 数据不会再留下 `audio.started = true` 或 `audio.released = true` 但 `terminal = idle` 的半截状态。

## 6. 当前结构关注点

当前更值得持续关注的是：

1. `TurnPlaybackSession` 是否继续保持为播放事实来源
2. `control.synth_finished / playback_finished / turn_finished` 的三层语义是否持续清晰
3. `engine.motion_intent -> frontend ModelEngine -> engine.parameter_plan.v2` 这条链路是否继续保持职责稳定
4. session 调试投影和高价值时序测试是否足够支撑后续动作引擎工作
