# 前后端动作链路结构

本文描述从 Persona Effect 到 Live2D 逐帧执行的唯一正式动作与播放链路。

## 1. 总体链路

```text
Persona Runtime
  -> spoken_reply + effect_calls[ag99live.motion]
  -> AG99 result contributor
  -> engine.motion_intent.v4
  -> 后端 PendingOutputSegment.motion
  -> output.segment.v4.motion
  -> 前端严格归一化
  -> SessionStore 原子提交
  -> TurnPlaybackOrchestrator
  -> PlaybackTimelineRuntime
  -> ModelEngine
  -> PerformanceSchedule
  -> 部位策略与 Parameter Track Graph
  -> engine.parameter_plan.v3
  -> Live2D WebSDK
```

主模型在同一次回复中生成文本和动作语义，Adapter 负责把 Persona Effect 参数转成可校验的 motion intent。前端 ModelEngine 才拥有模型相关采样、关系约束和参数计划编译。

## 2. Persona Effect 与兼容入口

### 2.1 主入口

主入口读取：

```text
view.effect_calls
  -> name = ag99live.motion
```

当前 Persona Effect 输出九级 `axis_levels: -4..4`、`intent_tags`、可选资源 ID 和 duration hint。它不输出连续 Live2D 参数，也不决定逐帧曲线。

### 2.2 官方兼容入口

只有 Persona Effect 注入函数不存在时，Prompt 才允许官方 `<@anim ...>` 形式。Adapter 在后端解析该标签，并把结果写入同一个原子段的 motion slot。

`<@anim>`：

- 是 AstrBot 官方原版环境的输入兼容。
- 不是 Persona Effect 校验失败后的 fallback。
- 不会在前端形成第二条动作播放链。
- 不允许与有效 Persona Effect motion 同时竞争。
- 只接受 `{ "mode": "inline", "intent": { "schema_version": "engine.motion_intent.v4", ... } }`；不保留裸 intent 或旧外层别名。

## 3. 后端段聚合

AstrBot 可能为同一回复产生多个物理组件：

- Plain 可见正文。
- Record WAV 与 canonical assistant text 候选。
- 图片。
- motion client object。
- result contributor 登记、并在 TTS `generating` 状态到达时启动的可选 performance curve 请求标识。

`OutputSegmentCoordinator` 以 `turn_id + message_id` 获取 `PendingOutputSegment`：

```text
Plain.content        -> segment.text
Record.file          -> segment.audio_path
Record.text          -> segment.text（与 Plain / semantic text 必须一致）
motion client object -> segment.motion_payload
Picture              -> segment.images
TTS request id owned by curve runtime -> segment.performance_curve_request_id
```

曲线 Provider 从只读 `on_tts_state_changed` 监听器收到 `generating` 后启动，并直接使用该次 `tts_request_id` 作为请求身份。没有进入 TTS 的回复不创建曲线请求。段出站只同步读取已经 ready 的结果；未 ready 时取消请求并
发送原 motion，不等待、不补默认曲线、也不在 segment 之后发送 patch。

以上 TTS 生命周期只存在于增强版 Core。官方 AstrBot 兼容模式没有 `TTSState`：它在
`on_llm_request` 注入 `<@anim>` V4 约束，以最终 `Record` 作为音频成功事实。AstrBot
`TurnDeliveryCoordinator` 在 `after_message_sent` Hook 返回后唯一调用平台事件的
`complete_visible_turn()`，由该事件关闭 Adapter 输出队列。该模式无法可靠区分 TTS 未触发与生成失败，
因此无 `Record` 时使用 `audio=absent`，且不启动可选 performance curve；禁止伪造状态或请求 ID。

冲突处理是 fail-visible：

- 同一字段出现两个不同值：报冲突。
- 同一段出现多个音频文件：报错。
- 多个 motion object：报错。
- motion schema 或资源非法：报错。
- WebSocket 发送失败：保留未发送段并报错。

动作是否“本应存在”由同一回复阶段写入的 `ag99live_motion_schedule` 决定：

- 未安排语义动作：motion slot 为 `absent`。
- 已安排且 payload 合法：motion slot 为 `present`。
- 已安排但 effect 缺失、解析失败或 payload 非法：motion slot 为 `failed`，保留明确 reason。

因此“没有收到 motion object”本身不能直接解释为 `absent`，正式动作失败也不能被
前端内部 speech-only 计划覆盖。

曲线 attached/skipped 记录、上一动作 Prompt snapshot 和 Motion Lab assistant output 都只在 `output.segment` WebSocket 发送成功后提交；发送失败的段不会推进这些状态。

输出队列关闭时，后端先发送每个完整 `output.segment`，成功后才从 pending map 删除；全部段发送成功后再发送 `control.synth_finished`。

## 4. 原子外部协议

正式回复只使用：

```text
output.segment
payload.schema_version = output.segment.v4
```

每段必须完整声明：

```text
text: present | absent | failed
audio: present | absent | failed
motion: present | absent | failed
speech: present | absent
images: string[]
```

表演曲线若已就绪，只存在于 `motion.payload.performance_curve_hint`，不再拥有 segment 顶层副本。

正式 turn 不再发送：

- `output.text`
- `output.audio`
- `output.image`
- 独立 `engine.motion_intent`
- 独立 `engine.performance_curve_hint`

独立 `engine.*` 只属于动作实验室和手动预览。

## 5. 前端接收边界

前端把拒绝边界分成三层：

1. 信封版本、身份和 tagged slot 结构由 parser 严格校验；失败时不进入业务分发，也不写 SessionStore。
2. 已解析事件继续完成音频 URL 重写和 motion payload 领域归一化；失败时提交一条
   `state=rejected` 的段事实，不释放其中的文本、音频或动作。
3. SessionStore 检查 session 阶段、`synth_finished` 边界和重复 `turn_id + message_id`；
   重复或迟到提交只拒绝本次写入，不覆盖首段，也不关闭 WebSocket。

领域预检完成后统一调用一次：

```text
SessionStore.commitOutputSegment(turnId, messageId, material)
```

该函数在局部构造完整 segment，最后一次性放入 session map。接受段保存完整播放材料；
领域拒绝段只保存 rejection reason，并被视为已结算失败。任何提交结果产生前都不会释放文本、音频或动作。

`control.synth_finished` 到达时，SessionStore 会断言所有内部段已经完整解析。已记录的 rejected
段满足解析完成条件，但会让最终播放回执失败；接受段若仍有 idle slot，则直接报告一致性错误，
不自动补成 `absent`。

## 6. Release 与执行

`TurnPlaybackOrchestrator` 只观察 SessionStore：

- 不保存第二份 slot readiness。
- 不等待后续分片。
- 不运行 text/audio/motion/speech 补齐定时器。
- 每个完整段只创建一个 `SegmentJob`。
- 只在当前没有开放的 required execution Timeline 时释放下一段，避免前一段的
  speech-only 尾部与后一段同时写模型参数。

`PlaybackTimelineRuntime` 在构造时获得固定 execution ports，并拥有：

- text sink release。
- audio sink 与真实时钟。
- lip-sync sink。
- required motion sink。
- sink started / terminal 状态。

`createConversationPlaybackRuntime.ts` 在 App composition root 内创建唯一的 `PlaybackTimelineRuntime` 和 `BrowserAudioTimelineSink`，并在 ModelEngine sink 就绪后只绑定一次。Adapter 只提供协议入站、字幕显示、音频播放与 UI 状态桥接 ports；完整 Segment 素材只由 SessionStore 保存。Adapter 不接收 Timeline factory，也不拥有 Timeline 实例创建权。

有音频时，Timeline 在 Audio metadata 给出真实 duration 后预编译语义动作或内部 `speech_only` request；Audio `playing` 事件携带绑定本段 AudioElement 的时钟，并立即启动已准备计划。禁止从全局 active audio element 反查时钟。动作自身的入场时机由 performance curve / parameter plan 决定，不再叠加固定延迟。audio 明确 `absent` 时才允许 synthetic motion-only timeline；audio `failed` 时不允许转成 motion-only。

## 7. ModelEngine 与 WebSDK

ModelEngine 的输入是归一化 motion intent 和 matched timeline snapshot。主要阶段：

```text
intent validation
  -> axis level sampling
  -> intensity
  -> semantic relation graph
  -> mode resolution
  -> timing
  -> CompiledSemanticMotion
  -> speech gesture track
  -> model parameter binding
  -> resource policy
  -> parameter_plan.v3
```

ModelEngine 负责：

- 九级锚点内的确定性采样。
- profile revision 校验。
- 轴关系图与硬约束。
- expression / motion resource 冲突。
- speech gesture 规划。
- 在起播前根据真实音频总时长生成 timing；晚到的显式非音频路径才使用自身时钟语义。

当前编译期的时间所有权位于 `PerformanceSchedule`：它统一保存 canonical text 的 phrase、sequence
step、semantic-group transition、SpeechPose 和部位事件。Parameter Track Graph 只把这些已编排事件
投影为现有 V3 keyframes/modulation；它不创建第二套时钟，也不重新解释主模型的九级动作方向。

这里需要区分 AG99 的 Live2D 运行时适配层与官方 Cubism SDK：

`frontend/src/live2d/WebSDK/src/` 是 AG99 的运行时层，负责：

- 逐帧曲线求值。
- velocity / acceleration 限制。
- speech gesture delay。
- lip-sync 与 speech energy source 生命周期。
- 从 Cubism Motion / EyeBlink / Expression / drag / breath 读取 base snapshot。
- 由 Parameter Mixer 组合 direct plan 与 lip-sync、执行唯一最终 clamp，并在 Physics 前一次写入主动参数。
- 调用官方 Cubism 的模型、Physics、Pose 和渲染能力。

官方 Cubism `Framework` / `Core` 只提供模型加载、参数存取、Physics 解算和最终绘制能力，
不负责理解 Turn、语义轴、文本、Performance Schedule 或 AG99 参数来源。

Performance Director 只负责生成参数轨道和时间结构，不参与上述逐帧来源融合。

同一类调整只能有一个主要所有者，避免 Adapter、ModelEngine 和 WebSDK 重复修正同一轴。

## 8. 终态

本地段 settled 要求：

- text 已 delivered。
- audio 为 `completed | failed | absent`。
- motion 为 `completed | failed | absent`。

SessionStore 槽位 settled 不等于 Timeline 已结束：speech-only 运行期间 motion slot
仍保持 `absent`，但 required motion sink 可能继续执行。全部段 settled、收到
`synth_finished`，并且同一 Turn 不存在开放的 required execution Timeline 后，
CompletionCoordinator 才发送 `control.playback_finished`。后端随后发送
`control.turn_finished`，前端 session 才进入 completed。

WebSocket 断开时，后端先停止全部在飞 AstrBot event，再清理段和映射；前端停止全部
Timeline。两端都不得让断连前的异步回调重新投递输出或重建播放状态。

零 sink 段允许：

```text
collecting -> ready -> settling -> completed
```

正常播放段使用：

```text
collecting -> ready -> playing -> settling -> completed
```

## 9. 关键文件

- `middleware/interaction_motion/`：AstrBot 动作交互边界；Prompt、Effect 解析、结果调度和兼容性分别由独立模块负责。
- `runtime/output_segment.py`：后端原子段缓冲。
- `runtime/turn_coordinator.py`：协议路由、Turn 生命周期和连接级清理。
- `runtime/output_segment_coordinator.py`：物理输出组件聚合、校验和 `output.segment.v4` 出站。
- `runtime/motion_observation_recorder.py`：MotionLab 观察与 Prompt 动作历史投影。
- `runtime/performance_curve_coordinator.py`：可选 performance curve 请求、附加和清理。
- `adapter-connection/inbound/`：前端严格协议入口。
- `turn-playback/useTurnPlaybackSessionStore.ts`：协议槽位与稳定投影事实源。
- `turn-playback/useTurnPlaybackOrchestrator.ts`：SegmentJob release。
- `playback-timeline/playbackTimelineRuntime.ts`：统一时钟和 sinks。
- `model-engine/`：动作编译。
- `live2d/WebSDK/src/lappmodel.ts`：逐帧执行。
