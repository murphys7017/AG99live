# 文本语音动作同步播放编排设计

本文描述当前第一版“文本 / 语音 / 动作”同步播放编排方案。

这里说的同步，当前是：

```text
同轮聚合 + 尽量同时起播 + 明确的完成回执边界
```

不是音素级同步。

## 1. 当前目标

当前系统已经把“起播”和“完成”拆成两层：

- `useTurnPlaybackOrchestrator`
  - 负责什么时候开始
- `usePlaybackCompletionCoordinator`
  - 负责什么时候可以宣布本地播放完成

本方案关心的是前一层，也就是：

```text
同一轮文本 / 音频 / 动作怎样尽量一起发生
```

这里的一轮不是“AI 只回复一句”。真实模型是：

```text
一个 user input
-> 一个 turn
-> 多个 assistant output segment
-> 每个 segment 绑定一组 text / audio / motion
```

## 2. 当前适用范围

当前方案覆盖：

- 同 turn 内多个 segment 按 turn session 聚合
- 同一 segment 的文本、音频、动作按 `message_id` 聚合
- 文本先到时先缓存
- 音频先到时先缓存
- 动作先到时先缓存
- 尽量一起释放
- 动作晚到时短等待
- 无音频轮次显式按 `absent` 语义处理

这里的“segment”是 assistant 输出片段，不是麦克风输入片段。麦克风输入也已经按独立 capture segment 组织，但它属于输入协议链路，不属于本文的播放编排对象。

当前不覆盖：

- 音素级口型同步
- 逐词字幕对齐
- 音频内容分析驱动动作节奏
- 新的帧级 motion mixer

## 3. 核心结构

当前前端链路已经不是“pending 队列自己互相观察”这种结构，而是：

```text
协议事件
-> useAdapterConnection
-> TurnPlaybackSessionStore
-> useTurnPlaybackOrchestrator
-> ModelEngine
-> PreviewMotionPlayer
```

### 3.1 Session 是轮次真源

当前同一轮的文本 / 音频 / 动作状态都先写入 `TurnPlaybackSession`。

当前外部协议已经只有 `turn_id` 一个交互身份。前端 playback session 也已经按 `turn_id` 单键收口，所有播放路由、聚合和完成判定都只基于这一个轮次主键。

当前已经是 segment-aware 结构：

```text
TurnPlaybackSession
  -> segments: Map<messageId, TurnPlaybackSegment>
       -> text
       -> audio
       -> motion
```

同一条回复片段的 `output.text`、`output.audio`、`engine.motion_intent` 应携带同一个 `message_id`，前端用它聚合同一个 segment。orchestrator 不直接以 adapter 的散装字段作为逻辑真源，而是观察 session 中当前 active segment。

### 3.2 Orchestrator 只负责 release

它负责决定：

- 何时 release 文本
- 何时 release 音频
- 何时 release 动作

它不负责：

- WebSocket 收发
- 动作编译
- Live2D 写参
- session 完成判定

### 3.3 ModelEngine 负责“进入引擎后的最后一小段等待”

即使 orchestrator 已经 release 动作，`ModelEngine` 仍可在动作已进入引擎后短暂等待音频起播。

这层等待和 orchestrator 的职责不同：

- orchestrator：决定何时把动作交给引擎
- model engine：动作进引擎后，是否还要再等音频一点点

## 4. 当前起播策略

### 4.1 文本 + 音频 + 动作都 ready

```text
立即释放文本、动作、音频
```

顺序上由 orchestrator 调用：

1. release text
2. release motion
3. release audio

动作交给 `ModelEngine` 后，真正启动仍会贴近音频起播。

### 4.2 文本 + 音频 ready，动作未到

此时不立刻放，而是进入一个较宽的等待窗口：

```text
AUDIO_MOTION_SYNC_WAIT_MS = 820
```

如果动作在窗口内到达：

```text
一起释放文本、动作、音频
```

如果窗口超时动作还没来：

```text
先释放文本 + 音频
```

后续动作更晚到时：

```text
作为 late motion 单独释放给 ModelEngine
```

### 4.3 只有文本 ready，音频未到

此时进入一个较短的文本等待窗口：

```text
TEXT_ONLY_RELEASE_WAIT_MS = 260
```

如果短时间内音频仍没来：

```text
先释放文本
```

这样纯文本回复不会被卡太久。

### 4.4 无音频确认

当前无音频不是靠模糊状态猜，而是靠明确终态：

```text
audio.terminal === "absent"
```

`absent` 的判定来源是 `TurnPlaybackSegment.audio`。当 `synth_finished` 到达后，只有仍然没有 audio URL、没有 release、没有 started、并且 terminal 仍是 `idle` 的 segment 才会被标记为 `absent`。已经开始播放或已经 release 的音频不会因为 adapter pending queue 为空而被误判为缺失。

这种情况下：

- 如果动作已 ready：释放文本 + 动作
- 如果动作未 ready：先释放文本

### 4.5 动作晚到后的补播

如果某组已经因为等待超时而先放了文本 + 音频，后续动作再到时：

```text
orchestrator 仍会把动作释放给 ModelEngine
```

此时 `ModelEngine` 会按当前 session / 音频 timing 估算剩余时长，尽量把动作贴到剩余音频窗口里。

## 5. 当前关键常量

当前实现位于：

`frontend/src/composables/turnPlaybackOrchestratorCore.ts`

```ts
const AUDIO_MOTION_SYNC_WAIT_MS = 820;
const TEXT_ONLY_RELEASE_WAIT_MS = 260;
```

当前理解：

- `820ms`
  - 用于等待晚到动作加入同轮起播
- `260ms`
  - 用于避免纯文本回复被过度延迟

它们现在是体感参数，不是协议常量。

## 6. 当前数据流

### 6.1 文本

```text
output.text
-> useAdapterConnection.applyOutputText()
-> sessionStore.markTextReceived(...)
-> useTurnPlaybackOrchestrator
-> adapter.releaseAssistantTextForPlayback(...)
-> sessionStore.markTextDelivered(...)
```

### 6.2 音频

```text
output.audio
-> useAdapterConnection.applyOutputAudio()
-> sessionStore.markAudioReceived(...)
-> useTurnPlaybackOrchestrator
-> adapter.releaseAudioForPlayback(...)
-> audioPlaybackActions.playAudioAndAcknowledge(...)
-> sessionStore.markAudioStarted(...) / markAudioTerminal(...)
```

### 6.3 动作

```text
engine.motion_intent
-> useAdapterConnection.handleSocketMessage()
-> sessionStore.markMotionReceived(...)
-> useTurnPlaybackOrchestrator
-> modelEngine.ingestNormalizedPayload(...)
-> usePreviewMotionPlayer.playPlan()
-> sessionStore.markMotionStarted(...) / markMotionCompleted(...)
```

## 7. 与完成判定的关系

当前要特别区分两件事：

### 7.1 起播编排

由 orchestrator 负责。

它只回答：

```text
什么时候把文本 / 音频 / 动作放出来
```

### 7.2 完成判定

由 completion coordinator 负责。

它回答：

```text
什么时候本地播放已经完成
什么时候具备发送 playback_finished 的条件
什么时候 turn_finished 回来后才能真正清理
```

完成侧现在采用三层信号：

```text
control.synth_finished
= 后端输出队列关闭
= 这个 turn 不会再追加新的 segment

control.playback_finished
= 前端本地播放完成
= synth_finished 已到，且所有 segment 都 settled

control.turn_finished
= 后端确认整轮闭环收口
= 后端收到 playback_finished 后发出
```

因此，`synth_finished` 不要求早于所有播放完成。前端可以边收 segment 边播放；只有队列关闭且已知所有 segment 都 settled 后，才发送 `playback_finished`。

后端必须保证 `synth_finished` 是 turn 级队列关闭信号。当前后端已经通过 turn 输出队列关闭点发送该信号，不能再把它退化成单条音频生成完成信号。

两者不能混写，否则：

- 起播等待策略
- 完成收尾策略

会重新搅在一起。

## 8. 当前测试覆盖

当前前端纯逻辑测试已覆盖：

- 三者都到齐时一起释放
- 音频到、动作晚到但窗口内到达
- 音频到、动作超时后晚到补播
- 文本-only 短等待释放
- 无音频确认下释放文本 + 动作
- 不同 turn 组互不串组
- Session store 轮次主键、状态迁移、absence 语义
- Completion coordinator 的本地 settled / playback_finished / turn_finished 顺序
- turn 内多 segment 的队列关闭语义

测试命令：

```powershell
cd frontend
npm run test
```

## 9. 当前关注点

当前更值得持续观察的是：

1. 等待窗口是否与真实模型体感一致
2. session 的 release reason / settling reason 是否足够可见
3. interrupt / stale turn / 快速连发时序是否稳定
4. 当前“同轮聚合 + 尽量同时起播”策略是否仍然满足实际体验
