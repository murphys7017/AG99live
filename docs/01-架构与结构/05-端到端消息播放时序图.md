# 端到端消息与统一播放链路

本文描述当前真实实现，不描述旧播放链路或目标草案。范围从 Prompt 构建开始，一直到文本、音频、口型和动作完成并向后端发送播放回执。

## 2. 当前主链路

```text
Prompt 构建
  -> 主模型一次生成 spoken_reply + effect_calls
  -> Persona Effect result contributor 生成 motion_intent.v4
  -> TTS 生成 WAV Record
  -> TurnCoordinator 按 turn_id + message_id 发出协议消息
  -> SessionStore 聚合同一 logical segment
  -> Orchestrator 决定何时 release
  -> PlaybackTimelineRuntime 建立 audio / lip_sync / motion sinks
  -> HTMLAudioElement 提供真实时钟
  -> audio playing 后 90ms 唤醒 ModelEngine 动作
  -> ModelEngine 编译 parameter_plan.v2
  -> Live2D WebSDK 逐帧插值、动力学、口型和参数写入
  -> Timeline 回写终态
  -> playback_finished / turn_finished 收口
```

当前主路的动作协议是 `engine.motion_intent.v4`。`<@anim>` 只在 Persona Effect 注入能力不存在时作为 AstrBot 官方兼容入口，不是动作失败后的兜底。

## 3. 身份与消息类型

一个用户 turn 可以有多个 assistant segment。每个 segment 必须由下面的复合键唯一标识：

```text
turn_id + message_id
```

同一逻辑回复可能被 AstrBot 物理拆成 Record 与 Plain 两条 message chain：

- `Record.text` 只进入 `output.audio.caption_text`，用于语音字幕和口型语义，不进入可见聊天正文。
- `Plain` 才生成 `output.text`，进入可见聊天历史。
- motion client object、音频和正文必须使用同一个归一化逻辑 `message_id`。

前端允许这些协议事件乱序到达，但不允许它们跨 segment 合并。

## 4. 各层所有权

| 层 | 唯一职责 | 不应承担 |
| --- | --- | --- |
| Persona Runtime / LLM | 回复语义、动作意图与九级轴强度 | Live2D 参数动力学、播放时钟 |
| AG99 adapter | effect_calls 校验、协议转换、资源与 profile 身份校验 | 前端逐帧插值 |
| SessionStore | 持久保存 turn / segment 事实 | 决定具体播放实现 |
| TurnPlaybackOrchestrator | 根据事实决定何时 release segment slots | 音频播放、动作编译、终态模拟 |
| PlaybackTimelineRuntime | 创建 sinks、统一时钟、生命周期和终态 | 动作语义决策 |
| ModelEngine | 轴采样、关系图、资源策略、timing、parameter plan | HTMLAudioElement 所有权 |
| Live2D WebSDK | 每帧曲线、动力学、口型值和 Cubism 参数写入 | 消息聚合与 turn 收口 |
| CompletionCoordinator | 本地 settled 后发送播放回执 | 写入各 sink 的执行终态 |

## 5. 当前起播时序

`SegmentJobExecutor` 的实际顺序是：

1. 释放可见文本。
2. 启动 audio sink。
3. 在同一 segment timeline 上注册 required motion sink。
4. Audio `playing` 后取得真实 `HTMLAudioElement` clock。
5. `AudioStartMotionBridge` 等待 `90ms`。
6. ModelEngine 使用同一 segment 的 timeline snapshot 启动动作。
7. Lip sync 使用同一个 AudioElement 和 WebAudio RMS，不运行第二套音频时钟。

无音频且协议明确为 `absent` 时，motion-only 才能创建 synthetic timeline。原本应有音频但失败时，不允许伪装成 motion-only。

## 6. 等待与失败规则

| 情况 | 当前规则 |
| --- | --- |
| text + audio + motion 已到 | 建立 segment job，音频先获得执行时钟，动作在 audio playing 后 90ms 启动 |
| text + audio 已到，motion 未到 | 最多等待 `820ms`，之后先播放文本与音频 |
| 只有 text，且未声明 audio expected | 等待 `260ms` 后显示文本 |
| 已声明 audio expected | 最多等待 `3000ms`；超时标记 audio failed |
| audio absent | 允许 text-only 或 motion-only synthetic timeline |
| audio failed | 显示正文，终止本段媒体；不转换为 absent |
| Record 先到、Plain 晚到 | late text 单独显示，不重放音频和动作 |
| lip sync 主路径失败 | 记录明确错误；允许口型 sink 使用已定义的随机开合降级，不能影响 speech energy |
| Live2D 模型加载中被替换 | 取消旧 generation；旧异步回调不得访问已释放的 Cubism manager |

## 7. 当前评估

### 7.1 已经合理的部分

1. **身份边界已经统一。** 后端和前端都以 `turn_id + message_id` 管理 segment，动作、音频、正文和曲线不会依赖“当前消息”猜测归属。
2. **字幕与正文已经分离。** `Record.text` 不再被当作第二份可见回复，修复方向是消息类型收口，而不是显示层去重。
3. **统一时钟已经成为正式主路。** 音频、动作和口型都挂在 PlaybackTimeline 下；有音频时不再安装模拟时钟。
4. **动作启动关系符合当前体验目标。** 音频先发声，动作约晚 `90ms`，避免动作先动而声音迟到。
5. **失败解释较严格。** `failed`、`absent`、`completed`、`interrupted` 各自有独立语义，音频失败不会伪装成正常无音频。
6. **Live2D 实例生命周期已收紧。** 模型切换会取消旧加载代际，旧模型、纹理和 uncached motion 回调不能继续触碰已释放实例。

### 7.2 仍存在的风险

1. **中：后端物理输出仍不是原子 segment。** AstrBot 可以把同一句回复拆成 Record 与 Plain 两条链。当前归一化和 late release 已能正确处理，但任何新的输出组件都必须继续遵守相同逻辑 `message_id`，否则仍会产生跨段错配。
2. **中：release 状态机与 execution 状态机仍然是两层。** Orchestrator 管 ready/release，Timeline 管 started/terminal，这个分层本身合理，但接口较多，新增 sink 时容易把 SessionStore 写入权放错层。后续迁移应继续减少 adapter execution ports，而不是把两层合并回一个大 runtime。
3. **中：固定 `3000ms` TTS 等待对慢环境敏感。** 这是明确失败策略，不是隐藏兜底，但在远程 TTS 或首次冷启动时可能误判超时。应先记录真实分位延迟，再决定是否配置化或按 provider 建模。
4. **低：performance curve 是非阻塞质量增强。** 小模型结果在音频出站前未完成时会记录 `not_ready_before_audio_egress` 并跳过该 hint。主播放链不会卡住，但相同语义的 timing 表现可能因小模型响应速度不同而变化。
5. **验证缺口：仍需要一次真实 Electron 端到端回归。** 单元测试、类型检查和生产构建已覆盖代码边界，但 Live2D 模型切换、真实 WAV、WebAudio、透明窗口和 GPU 渲染只能通过运行时实测最终确认。

## 8. 下一步优化建议

1. 为随机乱序组合增加协议级集成测试：`motion -> audio -> text`、`audio -> text -> motion`、失败后 late text、同 turn 多 segment。
2. 在 Motion Lab 中统一记录关键时刻：LLM 完成、TTS 完成、协议出站、audio playing、motion started、各 sink terminal。
3. 用真实数据统计 TTS、performance curve 和 motion 到达延迟的 P50/P95/P99，再调整 `260/820/3000/90ms`，避免凭体感继续叠常量。
4. 长期可考虑一个原子的 `output.segment` manifest 先声明本段将包含哪些 slots；正文、音频和动作仍可流式到达，但前端不再依靠多个物理消息推断预期集合。
