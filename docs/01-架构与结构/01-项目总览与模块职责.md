# 项目总览与模块职责

本文是 AG99live 的长期维护型结构总览文档，合并了仓库结构、模块职责、依赖方向和维护规则。

目标：稳定回答下面这些问题：

1. 这个项目当前有哪些一级目录和一级模块
2. 每个模块负责什么，不负责什么
3. 模块之间的大致依赖方向是什么
4. 后续重构时，应该优先把变更落在哪个模块

## 1. 项目定位

AG99live 是一个**桌面虚拟宠物（桌宠）实时交互系统**，由前端 Electron 桌面应用 + 后端 AstrBot 插件适配器组成，通过 WebSocket 协议通信。

当前部署假设是 Electron 与 AstrBot Adapter 位于同一台电脑。桌宠 WebSocket、模型/音频静态
资源和 debug HTTP 只支持 `127.0.0.1` / `localhost`。远程执行器 endpoint 是独立出站连接，
不代表当前桌宠协议支持远程 AstrBot；跨主机部署需要另行设计认证 WSS/HTTPS 和媒体授权。

核心数据流：

```
用户输入（文本/语音）
  → 前端 Electron 应用
    → WebSocket 发送到后端
      → AstrBot 适配器协调 AI 模型
        → 返回文本回复 + 音频 + 动作指令
          → 前端播放：文字显示 + 音频播放 + Live2D 模型动作渲染
```

## 2. 仓库目录结构

```text
AG99live/
  .ai/                          # AI 代理治理入口和状态文件
  astrbot_plugin_ag99live_adapter/  # 后端 AstrBot 适配器、运行时、协议和动作服务
  docs/                         # 架构、协议、设计文档
  frontend/                     # Electron + Vue 前端桌宠运行时和工具窗口
  scripts/                      # schema manifest 等仓库级校验脚本
  tools/                        # 仓库级开发辅助脚本和校验工具
  vts-data-recorder/            # 独立 VTube Studio 原始参数录制器
```

## 3. 系统总体分块

从职责上看，项目分为四个大系统：

```text
前端桌宠运行时
后端适配器与服务
动作与模型能力体系
文档与治理体系
```

更贴近数据流的表达：

```text
用户 / 辅助窗口
  → 前端运行时
    → 后端适配器
      → 模型与动作服务
        → 前端回放与渲染
```

## 4. 前端架构

前端位于 `frontend/`，是桌宠系统的运行时核心。当前建议理解为 **9 个一级模块 + 2 个横切层**。

### 4.1 模块总览

```text
桌面宿主           → Electron 窗口管理
多窗口桥接         → 窗口间状态同步与命令转发
主控制器           → 主窗口组合根（装配所有模块）
适配器协议层       → WebSocket 协议收发与边界校验
播放管线           → 文本/音频/动作播放轮次编排
模型能力管理       → 模型能力事实维护
动作引擎           → 动作意图编译与参数计划生成
虚拟形象运行时     → Live2D 渲染与参数执行
创作工具           → 设置/历史/动作实验室/档案编辑

音频输入输出 (横切) → 音频播放与麦克风采集
协议契约     (横切) → 前后端协议与窗口间通信类型定义
```

模块关系：

```text
桌面宿主
  → 多窗口桥接
      → 主控制器
          → 适配器协议层
          → 播放管线
          → 模型能力管理
          → 动作引擎
          → 虚拟形象运行时
          → 创作工具投影
```

数据方向：

```text
适配器协议层 → 播放管线 → 动作引擎 → 虚拟形象运行时
模型能力管理 → 动作引擎
模型能力管理 → 创作工具
主控制器 → 多窗口桥接 → 创作工具
```

### 4.2 桌面宿主

**位置**：`frontend/electron/main/`、`frontend/electron/preload/`

**职责**：
- 创建宠物窗口、覆盖层、设置、历史、动作实验室、档案编辑器
- 管理透明窗口、鼠标穿透、窗口拖动
- 提供右键菜单和桌面截图
- 暴露预加载接口：`window.ag99desktop`

**边界要求**：
- 不理解适配器 V2 协议
- 不理解播放会话对象
- 不直接参与动作编译和 Live2D 参数计划

### 4.3 多窗口桥接

**位置**：`frontend/src/desktop-bridge/`、`frontend/src/types/desktop.ts`

**职责**：
- 主宠物窗口发布运行时快照和模型能力投影
- 辅助窗口发送运行时命令
- 档案编辑器使用独立的档案编辑命令与快照
- 使用浏览器广播通道实时同步，本地存储兜底恢复

**边界要求**：
- 辅助窗口不直接持有适配器连接
- 辅助窗口不直接修改播放管线内部状态
- 主窗口负责解释命令并调用对应运行时模块

### 4.4 主控制器（组合根）

**位置**：`frontend/src/app/`、`frontend/src/views/PetDesktopView.vue`

**职责**：
- 装配所有核心模块：适配器、会话存储、播放编排器、完成协调器、动作引擎、动作播放器、桌面桥接、快照发布器
- 处理辅助窗口命令和档案编辑器命令
- 计算连接状态、连接标签、阶段消息、人工智能状态
- 触发自动连接适配器
- 通过主窗口子控制器承接按键说话和右键菜单；Live2D 表现设置由 renderer 在初始化与运行期统一应用

**边界要求**：
- 可以装配模块，但不应发明新的播放语义
- 可以转发命令，但不应把具体协议处理写在自己内部
- 主窗口特有监听和桌面桥接细节应落到 `frontend/src/app/use*Controller.ts` 或同级小模块中

**当前主窗口子控制器**：

| 文件 | 职责 |
|---|---|
| `usePetDesktopRuntime.ts` | 主窗口组合根，装配 View 所需的桌面运行时与业务投影 |
| `createConversationPlaybackRuntime.ts` | 对话播放组合：创建 Adapter、Timeline、BrowserAudioSink，并在 ModelEngine 就绪后一次性绑定 motion sink |
| `usePushToTalkController.ts` | Push-to-talk 键盘与主进程 IPC 监听，按当前配置按键启动/停止麦克风采集 |
| `useDesktopContextMenu.ts` | 桌面右键菜单桥接 |

`ModelEngineSettings` 只包含语义动作编译配置。`physicsResponseScale`、`renderDprCap` 与 `ambientMotionEnabled` 归入 `Live2dPresentationSettings`，由 `live2d-renderer` 和 WebSDK 承接，不经过 ModelEngine。

### 4.5 适配器协议层

**位置**：`frontend/src/adapter-connection/useAdapterConnection.ts`、`frontend/src/adapter-connection/`

**子目录结构**：

```text
adapter-connection/
  useAdapterConnection.ts → 适配器协议层 facade
  core/        → 网络连接、消息信封、地址解析、本地偏好、协议常量
  history/     → 后端历史会话操作
  inbound/     → 消息信封校验、事件映射、领域分发器
  model-sync/  → 模型能力同步状态
  motion-tuning/ → 动作调参样本操作
  outbound/    → 统一出站客户端、出站动作
  runtime/     → 音频执行适配、麦克风、播放收口、连接重置
  state/       → 适配器连接状态容器
  features/    → 历史记录、动作调参、模型同步载荷归一化
```

**入站流程**：

```text
WebSocket 原始消息
  → 解析入站信封
    → system.server_info manifest 握手
      → 握手成功后映射为内部事件
        → 分发内部事件
          → 写入会话/模型/音频/历史/动作调参状态
```

`system.model_sync` 使用 `live2d_scan.v3`，只传递 renderer、ModelEngine 和工具窗口实际消费的能力投影。motion constraint 保留扫描器从 `model3.json` 读取的原始 `group + group_index`，前端禁止从去重列表重新推导 SDK locator。扫描缓存与 Prompt 分析中间产物保留在 Adapter；`runtime_cache_errors` 是 model-sync payload 根部的独立运行诊断，不属于 `ModelSyncInfo`。

**出站流程**：

```text
运行时动作
  → 构建消息信封
    → WebSocket 发送
```

**常见出站协议**：`input.text`（发送文本）、`control.interrupt`（中断）、`control.playback_finished`（播放完成）、`system.history_*`（历史操作）、`system.semantic_axis_profile_save`（保存档案）、`system.motion_tuning_sample_*`（动作样本）

**边界要求**：
- 协议信封和载荷校验应在这一层完成
- 进入运行时的事件应尽量是已经定型的内部事件
- 适配器层不应该直接包含动作编译逻辑
- AdapterConnection 不保存 audio started/duration/terminal 的第二份事实；这些由 PlaybackTimeline 和 SessionStore 持有

### 4.5.1 桌面麦克风与按键说话

**位置**：`frontend/electron/main/native-microphone.ts`、`frontend/electron/preload/index.ts`、`frontend/src/adapter-connection/runtime/microphoneCapture.ts`、`frontend/src/adapter-connection/runtime/microphoneDevices.ts`、`frontend/src/adapter-connection/core/pttKeyBinding.ts`

**当前行为**：

- Windows / Electron 桌面端优先通过主进程调用 ffmpeg DirectShow 枚举输入设备，并把设备列表暴露给渲染进程。
- `FFMPEG_PATH` 可指向完整 `ffmpeg.exe`、不带 `.exe` 的可执行路径、ffmpeg 目录或包含 `bin/ffmpeg.exe` 的目录；未配置时从 `PATH` 查找。
- 用户选择 DirectShow 原生设备时，采集由主进程 ffmpeg 输出 `s16le` PCM16LE 音频块，preload 转发给前端麦克风 runtime；没有原生设备或原生启动失败时，前端保留浏览器 `navigator.mediaDevices` fallback，并在 renderer 内转成 PCM16LE。
- 按键说话模式由设置窗口写入桌面运行时命令，主宠物窗口持有真实 adapter runtime；主进程只负责全局键盘 hook 和 `desktop:ptt-keydown / desktop:ptt-keyup` IPC。
- PTT 按键绑定保存在本地偏好里，能映射到 `uiohook-napi` 的按键可全局触发；无法映射的按键只能在桌宠窗口可接收键盘事件时触发。

**边界要求**：

- 辅助设置窗口只发送命令，不直接启动麦克风采集。
- 主进程只做设备枚举、原生采集和全局按键事件桥接，不持有 AG99live WebSocket 协议状态。
- 同一段采集仍由 adapter runtime 分配一个输入 `turn_id`，并通过 `input.audio_stream_start` / WebSocket binary `AG99` PCM16LE chunk / `input.audio_stream_end` 发送给后端。

### 4.6 播放管线

**位置**：`frontend/src/turn-playback/`

**核心对象**：

```text
播放会话
  → 后端状态 / 阶段 / 是否被中断
  → 片段集合: 映射<messageId, 播放片段>
       → 文本 / 音频 / 动作
```

**建模原则**：

```text
一次用户输入
  → 一个播放会话
    → 多个播放片段
      → 每个片段 = 文本 + 音频 + 动作
```

**标识符契约**：

| 标识符 | 归属层级 | 作用 | 缺失时策略 |
|---|---|---|---|
| `turn_id` | 交互轮次层 | 连接输入、输出、动作、播放完成、轮次结束 | 缺失时不再创建交互会话 |
| `message_id` | 单条回复片段 | 绑定同一片段的文本/音频/动作 | 新协议路径必须携带，缺失时作为协议错误 |

**会话标识解析方式**：`turn:<turn_id>`

**起播策略**：

- Adapter 在后端把物理消息链聚合成一个 `output.segment.v3`。
- 前端原子提交完整段，不等待晚到 text/audio/motion patch。
- Orchestrator 从 SessionStore 直接创建一个 SegmentJob，不维护补齐定时器。
- 有音频时以真实 AudioElement 时钟为准；duration ready 时预编译动作，audio playing 时统一释放字幕、口型和动作，动作入场由表演曲线控制。

**完成语义（三层信号）**：

```text
control.synth_finished    = 后端输出队列逻辑关闭，不应再追加新片段
control.playback_finished = 前端本地播放完成（合成完成已到 + 槽位已稳定 + required Timeline 已关闭）
control.turn_finished     = 后端确认整轮闭环收口
```

`synth_finished` 到达前，每个 segment 必须已经完整声明 text/audio/motion slot；到达后不接受新段或 late slot patch。

SessionStore 保存协议槽位和稳定生命周期投影，PlaybackTimeline 保存 required sink 的实时执行事实。
二者不是重复状态：Orchestrator 只有在全局没有开放的 required execution Timeline 时才释放下一段；
CompletionCoordinator 只有在同一 Turn 没有开放 Timeline 时才发送播放完成。该门禁覆盖不会改写
`motion absent` 槽位的内部 speech-only 动作尾段。

**边界要求**：
- 管线不应该理解 WebSocket 原始消息
- 管线不应该编译动作
- 管线只应该通过窄接口通知适配器发送播放完成信号

### 4.7 模型能力管理

**位置**：`frontend/src/adapter-connection/model-sync/useModelSync.ts`、`frontend/src/types/protocol.ts`、`frontend/src/action-lab/parameterActionPreview.ts`

**职责**：维护后端同步来的模型能力事实，包括：
- 当前会话/配置信息、选中模型、可用模型列表
- 资源扫描和参数扫描
- 动作资源池、基础/参数动作库
- 语义轴档案、校准档案
- 运行时缓存错误

**边界要求**：
- 是模型能力事实来源
- 动作引擎和创作工具消费它
- Live2D `Expressions/*.exp3.json` 不作为动作主轴或隐式自动播放目标；它可以提供姿态参考，只有 catalog 明确暴露的 expression 才能由 typed resource 选择
- Live2D `Motions/*.motion3.json` 用于反推真实动作骨架、参数幅度和轴选择依据，不直接作为 LLM 输出协议
- Action Lab 左侧以 tab 区分历史动作和已保存动作样本；保存样本复用同一套参数编辑器继续优化
- 不负责播放编排

### 4.8 动作引擎

**位置**：`frontend/src/model-engine/`

**当前文件**：

| 文件 | 职责 |
|---|---|
| `useModelEngine.ts` | 引擎 facade：持有状态、装配 runtime/start 依赖、暴露对外 API |
| `normalize.ts` | 动作意图和参数计划的入站归一化 |
| `planParser.ts` | 参数计划解析与克隆 |
| `compiler/compileParameterMotionIntent.ts` | 参数动作 compile 主入口，装配两阶段 pipeline 并收口结果 |
| `compiler/compileContext.ts` | compile 共享上下文与中间 state |
| `compiler/contracts.ts` | compile 契约、diagnostics、timing/result 类型 |
| `compiler/registry.ts` | 每个 ModelEngine 实例独立的 stage registry；核心阶段受保护，扩展可挂载 |
| `compiler/stages/*.ts` | compile 各阶段实现 |
| `runtime/motionRuntimeScheduler.ts` | pending queue、音频等待、过期清理、启动调度 |
| `runtime/motionStart.ts` | payload 启动、compile 触发、playPlan 调用、启动结果写回 |
| `runtime/playbackClock.ts` | 定义 Timeline 时钟投影并解析剩余可用时长，供启动阶段和 performance curve 求解使用 |
| `runtime/contracts.ts` | runtime 调度、启动、状态控制、依赖端口类型 |
| `timing.ts` | 时机决策（提示/音频同步/默认） |
| `settings.ts` | 强度倍率设置 |
| `contracts.ts` | 入站动作 payload 的边界类型 |
| `constants.ts` | 默认时长、等待窗口、参数轴常量 |

**输入**：正式 V4 动作意图或本地 `CompiledSemanticMotion` 预览、当前模型摘要、当前语义轴档案、动作引擎设置、音频播放上下文

**输出**：编译后的参数计划、播放器执行计划、动作播放记录

**主轴设计口径**：
- 动作主轴负责姿态和动作骨架，包括头部偏转、身体扭转/摇晃、眼睛开闭等。
- 表情辅轴负责面部表情、态度和细节微调，包括嘴角笑意、眉毛、视线偏移等。
- 嘴巴开闭是重要动作轴，但说话场景下主要由 runtime/lip sync 管理。
- 身体扭转和摇晃参与表达情绪强弱，不应只作为视觉附带效果看待。
- Motion 文件用于校准主轴/辅轴选择，Expression 文件不作为主轴来源。

**边界要求**：
- 不直接处理 WebSocket
- 不直接决定文本和音频何时释放
- 可读取必要的会话/音频时机信息，但不应成为播放管线的事实来源
- compile 侧 `SpeechPoseStage` 生成确定性的 `speech_gesture_track`；逐帧插值、speech energy 和物理表现由 Live2D WebSDK 承接

### 4.9 虚拟形象运行时

**位置**：`frontend/src/components/DesktopPetCanvas.vue`、`frontend/src/live2d-renderer/`、`frontend/src/live2d/WebSDK/`

**职责**：
- 初始化 Live2D 引擎、加载模型和纹理
- 渲染透明桌宠画布
- 执行动作参数计划
- 支持平滑交接
- 处理待机/空闲动作
- 由 SDK 侧 `ParameterPresentationNode` 处理 direct plan 的进入/退出轨迹、速度和加速度；Parameter Mixer 是跨来源组合和最终运行时范围裁剪的唯一所有者

**边界要求**：
- 不理解后端协议
- 不理解播放会话
- 只接受模型加载、参数计划执行和运行时表现层控制请求

### 4.10 创作工具

**位置**：`frontend/src/views/SettingsWindowView.vue`、`frontend/src/views/HistoryWindowView.vue`、`frontend/src/views/ActionLabWindowView.vue`、`frontend/src/views/ProfileEditorWindowView.vue`、`frontend/src/components/MotionTuningPanel.vue`、`frontend/src/components/SemanticAxisProfileEditor.vue`、`frontend/src/components/BaseActionPreviewPanel.vue`

**交互模式**：

```text
工具窗口
  → View 读取 desktop-bridge 快照
    → 组件通过 props 展示和编辑
      → 组件通过 events 表达操作
        → View 转成桌面命令
          → 主控制器
            → 对应运行时模块
              → 快照回传工具窗口
```

**边界要求**：
- 工具窗口不直接连接适配器
- 工具窗口不直接写主运行时状态
- 窗口 View 可以访问 `useDesktopBridge()`
- 组件不直接访问 `desktop-bridge`、`adapter-connection` 或 WebSocket
- 组件通过 props 接收快照投影，通过 emits 输出保存、删除、预览、同步等操作

### 4.11 音频输入输出（横切层）

**位置**：`frontend/src/adapter-connection/runtime/audioRuntime.ts`、`frontend/src/playback-timeline/audioSink.ts`、`frontend/src/playback-timeline/audioSegmentPlaybackSink.ts`、`frontend/src/adapter-connection/runtime/microphoneRuntime.ts`、`frontend/src/adapter-connection/runtime/microphoneCapture.ts`、`frontend/src/adapter-connection/runtime/microphoneDevices.ts`

**输出音频方向**：

```text
原子 segment 提交 → PlaybackTimeline 释放音频 → BrowserAudioSink 播放
  → Timeline 记录 duration / started / terminal → SessionStore 稳定投影 → 完成协调器
```

输出音频 URL 指向 Adapter HTTP 静态资源，通常为 `/cache/audio/*.wav`。前端会按当前连接重写 host 后播放和拉取 lip sync 数据；如果 TTS 文件存在但前端无声，应把 Adapter 静态资源服务可达性作为第一排查项之一。

**输入麦克风方向**：

```text
麦克风采集 → 分配活跃麦克风输入段标识
  → 发送原始音频数据 → 发送麦克风音频结束
```

**关键语义**：
- 一段采集期内的所有原始音频块与结束信号共用同一个新的 `turn_id`
- 不再借用当前助手播放轮次的任何额外编排 ID
- 如果发送缓冲积压，前端标记为损坏，结束信号携带丢弃标记
- 后端收到丢弃标记后直接清空音频缓冲，不做残缺转写

### 4.12 协议契约（横切层）

**位置**：`frontend/src/types/protocol.ts`、`frontend/src/types/desktop.ts`、`frontend/src/types/semantic-axis-profile.ts`、`frontend/src/adapter-connection/core/protocolMessageTypes.ts`、`frontend/src/adapter-connection/inbound/inboundPayloads.ts`

**包括**：适配器 V2 信封、消息类型、`turn_id + message_id` 标识契约、动作模式定义、模型同步载荷、桌面运行时命令/快照、档案编辑命令/快照、语义轴档案

## 5. 后端架构

后端核心位于 `astrbot_plugin_ag99live_adapter/`，是前端桌宠运行时的协作编排后端。

### 5.1 目录结构

| 路径 | 职责 |
|---|---|
| `runtime/` | 轮次状态机、主运行时编排、协议收口 |
| `protocol/` | 协议消息定义、解析、构建 |
| `transport/` | WebSocket 服务器和静态资源路由 |
| `services/` | 上层服务组合（语音、媒体、历史、前端系统） |
| `motion/` | 动作契约归一化、能力校验、资源候选、性能曲线与输出清理 |
| `middleware/` | 中间处理层（交互动作贡献者） |
| `prompts/` | 提示词和模型交互文本资源 |
| `live2d/` | Live2D 相关（语义轴档案、扫描器、运行时缓存） |
| `assets/` | 静态资源 |
| `tests/` | 测试 |

### 5.2 插件数据边界

AstrBot 插件数据目录按失败域拆分，不能再把持久数据放进可丢弃缓存或公开整个缓存根目录：

```text
plugin_data/astrbot_plugin_ag99live_adapter/
├─ cache/                    # 可重建运行缓存
├─ public_cache/
│  ├─ audio/                 # 仅通过 /cache/audio 暴露
│  └─ images/                # 仅通过 /cache/images 暴露
└─ state/
   ├─ motion_lab.sqlite3     # 持久观察数据
   └─ motion_tuning_samples.json
```

`live2d_runtime_cache.v3` 只保存可重建的 Live2D 扫描缓存。Motion Lab 和 Motion Tuning 的加载错误分别阻断各自写入，不得由运行缓存错误联动覆盖，也不得通过静态资源路由公开。

### 5.3 核心模块

**`runtime/turn_coordinator.py`** — 后端协议和轮次编排中枢：
- 接收入站协议、建立轮次
- 按 `turn_id + message_id` 聚合并发送原子输出段
- 区分“明确无动作”和“安排了动作但载荷缺失/非法”，后者发送 `motion.failed`
- 在音频轮次下等待前端播放完成
- 收到后发送轮次完成
- 关闭 turn 输出队列时发送 `control.synth_finished`；该信号不是单条音频生成完成信号
- WebSocket 断开时先停止在飞 AstrBot event，再清理连接级 Turn、Segment、曲线和 ID 状态

**`runtime/session_state.py`** — 后端单连接轮次状态机：
- 管理当前协议 `turn_id` 与轮次阶段
- 区分阶段：空闲 → 思考中 → 合成中 → 播放中
- 在有音频时等待前端播放完成

**`protocol/`** — 协议层：
- `constants.py` — 协议消息类型常量
- `parser.py` — 入站消息解析
- `builder.py` — 出站消息构建
- `models.py` — 协议数据模型

**`services/`** — 服务层：
- `speech_service.py` — 语音输入处理（语音转文字入口）
- `media_service.py` — 音频文件缓存；通过 transport 静态资源路由暴露给前端播放
- `history_service.py` — 历史增删改查
- `frontend_system_service.py` — 前端系统消息处理
- `message_factory.py` — 消息工厂

**`motion/`** — 动作处理：
- `payload_dispatch.py` — 按 schema 校验 payload 并解析对应 `engine.*` message type
- `motion_intent.py` — V4 intent 归一化、profile 解析和基础校验
- `resource_catalog.py` — typed expression/motion resource 候选与校验
- `inline_motion.py` — Persona Effect 注入能力缺失时的官方 `<@anim>` 兼容入口
- `output_sanitizer.py` — 输出文本清理

### 5.4 后端职责总结

后端承担：
- 维护轮次生命周期
- 接收前端输入
- 广播输出/控制/引擎消息
- 同步模型能力和档案
- 提供动作调参样本存储与读取
- 语音输入处理
- 音频文件缓存与网络服务

## 6. 关键主流程

### 6.1 文本对话主流程

```text
辅助窗口输入文本
  → 发送文本命令
    → 主控制器
      → 适配器发送文本
        → 文本输入到达后端
          → 轮次开始
            → 输出文本/音频/动作
              → Adapter 聚合 output.segment.v3
                → SessionStore 原子提交槽位事实
                  → 播放编排器释放
                    → 文本显示/音频播放/动作引擎
                      → 合成完成关闭片段队列
                        → 所有片段槽位稳定且 required Timeline 关闭
                          → 播放完成
                            → 轮次完成
                              → 会话完成
```

### 6.2 模型同步主流程

```text
后端扫描模型
  → 检查语义轴档案
    → 模型源或默认生成设计不匹配时重新生成并原子替换旧档案
      → 系统模型同步
    → 适配器连接
      → 模型同步
        → 选中模型/选中语义轴档案
          → 动作引擎/创作工具/运行时快照
```

### 6.3 动作测试主流程

```text
动作实验室/档案编辑器
  → 预览已保存的 CompiledSemanticMotion
    → 主控制器
      → 第二阶段参数编译
        → 动作引擎本地播放
          → 适配器发送播放记录到后端
```

语义轴档案无法通过当前 schema 校验时明确报错，不以重新生成掩盖损坏；结构兼容的用户手工档案继续保留。

## 7. 推荐依赖方向

维护时坚持以下依赖方向：

```text
创作工具 → 多窗口桥接 → 主控制器

主控制器 → 适配器协议层
主控制器 → 播放管线
主控制器 → 模型能力管理
主控制器 → 动作引擎
主控制器 → 虚拟形象运行时

适配器协议层 → 播放管线
播放管线 → 动作引擎
动作引擎 → 虚拟形象运行时
模型能力管理 → 动作引擎
模型能力管理 → 创作工具
播放管线 → 适配器协议层（仅播放完成信号，通过窄接口）
```

**不建议出现**：
- 虚拟形象运行时直接访问适配器协议层
- 创作工具直接修改播放会话
- 动作引擎直接发送 WebSocket 消息
- 适配器协议层内部编译动作计划
- 桌面宿主理解业务协议

## 8. 当前判断与维护规则

### 8.1 关键判断

1. 前端是**桌面运行时系统**，不是普通页面应用
2. `usePetDesktopRuntime.ts` 是前端主装配根；`createConversationPlaybackRuntime.ts` 只负责对话播放实例装配
3. `adapter-connection/` 是适配器核心实现区，包含核心、入站、出站、运行时和特性模块
4. 适配器层通过 facade 对外暴露连接与协议能力
5. `model-engine/` 是动作引擎独立区域，扩展能力通过 compiler stage registry 挂载
6. `action-lab/` 与相关组件是动作库/调参工具区，组件层保持 props + events 边界
7. `astrbot_plugin_ag99live_adapter/` 是后端主业务区，不只是简单桥接壳
8. 动作路线分为两层：ModelEngine 编译语义参数与 `speech_gesture_track`；Live2D WebSDK 的 ParameterPresentation 只执行 direct plan 的轨迹和动力学，Parameter Mixer 再以 Cubism Motion、EyeBlink、Expression、drag、breath 形成的 base snapshot 组合 direct plan 与口型、一次最终裁剪后交给 Cubism Physics。

### 8.2 维护规则

1. 只写"当前真实结构"，不要把未来设想伪装成现状
2. 每当新增一级模块或一级职责，就补到本文
3. 每当一个模块职责明显变化，就更新"负责什么 / 不负责什么"
4. 每当重构完成一个大边界，就同步删掉过期描述
5. 如果某个文档更偏时序或实现细节，就写到其他架构文档，不要把本文写成大杂烩
