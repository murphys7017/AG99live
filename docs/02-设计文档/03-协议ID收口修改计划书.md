# 协议 ID 收口修改计划书

> 状态：待实施设计文档。本文定义前后端协议 ID 收口目标、迁移阶段、影响范围、风险与验证要求。

更新时间：2026-05-17

## 1. 背景

当前前后端协议同时存在以下身份字段：

- `session_id`
- `turn_id`
- `orchestration_id`
- `message_id`

现状问题：

- `session_id` 并不是前后端交互链路中的真实业务身份。
- `turn_id` 和 `orchestration_id` 在当前链路中分担了轮次和输入分段职责，增加了状态模型复杂度。
- 前端播放聚合、音频分段、动作过滤需要同时理解两套轮次上下文。
- 后端对外协议身份和 AstrBot 内部 turn 身份没有明确分层。

本次收口的前提是：

- 用户一条输入，会触发 AstrBot 产生一条或多条输出。
- 前后端协议需要一个轮次级主 ID，用来贯穿整轮交互。
- 这个轮次级主 ID 必须在发送文本或语音流之前就存在。
- 后端收到 AstrBot 返回的内部 turn 后，只在内部维护映射，不把 AstrBot turn 直接暴露给前端。

## 2. 目标结论

前后端协议收口为两个主身份：

- `turn_id`
- `message_id`

其中：

- `turn_id` 是前后端唯一轮次主 ID。
- `message_id` 是 assistant 输出片段 ID。

本次收口后的协议原则：

- 前端在输入发起前主动创建 `turn_id`。
- 文本输入、语音流输入、打断、播放完成、输出回传、动作回传全部使用同一个 `turn_id`。
- 一轮内允许一条或多条输出片段，每个片段继续使用自己的 `message_id`。
- 协议层移除 `session_id`。
- 协议层移除 `orchestration_id`。

后端内部原则：

- AstrBot 内部可继续有自己的 turn 身份。
- Adapter 后端维护 `frontend_turn_id <-> astrbot_turn_id` 映射。
- 前端永远只理解协议层的 `turn_id`。

## 3. 非目标

本计划不包含以下目标：

- 不重写 AstrBot 自身内部会话模型。
- 不在本轮收口中重做历史记录的业务语义。
- 不顺带改造与协议 ID 无关的 ModelEngine 功能。
- 不把多个用户输入合并为共享 turn。

## 4. 新身份模型

### 4.1 协议层

协议层只保留：

- `turn_id`
- `message_id`

信封目标形态：

```json
{
  "type": "<消息类型>",
  "version": "v2",
  "message_id": "<非空字符串>",
  "turn_id": "<非空字符串 | 某些非 segment 控制消息可为 null>",
  "source": "adapter" | "frontend" | "astrbot" | "engine",
  "timestamp": "<ISO 8601 时间戳>",
  "payload": { ... }
}
```

规则：

- 所有与某轮输入相关的 `input.*` 消息都必须带 `turn_id`。
- 所有属于该轮的 `output.*` / `control.*` / `engine.*` 消息都必须回带相同 `turn_id`。
- `message_id` 只用于 segment 级输出和动作片段绑定。

### 4.2 前端层

前端职责：

- 在用户开始一次输入前创建 `turn_id`。
- 文本发送时直接携带该 `turn_id`。
- 语音流开始前创建或复用该 `turn_id`，后续 chunk/end 共享同一个 `turn_id`。
- 前端播放 session、动作过滤、播放完成回执全部只按 `turn_id` 工作。

### 4.3 后端层

后端职责：

- 接收前端 `turn_id` 并将其视为外部协议主键。
- 使用该 `turn_id` 进行音频缓冲分段、turn 生命周期广播、输出回传、打断、播放完成归并。
- 在内部维护协议 `turn_id` 与 AstrBot 内部 turn 身份的映射。

后端不再对前端暴露：

- `session_id`
- `orchestration_id`
- AstrBot 原生 turn 身份

## 5. 迁移原则

### 5.1 单轨优先

所有新逻辑优先向单轨 `turn_id` 收口，不再新增任何依赖 `orchestration_id` 的路径。

### 5.2 先兼容后清理

迁移时允许短期兼容旧字段，但兼容层只用于过渡，不作为长期设计。

### 5.3 不隐藏映射

AstrBot 内部 turn 映射必须显式维护，不能靠“当前 active turn”这类隐式状态代替。

### 5.4 不扩大范围

本次改动只处理协议 ID 收口，不借机重写无关模块。

## 6. 分阶段实施计划

### Phase 0：文档冻结与迁移基线

目标：

- 冻结新的协议 ID 设计结论。
- 明确当前代码中所有 `session_id` / `orchestration_id` / `turn_id` 的职责和落点。

产出：

- 本文档
- 后续协议契约更新草案

验收：

- 团队对“前端只认 `turn_id`，后端内部维护 AstrBot turn 映射”的设计结论达成一致。

### Phase 1：协议兼容层引入

目标：

- 先让前后端都支持“单轨 `turn_id`”运行。
- 暂时兼容旧的 `orchestration_id` / `session_id` 输入输出，避免一次性切断。

建议改动：

- 后端 parser 接受旧字段，但内部统一归并到 `turn_id`。
- 前端 parser 若收到旧 `orchestration_id`，只作为兼容读取，不再进入新状态主路径。
- 对旧字段使用加日志告警，便于确认残留路径。

验收：

- 在兼容模式下，新旧消息都能跑通。

### Phase 2：前端输入侧收口

目标：

- 让当前前端“预生成 `orchestration_id`”的逻辑正式升级为“预生成 `turn_id`”。

建议改动：

- 文本输入发送前创建 `turn_id`。
- 麦克风开始采集前创建 `turn_id`。
- `input.raw_audio_data` / `input.mic_audio_end` 改为仅携带 `turn_id`。
- 删除前端输入阶段对 `currentOrchestrationId` 的依赖。

验收：

- 文本输入和语音输入都能在无 `orchestration_id` 的前提下正常贯穿。

### Phase 3：后端运行时收口

目标：

- 后端 turn 生命周期、STT ingress、输出广播统一以协议 `turn_id` 为外部身份。

建议改动：

- `SpeechIngressService` 的音频缓冲分桶键从 `orchestration_id` 改为 `turn_id`。
- `SessionState` 删除 `current_orchestration_id`。
- `TurnCoordinator` 的控制消息与输出消息不再构造 `orchestration_id`。
- 新增协议 `turn_id <-> astrbot_turn_id` 映射容器。

验收：

- STT、reply、interrupt、turn_finished 都能只靠 `turn_id` 正确关联。

### Phase 4：前端播放与动作链路收口

目标：

- 前端运行时、session store、动作过滤统一收成单 `turn_id` 语义。

建议改动：

- `useAdapterConnection` 删除 `sessionId`、`currentOrchestrationId`。
- `TurnPlaybackSessionStore` 从 `orchestration + turn` 双键模型改为单 `turn_id`。
- `inboundMotion` 过期过滤改为仅基于 `turn_id` 与 active audio segment 做判断。
- 音频播放状态、pending queues、playback completion coordinator 改为只按 `turn_id` 路由。

验收：

- 一轮多 segment 文本/音频/动作同步释放逻辑不回归。

### Phase 5：协议清理与文档收尾

目标：

- 删除兼容逻辑。
- 删除旧字段。
- 同步文档、测试、调试输出。

建议改动：

- 协议模型删除 `session_id`、`orchestration_id`。
- 清理旧日志字段与状态命名。
- 更新所有当前文档与测试夹具。

验收：

- 仓库内当前路径不再依赖协议 `session_id` 和 `orchestration_id`。

## 8. 主要风险

### 8.1 语音输入空轮次清理

前端提前创建 `turn_id` 后，如果整段录音最终为空、被丢弃、被 VAD 中断，必须明确：

- 是否结束该 `turn_id`
- 是否允许该 `turn_id` 后续继续复用

建议：

- 一次输入创建一个 `turn_id`
- 该次输入结束后，无论是否转写成功，都结束该 `turn_id`

### 8.2 播放聚合回归

当前播放 session store 支持 `orch -> turn` 提升。改单键后，segment 聚合会更简单，但需要重新验证：

- 文本先到、音频后到
- 动作晚到
- synth_finished 先到

### 8.3 动作 stale 判定回归

当前动作 stale 过滤同时参考 `turn_id` 和 `orchestration_id`。改单键后，必须重新验证：

- 当前 active turn 内晚到动作是否仍被接受
- 已结束 turn 的动作是否会被误放行

### 8.4 AstrBot turn 映射遗漏

若后端没有正确维护 `frontend_turn_id <-> astrbot_turn_id`，则会影响：

- interrupt
- playback_finished
- turn completion
- 多轮串扰防护

## 9. 验证策略

### 9.1 必跑主路径

- 文本输入 -> 单条文本输出
- 文本输入 -> 文本 + 音频 + 动作输出
- 语音输入 -> 转写 -> reply 输出
- 语音输入丢包 -> dropped 路径
- interrupt 路径
- playback_finished -> turn_finished 路径

### 9.2 关键边界

- 一轮多 segment 输出
- 文本先到音频后到
- 动作 payload 晚到
- synth_finished 无音频
- 空转写 / 空录音 / dropped 输入

### 9.3 验收标准

- 仓库当前主路径不再依赖协议 `session_id`
- 仓库当前主路径不再依赖协议 `orchestration_id`
- 前端只以 `turn_id` 为轮次主身份
- 后端对 AstrBot turn 的依赖被封装在内部映射中

## 10. 建议执行顺序

建议按以下顺序推进：

1. 更新协议设计文档与契约文档
2. 增加兼容层与日志
3. 改前端输入侧预创建逻辑
4. 改后端 STT ingress 与 turn runtime
5. 改前端播放与动作链路
6. 清理旧字段与兼容分支
7. 更新测试与调试日志

## 11. 当前结论

该方案可行，但属于协议边界级重构。

它的核心收益是：

- 把前后端轮次身份收敛为单一 `turn_id`
- 消除 `session_id` 与 `orchestration_id` 的外部协议混淆
- 让 AstrBot 内部 turn 与前端协议 turn 明确分层

后续实施必须按阶段推进，并且优先做好兼容层与验证。
