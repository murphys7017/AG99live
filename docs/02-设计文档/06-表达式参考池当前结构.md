# 表达式参考池当前结构

本文记录当前动作 LLM 表达式参考池的数据来源、协议入口和维护边界。

## 1. 目标

动作 LLM 的参考由两层组成：

1. 用户确认过的动作调参样本：`motion_tuning_samples`
2. 当前模型扫描出的表达式参考：`expression_example_library.examples`

用户样本优先，模型原生表达式用于补齐，默认示例作为兜底。

## 2. 数据流

后端扫描 → .exp3.json → scan.py → constraints.expressions
→ `_build_expression_example_library()`（原始值→0-100语义轴值）
→ `model_info.models[*].expression_example_library.examples`
→ `RuntimeState.model_info`
→ `system.model_sync`
→ 前端 `selectedModel.expression_example_library.examples`
→ `buildModelProjectionSnapshot()`
→ 调参面板展示

当前事实源：

- 后端 `RuntimeState.model_info.models[*].expression_example_library.examples` 是表达式参考的当前有效状态。
- prompt 选择 model native few-shot 时读取同一个 `RuntimeState.model_info`。
- 前端调参面板只展示后端同步后的模型投影，不单独重算表达式参考。
- Action Lab 左侧样本栏用 tab 区分历史动作和已保存参考。用户保存样本、扫描表情和默认兜底示例都属于已保存参考，选中后复用右侧同一套参数编辑器继续优化；表达式启用状态仍通过覆盖项保存。

## 3. 协议消息

| 消息类型 | 方向 | 用途 |
|---|---|---|
| `system.expression_example_override_save` | 前端→后端 | 保存覆盖（model_name、example_id、enabled、feedback、tags） |
| `system.expression_example_override_delete` | 前端→后端 | 删除覆盖（model_name、example_id），恢复模型默认状态 |
| `system.expression_example_overrides_state` | 后端→前端 | 推送覆盖状态 |

覆盖项作用域：

- 覆盖项必须带 `model_name`。
- 同名表达式只在对应模型内生效，避免不同模型的 `happy`、`angry` 等表达式互相串扰。
- 用户关闭表达式时保存 override；用户重新开启时删除 override，表示恢复默认。

## 4. 默认值策略

`EXPRESSION_KEYWORD_REFERENCES`（7 组关键词参考）和 `DEFAULT_SELECTOR_FEW_SHOT_EXAMPLES`（5 个示例）保留为 prompt 的兜底参考。

关键词参考、few-shot 示例选择、语义轴说明和最终 prompt 拼装分开维护：

- `prompts/expression_references.py` 维护表情关键词组、心情态度、实际动作表现和参考轴值。
- `prompts/motion_selector_examples.py` 维护默认示例、模型原生表达式示例转换和 few-shot 补齐顺序。
- `prompts/semantic_axis_prompt.py` 维护可控语义轴筛选与轴说明文本格式。
- `prompts/motion_selector.py` 负责动作 selector prompt 的入口组装。

few-shot 来源顺序保持：

1. 用户确认过的 `motion_tuning_samples`
2. 当前模型启用状态下的 `expression_example_library.examples`
3. 默认示例

禁用的扫描表达式不进入 model native few-shot 候选。

## 6. 边界规则

- 前端不独立重算表达式参考池。
- 后端 `RuntimeState.model_info` 是当前有效参考事实源。
- 覆盖项只改变对应模型内的表达式参考启用状态和说明。
- 禁用项不进入 model native few-shot 候选。
- 用户动作调参样本优先级高于模型原生表达式参考。

## 7. 表情能力与语义轴池设计记录

本节记录下一阶段设计判断，尚未代表当前代码已经完全落地。

### 7.1 核心判断

`Expressions/*.exp3.json` 不应该直接等同于动作 few-shot 示例。

表情文件里的参数经常是模型原生表情开关或局部效果，例如：

- `ExpHappy`
- `ExpQuestion`
- `ExpFaceBlush`
- `ExpDarkcircle`
- `ExpEyeHighlight`

这些参数说明模型具备某种表情能力，但不一定能直接反推出完整的语义动作，例如“开心 = 抬头 + 微笑 + 眼神明亮”。

因此表情文件的主要用途应调整为：

1. 发现模型具备哪些表情能力。
2. 辅助生成或修正语义轴池。
3. 作为关键词参考的能力依据。
4. 不直接作为完整 few-shot 示例来源。

### 7.2 第一阶段范围

第一阶段只使用 `Expressions/*.exp3.json`，暂不引入 `Motions/*.motion3.json`。

原因：

- 表情参数更集中，复杂度低。
- 更适合先解决表情语义和 LLM 参考稳定性。
- 不把身体动作、时序、动画片段提前混入动作引擎设计。

动画资源后续再进入姿态、连贯性或 SpeechPose 相关模块。

### 7.3 目标语义轴规模

目标不是只保留少量 `happy / confused` 类别，而是形成约 10-20 个可理解、可编辑、可绑定的语义轴。

候选轴池按表达部位分组：

| 分组 | 候选语义轴 |
|---|---|
| 头部 | `head_yaw`、`head_pitch`、`head_roll` |
| 视线 | `gaze_x`、`gaze_y` |
| 眼睛 | `eye_open_left`、`eye_open_right`、`eye_smile`、`eye_wide` |
| 嘴部 | `mouth_open`、`mouth_smile`、`mouth_press`、`mouth_shape` |
| 眉毛 | `brow_raise`、`brow_frown`、`brow_bias` |
| 脸部效果 | `face_blush`、`face_shadow`、`darkcircle`、`tear`、`question_mark` |

这些名字是动作引擎理解的语义轴，不要求与 Live2D 原始参数名一致。

### 7.4 轴角色

语义轴池建议分为四类：

| 角色 | 用途 |
|---|---|
| `primary` | LLM 经常直接控制的核心动作轴 |
| `hint` | LLM 可以参考或由引擎自动补充的辅助轴 |
| `native_expression` | 模型原生表情开关或局部效果，不作为主轴直接暴露 |
| `debug` | 扫描到但暂不进入动作生成链路的参数 |

示例：

- `mouth_smile`、`head_pitch`、`gaze_y` 适合做 `primary`。
- `face_blush`、`darkcircle`、`question_mark` 更适合做 `hint` 或 `native_expression`。
- 道具、衣服、手臂开关等参数默认不进入 LLM 主控轴。

### 7.5 参考生成原则

后续 few-shot 和 prompt 参考应由“关键词语义参考 + 当前模型能力”共同生成。

示例：

```text
[害羞、不好意思、尴尬、被夸]
→ 低头、视线躲闪、弱笑
→ 如果模型支持脸红能力，则补充 face_blush 或原生 ExpFaceBlush
```

也就是说：

- 关键词参考负责表达语义。
- 表情扫描负责发现模型能力。
- 语义轴池负责提供统一控制接口。
- 动作引擎负责把主轴、辅轴和原生表情能力组合成最终动作。

### 7.6 暂定数据方向

下一阶段可以把扫描表情整理成“表达式能力表”，而不是直接整理成 few-shot 示例。

能力表可以包含：

- `capability_id`
- `parameter_id`
- `source_expression`
- `kind`
- `suggested_role`
- `keywords`
- `visual_description`
- `suggested_axis_id`

例如：

```json
{
  "capability_id": "face_blush",
  "parameter_id": "ExpFaceBlush",
  "source_expression": "Blush",
  "kind": "expression_switch",
  "suggested_role": "hint",
  "keywords": ["害羞", "脸红", "不好意思", "被夸"],
  "visual_description": "脸红",
  "suggested_axis_id": "face_blush"
}
```

这份能力表后续可以用于：

- 辅助生成默认 `semantic_axis_profile`。
- 在 Action Lab 中说明模型支持哪些表情能力。
- 给关键词参考池补充模型原生能力。
- 为后续 `ExpressionStage` 提供挂载依据。
