# AG99 与 AG99live 产品定位与项目职责讨论稿

> **状态：方向已确认，本文记录已确认的定位与命名结论。** 本文用于固化产品和项目定位，再进入功能优化；不代表仓库拆分、合并或运行方式已经决定。

## 1. 当前要解决的问题

AG99live 已经完成了相当一部分 Live2D 桌宠、播放编排和桌面运行能力；AG99 也不再只有传统的服务端消息收发链路，已经包含跨轮次 Personal Runtime、主动观察/表达、记忆及工具能力。若仍把 AG99 简单称为“服务器”、把 AG99live 仅称为“桌宠前端”，就难以表达两者正在形成的产品关系。

定位不清会让以下问题混在一起：

- 新能力应该由 AG99 提供，还是由 AG99live 桌面端提供；
- 已有 AG99 能力是需要优化和接入，还是要在 AG99live 重做；
- AG99live 是未来产品名、独立项目名，还是 AG99 身体运行时的一种实现；
- 桌面端是本地 AG99 的界面，还是也可以连接远端 AG99。

这些是产品和职责边界问题，不应靠继续增加功能来掩盖。

## 2. 已确认的产品定位

### 确认表述

> **AG99 的产品重心转向桌面端，是用户使用智能体的主应用，组织对话、人格、记忆、主动行为、工具及统一的配置和管理体验。AG99live 是 AG99 的身体，负责感知输入、本地实时反应、Live2D 角色呈现、音频播放和设备连接。AG99 内部继续保留智能体运行时与多平台能力；AG99live 通过 Adapter 协议与其协作。AstrBot 是 AG99 的上游来源，并作为兼容命名继续保留。**

这里确认的是产品方向：桌面主应用体验需要逐步形成。桌面端只提供统一入口并连接已经运行的 AG99 服务和 AG99live 身体，不负责启动、托管、打包或替代这些服务；这不预先决定仓库合并或远端部署方案。

### 这一定义想表达什么

- **AG99 以桌面端产品为重心**。智能体运行时是其内部能力基础，用户入口、角色管理、会话、记忆、工具和整体体验由 AG99 组织。
- **AG99live 是身体运行时**。它承担角色的感知、实时反应和表达；当前身体形态主要落在桌面端。
- **身体不等于渲染器**。AG99live 还负责输入感知、实时状态、低延迟本地反应、窗口、音频播放和设备生命周期。
- **AG99live 是仓库名和产品名**。它已经同时包含 Adapter 插件、Electron 桌面端、Native 渲染实现和录制工具，不需要另一个并行的“桌面产品名”。
- **AstrBot 不作为职责方出现**。它只表示 AG99 的上游来源，以及 `astrbot` 包、`astrbot` CLI、`astrbot_plugin_` 插件前缀这些有意保留的兼容命名。

## 3. 术语约定

| 术语 | 含义 | 说明 |
| --- | --- | --- |
| **AG99** | 以桌面端为重心的智能体主应用 | 内含智能体运行时及多平台能力；名称不改 |
| **AG99live** | 身体运行时 | 本仓库；当前主要实现桌面身体，名称不改 |
| **AG99live Adapter** | 装进 AG99 的插件 | 协议与业务能力层，目录 `astrbot_plugin_ag99live_adapter/` |
| **AG99live Desktop** | 桌面客户端 | AG99live 仓库内 Electron 与 Native 运行时的统称，用于与 Adapter 区分 |
| **AstrBot** | 上游来源与兼容命名 | 不承担职责，不再用作 owner |

“AG99 Desktop”不作为独立名称使用：桌面侧对外名称就是 AG99live，只有在需要区分 Adapter 与桌面客户端时才写作 AG99live Desktop。

## 4. 能力所有权

| 能力 | owner | 协作方式 |
| --- | --- | --- |
| 普通对话、会话历史、人格、记忆 | AG99 | 桌面端提交输入并呈现结果，不建立平行历史或记忆事实源 |
| 主动观察、主动表达及语义策略 | AG99 | 目标是由 AG99live 提供经过授权的低频桌面事实；当前该 scene/desktop-fact 链路尚未接通。AG99 决定是否形成语义表达；桌面端负责表现、即时可说性和打断恢复 |
| Provider、工具和 AG99 插件生命周期 | AG99 | AG99live 通过宿主公开接口调用或接收结果，不复制管理器 |
| 光标、点击、触摸、窗口与设备输入 | AG99live | 高频信号先由本地运行时过滤；只有策略需要时才发送必要事实给 AG99 |
| Live2D、模型 Profile、视线、动作、表情和帧级状态 | AG99live | 接收表达意图并映射为角色表演；报告模型能力和执行状态 |
| TTS 生成与音频播放 | 生成由 AG99/配置的服务提供；桌面播放由 AG99live 持有 | 通过既有输出段和播放终态协议连接；生成与播放分别报告状态 |
| Turn/Segment 协议、跨进程身份与错误语义 | Adapter / 双方协议边界 | 唯一传递和校验边界，不另建第二条消息或播放时钟 |
| 主应用入口、统一配置与管理体验 | AG99（目标职责） | AG99live 提供身体能力设置、状态和诊断；现有独立窗口的迁移或整合需另行设计，避免复制设置存储 |

边界判断以“谁拥有事实、谁做决策、谁执行副作用、谁负责结束状态”为准，而不是只看功能名字。

### 当前链路与目标设计的差别

当前协议 manifest 的 10 个 schema 和 Adapter 入站消息都没有 scene/desktop-observation 类型；AG99live 也没有注册 Runtime Observation sensor 或提交桌面场景事实。桌面到 Adapter 的实际协议不止播放回执等四类：还包括文本输入（可带本轮桌面截图）、麦克风音频流、打断、历史与设置操作、Profile/动作调校和 Motion Lab 数据；但这些消息都不能表达“用户回来了”“点击了桌宠”“当前不适合说话”等场景语义。

AG99 的 `RuntimeObservationSensorHandle.submit()` 是插件注册后向现有 Inbox 提交结构化事实的 push API，不会自动采集桌面状态。`personal_action` 和 `proactive_output` 是禁止作为插件 observation kind 提交的保留值。要建立场景链路，仍需桌面事件、协议输入、Adapter 校验/权限以及 sensor handle 调用的完整连接。

AG99live 的 Bilibili 客户端位于桌面仓库：当前收到弹幕后按间隔合批，以文本输入提交给 AG99。当前代码事实应与“直播互动编排已由 AG99 提供”区分；是否把现有弹幕输入提升为核心卖点或扩展成更完整的直播表演，属于后续产品范围决策。

## 5. 部署与进程关系：连接已运行的服务

产品定位支持以下两种拓扑，不预先限定其中一种。AG99 桌面主应用在两种拓扑中都只承担统一入口和连接职责，不负责启动或托管服务：

```text
本机部署：
  AG99 Desktop Shell ↔ 本机 AG99
  AG99 Desktop Shell ↔ 本机 AG99live Body

远端部署：
  AG99 Desktop Shell ↔ 远端 AG99
  AG99 Desktop Shell ↔ 本机或远端 AG99live Body
```

当前 Adapter 固定绑定 `127.0.0.1`，只允许一个桌面 WebSocket 客户端，也没有远端连接认证；因此远端部署是未实现的产品目标，不是当前可用能力。第一阶段应先做已运行服务的连接、认证、状态展示和故障恢复；远端自动发现、跨设备编排和服务托管暂不纳入首批范围。

AG99 侧的桌面主应用与身体接入实施计划见 AG99 仓库 `docs/Yakumo/dev/desktop-application-and-body-integration-plan.md`。

## 6. 对现有功能路线的影响

定位确认后，功能工作归入三类：

1. **新增身体能力**：触摸互动、场景模式等桌面体验。
2. **优化智能体能力与身体配合**：AG99 已有主动对话和记忆，先审计根因并改进；AG99live 优化状态输入、可见反馈和 Live2D 表现衔接。
3. **重组已有身体能力**：角色状态模型、设置/状态入口、Profile 与表演配置、能力成熟度标记。

音乐与节目单暂不作为 AG99live 新增方向，沿用 AG99 已有能力。直播方面，现有 Bilibili 弹幕输入实际由 AG99live 桌面侧实现；当前不扩大直播互动编排范围，是否把该输入作为 AG99live 核心卖点仍待产品决策。详细分类见[功能扩展与体验改进汇总](10-功能扩展与体验改进汇总.md)。

在定位和 owner 未明确前，不应先做宽泛的功能扩张或大规模重构。已知且边界明确的局部体验修复仍可单独评估，但不得借机改变两项目的所有权关系。

## 7. 已确认的决策与仍待决定的问题

### 已确认

1. **名称与产品重心**：AG99 面向桌面端主应用，AG99live 定位为身体运行时；两者名称均不改动。
2. **项目层级**：AG99live 是桌面身体项目，包含 Adapter 插件、Electron 桌面端和 Native 实现，不拆分为“AG99 Desktop”独立项目。
3. **AstrBot 关系**：AstrBot 是 AG99 的上游来源，保留 `astrbot` 包/CLI/插件前缀兼容命名，不再作为职责方出现。
4. **代码标识**：`ag99.*` 协议 Schema 前缀与 `ag99::` C++ 命名空间保持不变。

### 仍待决定

1. **部署基线**：是否同时正式支持本机与远端 AG99；若是，哪一种先作为正式验收基线？
2. **仓库结构**：Adapter 插件与桌面端是否长期共仓库，还是在能力边界稳定后拆分。
3. **内部目录命名**：是否在需要时统一 `Desktop` 一词的用法（当前仅用于与 Adapter 区分）。
