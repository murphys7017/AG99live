# 已有能力可用性与拟人化审计

本文从源码盘点 AG99live 已实现的用户能力，重点判断它们是否容易发现、启用、理解，并能否让 Live2D 角色呈现连续而自然的存在感。它是静态源码审计，不等同于当前安装包的可用性或真实运行验收。

## 1. 判断口径

“源码里有”不等于“用户能顺利使用”。本审计把能力状态分为：

| 状态 | 含义 |
| --- | --- |
| 默认可用 | 无额外配置时会进入主要体验路径。 |
| 已实现需配置 | 代码已接通，但需启用、填写依赖或连接设备。 |
| 面向创作者/调试 | 主要服务于动作调校、Profile 制作、诊断或历史检查。 |
| 部分链路/反馈待核 | 存在实现，但源码审计发现状态反馈、错误可见性或启用持久化疑点。 |
| 需现场验收 | 依赖真实 AG99、Electron、模型、Provider 或外设；源码无法证明最终体验。 |

评分采用 0–3 分：0 表示缺失，1 表示入口或反馈弱，2 表示基本可用但仍需理解/配置，3 表示用户容易发现、启用并理解。拟人化价值衡量角色在非问答时刻是否有可感知、合时宜的反应，不代表“更频繁地说话”。

## 3. 核心发现

### 3.1 能力分布在多个入口，缺少一张“当前角色状态图”

配置分别落在 AG99 插件配置、AG99 Web 控制页、Electron 设置窗口、Motion Lab、Action Lab、Profile Editor 和 Native Runtime。设置页已经有连接诊断、历史、实验室和 Profile Editor 入口，但没有统一回答“角色现在能做什么、哪些已启用、缺什么依赖、最近哪里失败”。

### 3.2 多项能力需要用户主动发现并配置

源码默认值显示：麦克风自动启动、Performance Curve、Independent Motion、Spout、ESP32 和 Bilibili 输入默认关闭；Cursor gaze 默认开启。关闭默认对隐私、外设和额外模型调用是合理的，但首次使用需要解释“为什么没反应”和“如何启用”，而不是单纯把开关放在设置中。

### 3.3 拟人化基础部件已经存在，但体验没有围绕角色状态组织

待机动作、呼吸、眨眼、鼠标凝视、思考随动、情绪动作及音频口型已经覆盖局部行为。当前主要由输入、回复和播放事件驱动，尚未形成一致的可见状态：注意到用户、思考中、等待、说话、被打断、恢复待机、连接异常等。缺少状态联动时，即使每个子功能都在运行，用户仍可能觉得角色只是在“收到回复时动一下”。

### 3.4 能力失败和“未启用”需要区分并解释

用户至少需要知道以下区别：未启用、尚未配置、依赖缺失、正在连接、运行失败、暂时被场景抑制、正常待机。现有历史审计提到 ESP32 错误反馈、模型扫描失败无明确前端错误、部分 Provider 配置问题只在运行日志暴露等风险；这些条目应在实现前重新对照当前源码和真实运行，不能把旧审计结论直接当作现状。

## 4. 优先级与建议切片

### P0：角色状态与能力状态总览

先复用现有 snapshot、连接诊断和各能力状态，在桌面设置首页提供简洁的“角色与连接状态”区域。每项只呈现：状态、缺少的依赖、可执行的下一步。首批覆盖 Adapter 连接、模型、麦克风、待机/凝视、Bilibili、Spout、ESP32、TTS/播放和 Native/TS 运行时身份。

这不是新增插件管理器，也不是重写设置体系；先把已有的状态聚合呈现出来。状态字段不足时，只补能支撑真实判断的最小数据链路。

### P0：本地角色状态反馈

在引入主动说话或新模型调用之前，先让已有本地机制组成连续的状态体验：

```text
idle → noticing → thinking/waiting → speaking → idle
                      ↘ interrupted → idle
连接或模型异常 → 可见错误状态 → 恢复后回到可用状态
```

每个状态都应有明确触发与结束条件，并组合现有视线、动作、表情和 UI 状态。高频互动继续在本地驱动；不因鼠标移动、凝视或 Physics 帧触发大模型调用。模型缺少相关参数时，应给出“该模型不支持此表现”的可理解反馈，而不是误报运行成功。

### P1：首次使用引导和分层设置

把“基础体验”与“高级/实验能力”分开。基础设置说明待机、凝视、语音输入和桌面连接；设备输出说明 Spout/ESP32 的适用场景和测试方式；实验设置明确额外 Provider、延迟和实验性质。Motion Lab、Action Lab、Profile Editor 保留为创作者工具，不要求普通用户理解这些概念才能获得自然待机表现。

### P1：失败反馈与恢复闭环

逐条验证模型扫描、麦克风权限/设备、TTS、Provider、Spout、ESP32 和 WebSocket 断连的失败路径。面向用户显示具体原因、最近发生时间及可执行恢复操作；诊断细节仍可保留在日志。错误状态在恢复后自动清除或转为已恢复，避免只显示一个长期失败标记。

### P1：优化 AG99 现有主动对话

主动对话已由 AG99 提供，不应在 AG99live 重建一套 Companion Mode 调度器。应结合 AG99 检查触发与抑制是否可理解、输出是否合时且可打断，并改善它与 AG99live 场景状态、Live2D 注意/思考/说话表现和播放终态的衔接。记忆同样沿用 AG99 现有模块；先排查造成混乱的原因，不新增平行的关系记忆。

上述场景状态衔接是目标，当前没有桌面事实协议、AG99live sensor 注册或本地开口准入层。AG99 的 Wake Scheduler/Heartbeat 可复用来重评已提交材料，不能替代桌面检测和即时表现准入；设计边界见联合边界文档第 6 节。

直播互动编排和音乐节目单暂不纳入 AG99live 的扩展范围；当前新增能力建议聚焦触摸互动与场景模式。

## 5. 首个实现切片建议

建议下一轮实现范围限定为 **“待机与交互状态可感知 v0”**：

1. 盘点现有 idle、gaze、thinking sway、输入/播放状态的实际 owner 与信号，定义最小状态模型。
2. 将现有信号映射到 idle、attention、thinking/waiting、speaking、interrupted，并保证状态终止、切换和断连恢复。
3. 复用现有设置/快照展示当前状态及简短原因；不增加主动对话、不增加 Provider 调用。
4. 用一个实际 Live2D 模型验证状态切换、覆盖优先级和模型缺轴行为，再决定是否扩展到场景模式。

验收要点：角色在无对话时保持自然待机；输入后及时表现注意到用户或思考；语音播放时说话表现与口型链路不冲突；打断后回到稳定状态；断连或模型不支持时用户能看懂原因；全程不增加大模型调用。

## 6. 范围边界

- 本审计不主张把每个模块都做成运行时插件；AG99live 与 AG99 的边界继续以联合边界文档为准。
- 不建议默认开启麦克风、摄像头/屏幕观察、外设输出或额外 Provider 能力。
- 不把“角色更拟人”简化为随机动作或更频繁说话；合时、可解释、可打断更重要。
- 不把源码检查当成产品体验或外设验收；没有实时链路证据的结论保持为待验收。
