# 动作处理链路修复与轴关系图设计

> 文档状态：阶段一已完成；阶段二、阶段三的主运行链路已完成。完整逐边诊断和等级区间内确定性采样已经落地。当前剩余工作集中在真实端到端验收和后续工具能力；资源 additive/blend 和在线自学习属于可选增强，不阻塞当前主链路。
>
> 本文描述动作链路的修复顺序和下一阶段优化目标。当前已经成立的 `ag99live.motion` Persona Effect、`engine.motion_intent.v4`、统一播放 Timeline 和 ModelEngine compiler stage 仍以现有权威文档为准；`engine.motion_intent.v3` 只保留给官方 `<@anim>` 兼容入口和内部手动预览。

## 目标

动作链路先解决确定性、可追踪性和错误暴露问题，再优化模型输出表达方式。最终目标不是继续在各层添加修正，而是建立一条明确的动作值处理管线：

```text
主模型文本 + Persona Effect
  -> 严格校验
     -> 失败：Motion Feedback / 诊断 / 不播放
     -> 成功：动作值处理
  -> 轴值关系图计算与约束
  -> engine.parameter_plan.v2
  -> PlaybackTimeline
  -> Live2D WebSDK
```

校验失败路径和成功路径共享同一份轴关系图、profile 和诊断视图，但失败路径不能伪造数值、生成默认动作或进入播放。

## 1. 首先修复的问题

本节记录第一阶段已经完成的缺陷修复和边界收口。九级强度与资源分层的当前实现记录在第 3 节。

### 1.1 动作资源在前端边界丢失（已修复）

后端动作归一化会按类型校验并写入 `expression_resource_id` 或 `motion_resource_id`。前端 `parseSemanticMotionIntent()`、ModelEngine 编译结果和 `MotionTransformTrace` 都会保留类型与解析结果，资源意图不会在边界丢失。

涉及位置：

- `astrbot_plugin_ag99live_adapter/middleware/motion_payload.py`
- `frontend/src/model-engine/normalize.ts`
- `frontend/src/types/protocol.ts`

当前行为：

- typed resource 字段完整穿过后端、协议、前端和 ModelEngine。
- 无效、类型错配或同时填写两个资源字段会拒绝整个 effect，不会清空资源后继续广播轴值。
- Persona Effect arguments 出现旧 catalog/motion wrapper 字段时直接进入 feedback；这些字段不会被删除后继续生成动作，`<@anim>` 兼容输入仍由独立解析入口处理。
- expression 资源只有在与最终参数计划没有参数 ID 冲突时才叠加播放；启动失败会让当前 motion sink 失败。
- motion 资源被解析成明确的 catalog motion 定位信息，并替代普通参数计划执行；它仍由当前 segment 的统一 motion sink 启动和收口，不产生第二条 Timeline。

验收标准：同一 `turn_id + message_id` 的动作在后端、WebSocket、前端归一化结果、参数计划和 Motion Lab 记录中拥有一致的资源字段。

### 1.2 effect 调用数量和 segment 身份不明确（已修复）

当前 effect 提取会检查当前 segment 内全部 `ag99live.motion` 调用，不再静默选择第一个。当前约束：

- 一个 assistant segment 最多接受一个 `ag99live.motion`。
- 出现多个同名 effect 时直接进入 Motion Feedback，记录 `duplicate_motion_effect`，不选择第一个，也不合并未知语义。
- 文本、音频、动作和表演曲线必须使用同一个 `turn_id + message_id`。
- `turn_id` 不能替代 `message_id`。同一 turn 内的多个 assistant segment 必须可以独立播放、失败和收口。
- 兼容 `<@anim>` 仍然只在 Persona Effect 注入能力不存在时启用；主链路 effect 无效时不能切换到 `<@anim>`。
- Orchestrator、Timeline 和 pending motion scheduler 遇到空 `turn_id` 直接失败，不再创建 anonymous 聚合键。

涉及位置：

- `astrbot_plugin_ag99live_adapter/middleware/interaction_motion.py`
- `astrbot_plugin_ag99live_adapter/runtime/turn_coordinator.py`
- `frontend/src/adapter-connection/inbound/inboundEvents.ts`
- `frontend/src/turn-playback/useTurnPlaybackSessionStore.ts`

### 1.3 收口重复的动作后处理（已修复）

当前所有权已经收敛：

- `motion/motion_intent.py` 是 `engine.motion_intent.v4` 结构、类型、互斥关系、时长和 summary 的唯一规则源；middleware 只检查当前 semantic profile 实际开放的轴、等级和 typed resource 白名单。
- `TurnCoordinator` 不再执行 fallback pose repair、expressive floor、轴范围 clamp 或头身关系约束。
- ModelEngine 的 candidate stages 产生直接值和派生候选，`SemanticAxisRelationGraphStage` 统一拥有范围与头身关系约束。
- `PlanBuilder` 只把最终轴值映射到 Live2D 参数，并对坏 binding 显式失败。
- `MotionTransformTrace` 记录 raw levels、resolved、derived、constrained 和 compiled 阶段数据。

同一类语义规则现在只有一个主要所有者，不再靠后端和前端重复 clamp 获得表面稳定。

Motion Lab 也只通过 `record_motion_lab_observation()` 写入统一 envelope。interaction、
TurnCoordinator、performance curve 和前端回传都只能提供领域上下文与 raw payload，
不能各自定义一份数据库事件结构；底层 recorder 只负责异步排队和 SQLite 落库。

### 1.4 清理隐式 fallback，区分缺失和错误（已修复）

当前缺失、错误和可选能力按下表处理：

| 输入状态 | 处理方式 |
| --- | --- |
| 字段不存在且该字段可选 | 正常继续，并记录未启用 |
| 字段存在但类型或枚举非法 | 进入 Motion Feedback，不播放该动作 |
| 轴不存在或不在当前 profile | 拒绝整个动作并记录非法轴，不部分保留其它轴 |
| 轴全部缺失、非法或全中性 | 无有效动作输入，不生成默认动作 |
| 音频已声明但音频链路失败 | 记录 audio failed，不伪装成 absent |
| lip-sync 能力缺失 | optional lip-sync sink 记录 failed；audio required sink 可继续播放 |

这里的 `Motion Feedback` 是结构化诊断，不等于自动重新调用模型，也不等于生成默认动作。

当前 ModelEngine 编译失败会生成 `MotionFeedback`，并以 `motion.frontend_compile_failed` 事件记录 intent、feedback、diagnostics、`turn_id + message_id` 和 timing 上下文。失败动作不会进入播放器。

### 1.5 删除主链路 fallback pose repair（已修复）

当前主链路不再根据候选姿态补轴或替换轴值：

- 省略轴保持省略；只有关系图中显式配置的 derive 规则可以生成派生轴。
- 显式中性和非中性输入都按原语义进入 ModelEngine。
- 空动作、非法动作和全中性动作直接失败，不生成默认姿态。
- fallback candidate 只作为 Prompt 参考和诊断数据，不进入 payload 值处理。

### 1.6 模型加载与动作启动必须使用真实终态（已修复）

- `initializeLive2D()` 只有在当前模型进入 Cubism `CompleteSetup` 后才完成；Vue `nextTick` 不再被视为模型 ready。
- 同一轮重复初始化共享同一个加载 Promise，模型切换由调用侧串行化；不使用延时重试。
- model3 配置或纹理加载失败会拒绝模型加载，动作不能在模型 loading/error 状态下伪装成已启动。
- motion sink 返回拒绝时，segment 进入 failed 且 payload 只消费一次；不得写入 `motion released` 或反复重试同一 payload。

### 1.7 删除运行时参数和随动猜测（已修复）

- WebSDK 只接受 semantic profile 声明的精确 Cubism parameter id，不再按大小写、去符号名称或常见轴名重新搜索。
- lip-sync 只使用 model3 明确声明的 lip-sync 参数；缺失声明时 lip-sync sink 失败，不扫描 mouth/open 参数。
- voice-following profile 只声明可执行 parameter id、范围、幅度、权重和延迟；手势方向由 `turn_id + message_id` 的确定性轨迹极性表达，不依赖不安全的校准方向猜测。
- `engine.parameter_plan.v2` 的 `source`、`neutral_target_value` 和 `dynamics` 是必填契约，parser 与 WebSDK 均不得补默认值。

### 1.8 收紧 manifest、序列和音频错误契约（已修复）

- Mk6 的 `model3.json` 显式把 `ParamMouthOpenY` 声明为 `LipSync` 参数；运行时不扫描 mouth/open 名称。
- `speech_gesture_track` 的 preset、控制点、方向、延迟与时长边界在公共 parser 和 WebSDK parser 均为必填；旧周期字段不会被补齐或解释。
- multi-step sequence 的每一步必须携带自己的 dynamics，缺失时返回 `motion_sequence_dynamics_missing`，不得继承上一步参数。
- PlanBuilder 必须为每个轴找到明确的 `source`，缺失时返回 `axis_value_source_missing`。
- 音频启动仅在浏览器报告 `NotAllowedError` 时标记 `audio_autoplay_blocked`；其他异常保留为 `audio_sink_start_failed:<name>`。
- manifest 声明了空纹理文件名时，模型加载明确失败，不能无限停留在 loading。

### 1.6 明确生成方式和回复阶段不是同一个概念（已修复）

当前代码已经把两类概念分开：

- **生成方式**：主模型是否在一次回复中同时产生文本和 `effect_calls`。
- **回复阶段**：当前结果属于 immediate 还是 final segment。

当前继续使用主模型一次生成文本和 effect_calls，暂不引入 `parallel_independent`：

- 生成方式应明确标记为 `single_response_effect`。
- immediate/final 只能描述 segment 生命周期，不应被命名为动作生成模式。
- hybrid 如果产生两个 assistant segment，每个 segment 都必须有独立 `message_id` 和独立动作状态。
- 同一 segment 的 effect 不能因为 immediate/final 处理重复下发。

### 1.7 明确文本、音频和口型的时序语义（已修复）

统一 Timeline 已经成为音频、动作和口型的播放边界，当前语义为：

- `output.segment.text.content` 是唯一 canonical assistant text，也是唯一字幕来源；audio slot 不再复制 caption。
- audio 为 `present` 时，canonical text 只能在真实 Audio `playing` 时显示；audio 为 `absent` 时才立即显示。
- audio clock 是音频同步的唯一时间事实来源。
- motion 在 audio duration ready 时预编译，在 audio started 时立即启动；视觉入场延迟由 performance curve / parameter plan 表达，不再叠加固定延迟。
- lip-sync 失败必须可见，不能只让音频正常结束而不留下 segment 级状态。
- lip-sync WebAudio 分析不可用但模型嘴部参数仍可写时，允许随机开合作为明确记录失败后的视觉降级；日志和 Timeline 必须保留原始失败 reason，音频结束时停止降级并清零嘴部参数。

后端仍通过 `cache_audio_file -> output.segment.audio.url` 提供静态资源 URL；PCM WAV 当前走 passthrough，不再为播放重复转码。静态资源交付属于音频边界，后续首播延迟优化不能放到动作层补偿。

### 1.8 修复阶段验收（已完成静态验收）

以下修复阶段验收条件已经由单元测试和静态检查覆盖：

- 一个 segment 只有一个明确的动作输入结果。
- 无效动作不会变成默认动作。
- 后端不会重复应用同一语义约束。
- 任何失败都有结构化 reason 和 segment identity。
- 资源字段不会在协议边界丢失。
- 音频失败不会被解释成无音频。
- lip-sync 失败至少会写入明确的失败状态。
- 当前动作的原始值和最终值可以在日志或 Motion Lab 中关联查看。

## 2. 轴关系图目标架构

### 2.1 关系图的定位

轴关系图不是 UI 图表，也不是运行时随机生成的动作。它是当前 Live2D 模型的一个可版本化能力 profile，描述：

- 每个轴的中性值、范围和语义等级锚点。
- 轴之间的影响方向和系数。
- 头部、身体、视线和表情之间的关系。
- 哪些轴可以派生，哪些轴只能由输入直接控制。
- 哪些轴存在派生和比例限制。
- 约束的优先级和所有权。

当前名称为 `SemanticAxisRelationGraph`，以区别于最终的 Live2D 参数计划。v1 只负责轴关系；资源参数冲突由后续 `resourcePolicy` stage 负责，不伪装成已经进入关系图。

### 2.2 两条处理分支

```text
raw effect arguments
        |
        v
strict validation
   |             |
 rejected        accepted
   |             |
 Motion         value resolver
 Feedback           |
   |                v
 graph diagnostic  direct axis values
 overlay           + derived candidates
                    |
                    v
             SemanticAxisRelationGraph
                    |
                    v
             constrained final values
                    |
                    v
             engine.parameter_plan.v2
```

失败分支不会向关系图注入伪造的数值。它只把被拒绝的字段、失败原因和对应轴显示在同一张诊断图上，便于观察“为什么没有进入计算”。

成功分支才会进入数值处理和图计算。这样既能在同一张图上观察成功与失败，也不会用诊断数据污染播放输入。

### 2.3 校验阶段

校验阶段只回答“这份输入能否进入计算”，不负责生成动作。

校验项目：

1. `contract_version` 和 schema 是否支持。
2. `turn_id`、`message_id` 是否完整。
3. `intent_tags` 是否满足最小要求。
4. 轴名是否存在于当前 profile。
5. 轴值是否为有限数字，或是否为合法的 `axis_levels`。
6. 资源 ID 是否来自当前模型白名单。
7. 是否存在重复 effect。
8. 当前 profile 的 `model_id`、revision 和 hash 是否匹配。
9. 是否存在空动作、全中性动作或没有任何有效轴。

输出建议：

```json
{
  "status": "accepted",
  "turn_id": "turn-123",
  "message_id": "segment-001",
  "rejected_fields": [],
  "warnings": [],
  "feedback": []
}
```

失败时 `status` 为 `rejected`，并携带稳定的 `reason_code`。失败结果不能被转换为默认 pose。

### 2.4 值处理阶段

值处理阶段把已通过校验的输入变成关系图可消费的轴值向量。

Persona Effect 当前使用九级轴强度并输出 `engine.motion_intent.v4`。单姿态使用 `axis_levels`；明确的连续、往返或分阶段动作使用 `motion_steps`，一个 effect 内可以包含 2 到 4 个有序步骤：

```json
{
  "intent_tags": ["轻微调侃", "疑惑"],
  "axis_levels": {
    "head_yaw": -1,
    "body_yaw": 0,
    "brow_bias": 1
  }
}
```

```json
{
  "intent_tags": ["测试", "左右扭头"],
  "motion_steps": [
    { "axis_levels": { "head_yaw": -3, "gaze_x": -2 }, "duration_weight": 1 },
    { "axis_levels": { "head_yaw": 3, "gaze_x": 2 }, "duration_weight": 1 }
  ]
}
```

`axis_levels` 与 `motion_steps` 必须二选一。序列中的每一步必须使用相同轴集合，避免省略轴在步骤切换时产生“保持上一值”还是“回到中性”的歧义。ModelEngine 分别编译各步骤，再合并为一个带参数关键帧的 `engine.parameter_plan.v2`；WebSDK 只启动一个 run，并由统一时钟驱动关键帧切换。

值处理顺序：

1. 保留原始 effect arguments。
2. ModelEngine 根据 `turnId + messageId + profile hash + transform version` 生成稳定 seed。
3. 等级 `0` 精确映射到中性值；其他等级在当前锚点与相邻等级中线构成的区间内确定性采样，不跨越等级边界。
4. 使用一个共享随机因子保持头、身、视线协调，再叠加小幅每轴因子；同一消息可复现，不同消息产生受控变化。
5. 标记转换前等级、seed、随机因子和转换后轴值；不在 adapter 里执行关系计算。
6. 将结果送入关系图，不在入口层提前执行第二套关系计算。

`engine.motion_intent.v3 + axes` 不属于过渡主输入，只在 `<@anim>` 官方兼容和内部手动预览中独立保留。

### 2.5 关系图数据结构

关系图是 semantic profile 的一部分。轴节点由 profile 的 `axes` 定义，`relation_graph` 当前只保存显式边；profile 自身提供 revision 和 source hash。当前真实结构如下：

```json
{
  "profile_id": "mk6.semantic.v1",
  "revision": 4,
  "source_hash": "sha256:...",
  "axes": ["... SemanticAxisDefinition ..."],
  "relation_graph": {
    "schema_version": "ag99.semantic_axis_relation_graph.v1",
    "edges": [
      {
        "id": "head_body_yaw_limit",
        "source_axis_id": "head_yaw",
        "target_axis_id": "body_yaw",
        "kind": "bounded_ratio",
        "mode": "same_direction",
        "scale": 0.5,
        "deadzone": 4,
        "max_delta": 12
      }
    ]
  }
}
```

`kind` 当前只接受 `derive` 和 `bounded_ratio`。轴自身的 `value_range` 由关系图 stage 统一应用，不另存一份重复 constraints 数组。

### 2.6 头部和身体的关系

头部和身体允许相反方向，但不能出现两个方向都达到极端值的非自然姿态。

关系图不应强制身体和头部同向，而应使用中性值差量计算：

```text
head_delta = head_value - head_neutral
body_delta = body_value - body_neutral

允许：sign(head_delta) == sign(body_delta)
允许：sign(head_delta) != sign(body_delta)
限制：abs(body_delta) <= body_cap(abs(head_delta), profile)
```

具体约束由 profile 配置，而不是写死在 Prompt 中。当前 trace 同时记录实际调整的 before / after / reason，以及逐边 `relationEvaluations`，包括输入值、限制值、最终值和跳过原因。

### 2.7 关系图在 ModelEngine 中的挂载方式

ModelEngine 已经有 compiler stage registry，因此关系图应作为一个明确的可挂载 stage，而不是继续散落在多个模块：

```text
IntentValidator
  -> AxisResolver
  -> IntensityStage
  -> DerivedCandidateCollection
  -> AxisRelationGraphStage
  -> ModeResolverStage
  -> TimingStage
  -> PlanBuilder
  -> ResourcePolicyStage
```

其中：

- `AxisResolver` 只负责输入轴识别和基础范围校验。
- `IntensityStage` 只负责整体和单轴强度。
- `DerivedCandidateCollection` 收集 coupling 和 speech pose 等轴候选值，不直接覆盖输入。
- `AxisRelationGraphStage` 统一执行轴之间的派生、比例和最终范围约束。
- `PlanBuilder` 只负责把最终轴值映射到 Live2D 参数。
- `ResourcePolicyStage` 基于已编译参数检查 typed resource 定位和参数所有权冲突。

后端可以执行协议安全校验，但不能再执行一套和 `AxisRelationGraphStage` 相同的语义耦合。这样既保留后端的输入防线，也避免前后端重复修正。

### 2.8 关系图输出和诊断

关系图每次计算都应输出：

- 直接输入轴值。
- `axis_levels` 到实际值的映射结果。
- 派生候选值。
- 被拒绝或忽略的轴。
- 每条边的实际影响。
- 每条约束的命中情况。
- 被调整的轴及调整前后值。
- 最终输出值。
- 对应的 profile revision、profile hash 和 transform version。

当前 `MotionTransformTrace` 结构为：

```json
{
  "transformVersion": "semantic_motion_transform.v4",
  "profileRevision": 4,
  "profileHash": "sha256:...",
  "rawAxes": {},
  "rawAxisLevels": { "head_yaw": 1 },
  "axisSampling": {
```

### 2.9 当前迁移落点

当前实现已经完成第一轮所有权迁移：

- `ModelEngine` 已增加 `MotionFeedback`、`MotionTransformTrace` 和可挂载的 `SemanticAxisRelationGraphStage`。
- `ModelEngine` 已增加 `resourcePolicy` stage：资源 ID 必须命中当前模型已暴露且类型匹配的资源。expression 必须通过参数所有权冲突检查；motion 必须拥有完整的 group/index/file 定位信息。
- semantic profile 已增加 `ag99.semantic_axis_relation_graph.v1`；当前第一版使用 `edges` 显式描述 `derive` 和 `bounded_ratio` 规则，头身规则不再依赖 `head_`/`body_` 命名推断。
- 非法轴、越界轴和明确全中性轴会终止编译，不再在 Engine 内静默 salvage 或 clamp。
- coupling、intensity 和 speech pose 先产生候选值，关系图阶段统一执行轴值范围、头身比例约束并记录调整前后值。
- PlanBuilder 对参数 binding 配置错误、输入范围不匹配和重复参数目标直接返回 feedback，不再跳过坏 binding 后继续生成计划。
- Persona Effect adapter 和 `TurnCoordinator` 不再执行 expressive floor、fallback pose repair 或头身关系约束；旧 `RealtimeMotionPlan` 生成器已删除。
- `TurnCoordinator` 只负责 v3/v4 协议校验、性能曲线挂载和消息发送。
- v3 兼容路径的 motion visibility summary 只保留轴可见性、资源意图和诊断描述，不再携带 fallback/repair 结果字段；Prompt 候选仍是独立的参考数据，不进入主动作 payload。
- `<@anim>` 仍作为官方兼容输入，但进入同一个前端 ModelEngine 编译链，不保留第二套语义处理规则。

当前明确保留的后续边界：

- 旧 profile 的关系图迁移已经完成：首次加载会持久化由 `couplings` 派生的关系图，前端主播放链路不再读取旧 `couplings`，后端仅保留一次性迁移所需的旧格式规范化。
- 关系图目前已接入派生、轴值范围和头身比例约束，参数 binding 已采用严格失败策略。资源采用第一版确定性策略，不隐式启用 additive/blend。
- Persona Effect 主链路已改为 `axis_levels -> engine.motion_intent.v4`；`engine.motion_intent.v3 + axes` 只保留给 `<@anim>` 官方兼容入口和内部手动预览，不作为 Persona Effect 的降级路径。
- Persona Effect 支持单 effect 内的 `motion_steps`；重复同名 effect 仍按协议错误拒绝。多步骤由 ModelEngine 编译为单一参数关键帧计划，并由 WebSDK 在同一个统一时钟 run 中播放。
- 九级锚点区间采样已在 `semantic_motion_transform.v4` 启用；缺失 `turnId/messageId` 时 v4 编译直接失败，不生成不可复现随机值。intensity 只能在本级 `sampleBounds` 内调整，不能把低等级放大到相邻等级。
- semantic profile 为每个轴保存最大速度、最大加速度、生命动作比例和说话随动最大偏移；旧 profile 缺少 dynamics 时会补齐并持久化。
- 语义动作和说话随动写入同一参数时，ModelEngine 把随动编译为该参数的 modulation，不创建第二写入者，也不因参数重叠拒绝整段动作。
- WebSDK 只接受完整且可绑定的 parameter plan；缺参数、重复参数、越界目标、坏 keyframe/modulation/dynamics 会让整个计划失败，不部分播放。
- expression/motion resource 已完成第一版严格策略：一次只接受一个 typed resource；expression 可与不冲突参数叠加，motion 作为完整动作主层替代普通参数计划。更复杂的 additive/blend 规则不在当前版本隐式启用。
- fallback candidate 仍可作为 Prompt 参考数据，但不再参与主动作 payload 修复或后端候选评分；旧 fallback 决策函数已删除。
- Live2D WebSDK 只接收 ModelEngine 已解析的 parameter plan、expression runtime ID 或 catalog motion 定位，不承载语义决策和资源仲裁。

## 3. 已实施的优化与可选后续

本节的主协议和主运行路径已经实施；每节会明确仍保留的可选能力。

### 3.1 九级方向强度

当前模型输出已经从连续 `0–100` 改为：

```text
-4 短时夸张负方向
-3 普通 Live2D 清晰可见负方向
-2 克制负方向
-1 局部细节、缓入或恢复负方向
 0 明确回到中性
+1 局部细节、缓入或恢复正方向
+2 克制正方向
+3 普通 Live2D 清晰可见正方向
+4 短时夸张正方向
```

模型负责语义方向和等级选择，adapter 负责严格校验并发送 `engine.motion_intent.v4`，ModelEngine 根据当前 profile 锚点转换为实际轴值。v4 同时出现 `axes`、等级非整数或超出 `-4..4` 时直接拒绝；不会部分保留合法轴，也不会退回 v3。

Live2D 表演以可读性为先。普通回复的主要姿态轴从三级开始；二级只用于安静、犹豫、低落等克制表达，一级用于局部细节和过渡，四级用于短暂而明显的夸张表演。身体仍受关系图的头身比例和硬范围约束，不能因为使用三级或四级而突破模型安全边界。

### 3.2 每个模型的等级锚点和确定性转换

每个轴拥有自己的等级锚点，不使用全局固定映射。当前计算为：

```text
±1 = soft_range 边界
±2 = soft_range 与 strong_range 的中点
±3 = strong_range 边界
±4 = extreme_range 边界
level_bounds = midpoint(previous_anchor, anchor, next_anchor)
axis_value = deterministic_sample(level_bounds, turn_id, message_id, profile_hash)
```

seed 至少包含：

```text
turn_id + message_id + axis_id + profile_hash + transform_version
```

实现使用稳定 hash，不使用语言运行时不保证稳定的内置 hash。同一 segment 可复现，不同 segment 会在同一等级范围内产生受控变化。共享随机因子占主要权重，每轴随机因子提供小幅差异，保持头身和视线协调。

`extreme_range` 是每轴独立配置，必须包含 `strong_range` 且位于 `value_range` 内。当前契约为 `ag99.semantic_axis_profile.v2`；v2 profile 缺失该字段时直接失败。磁盘中的 v1 profile 只在加载阶段执行一次显式 schema migration，优先从既有 `±4` 锚点恢复并持久化为 v2，不在播放时临时外推。

等级 `0` 精确等于 neutral；非零等级只在相邻锚点中线围成的本级区间内采样。`MotionTransformTrace` 记录 seed、共享因子、每轴因子、`sampledValues` 和 `sampleBounds`。profile 锚点缺失、越界、中性点不一致或顺序错误会显式失败。

头部和身体使用不同锚点和不同限制范围。头身关系仍然在中性差量上计算，不能直接比较两个绝对 `0–100` 数字。

### 3.2.1 每轴动态约束与逐帧合成

每个 semantic axis 的 profile 还定义：

- `max_velocity`：语义轴每秒最大变化量。
- `max_acceleration`：语义轴每秒速度变化上限。
- `life_motion_scale`：目标姿态附近生命动作的比例。
- `max_speech_offset_ratio`：说话随动相对参数输出范围的最大偏移比例。

`max_velocity` 和 `max_acceleration` 配置在语义轴空间，单位分别是“语义轴单位/秒”和“语义轴单位/秒平方”。PlanBuilder 根据 binding 的 input/output span 把它们映射到 Cubism 参数空间；`life_motion_scale` 和 `max_speech_offset_ratio` 保持无量纲。WebSDK 先合成序列关键帧、生命动作、说话随动和表演曲线 easing，再对最终写入目标应用速度与加速度限制。这样参数只有一个最终写入者，曲线也不能绕过动态上限。

逐帧动力学使用带制动距离的速度目标：目标反转时按最大加速度连续减速，不瞬间把速度清零；离散帧跨越目标时则精确停在目标，避免在目标两侧振荡。最后才执行 Cubism 参数硬范围校验，因此动态限制不能制造越界写入。

参数计划执行期间，WebSDK 将当前 run 视为帧异常的所有者。参数计算、Cubism update、physics 或 draw 在该帧抛错时，当前 run 必须立即以 `failed` 终止并携带具体异常原因；RAF 继续下一帧，不能因为一个动作段异常冻结整个 Live2D renderer。外层 terminal watchdog 超时时也必须主动停止 SDK 内的计划，不能只修改 UI 状态后留下悬挂 run。没有活动参数计划时的普通渲染异常仍然抛出，不会被动作层吞掉。

`engine.parameter_plan.v2` 中每个参数必须同时提供 `neutral_target_value` 和 `dynamics`。缺失任一字段都会拒绝整份计划，不能以关闭生命动作或动态限制的方式继续播放。动作实验室手动预览也从当前 axis profile 和 binding 计算这两个字段，不维护第二套默认值。旧 semantic profile 首次加载时补齐 dynamics 并持久化属于配置 schema 迁移；播放中的缺失字段仍然直接失败，二者不能混同为运行时 fallback。

多步骤动作在编译时按静止到静止的三角形或梯形速度曲线计算最短过渡时间。预算同时检查“中性位到第一步”和相邻步骤之间的运动；任一参数无法在当前步骤时长内满足速度与加速度上限时，整段序列以 `motion_sequence_transition_budget_exceeded` 失败。

### 3.3 Prompt 压缩和三层边界

保留三层结构：

- system：任务、选择原则、输出目标。
- capability：当前模型可用轴、九级含义、profile 风格、v4 参考示例和少量候选信息。
- context：本轮用户文本、助手文本、上一动作关键轴等级和必要的反重复提示。

Prompt 不再重复写完整 JSON 协议、相同轴说明和实现细节。Effect schema 负责结构约束，Prompt 负责语义选择。

### 3.4 删除不必要的实现信息

动作决策文本只需要告诉模型：

- 当前正在控制一个 Live2D 角色。
- 当前有哪些语义轴和每个轴的含义。
- 每个轴如何使用九级方向强度。
- 本轮需要返回哪些动作意图字段。

不应向模型暴露：

- AG99live 内部模块名。
- AstrBot 传输细节。
- WebSocket、client object、middleware 等实现名词。
- 前端 ModelEngine 的内部 stage 名称。

`<@anim>` 兼容链路可以保留自己的传输说明，但不得污染主 effect Prompt。

### 3.5 Few-shot、历史样本和 Motion Lab

内置参考由六类单姿态和一类序列组成：`neutral / explain / soothe / confused / happy / surprised / sequence`。它们直接展示当前 Persona Effect arguments，不再使用旧连续 `axes` 输出。人工筛选样本会根据当前 profile 锚点投影为 `axis_levels`，只有 profile id 和 revision 一致时才可进入 Prompt；`explain / surprised / sequence` 固定保留结构教学席位，再选择最多 3 条人工样本，其余席位按类别补齐到 7 条参考。

样本需要同时记录：

- 原始对话和 effect arguments。
- 原始 `axis_levels`。
- profile id、revision、hash。
- 转换后的轴值。
- 关系图调整前后的值。
- 最终 parameter plan。
- 实际音频、动作、口型终态。
- 人工评价和反馈。

省略轴和显式中性轴必须在样本中保持可区分。否则后续训练会把“未控制该轴”和“要求回到中性”学成同一种标签。

当前 raw levels、resolved/constrained axes、compiled parameters、profile hash、transform version、run ID 和 timeline outcome 已可持久化。尚未完成的是独立历史工作台中的筛选、回放、人工评价和训练集导出。

### 3.6 expression 和 motion resource 分层

主协议使用明确的 typed resource 意图：

```json
{
  "expression_resource_id": "expression.smile"
}
```

但资源不能直接绕过 ModelEngine 或 PlaybackTimeline。每个资源候选需要声明：

- 资源类型。
- 拥有的 Live2D 参数 ID。
- 优先级。
- 可叠加层级。
- 是否允许和语义轴同时播放。
- 冲突时的处理策略。

当前采用严格拒绝冲突，并禁止同时填写 expression 与 motion。后续只有在关系图拥有明确 additive、overwrite 或 blend 规则后才能放宽；不能依赖资源名称判断兼容性。

### 3.7 保持 fallback candidate 与运行时隔离

该项已完成：fallback candidate 只服务 Prompt 参考和诊断，不承担补轴、错误恢复或默认姿态生成。没有有效动作输入时明确返回失败或无动作状态，由播放编排器决定是否只播放文本或语音。

### 3.8 统一后处理所有权

目标所有权：

| 层 | 负责内容 |
| --- | --- |
| 主模型 | 文本、intent_tags、方向和九级强度、明确资源意图 |
| Adapter | effect 提取、schema 校验、协议安全检查、segment identity |
| 值处理器 | 九级到轴值的 profile 映射和来源标记 |
| ModelEngine 关系图 stage | 轴之间影响、派生、头身约束和最终轴范围约束 |
| ModelEngine resourcePolicy | typed resource 白名单、运行时定位和参数所有权冲突 |
| ModelEngine PlanBuilder | 语义轴到 Live2D 参数的映射 |

同一类规则只能有一个主要所有者。其它层最多做输入校验或诊断，不得再次修改同一类值。

### 3.9 其它优化状态

- **已完成**：`engine.motion_intent.v4` 是 axis-level contract version，主 Persona Effect 不同时接受 v3 axes。
- **已完成**：profile source hash、revision 和 transform version 进入编译校验与 trace。
- **部分完成**：Motion Lab 已记录 effect、intent、动作编译/播放和 timeline outcome；更细的 audio/lip-sync 时间点仍需结合真实端到端日志验证覆盖度。

### 3.10 第一阶段说话表演升级

原有说话随动使用固定频率正弦周期，长句中容易形成机械的左右往复。第一阶段已经替换为确定性的非周期手势轨迹：

```text
ModelEngine
  -> 根据 performance curve、intent tags 和 segment identity 选择预设
  -> 生成 speech_gesture_track 控制点
  -> 为身体通道写入明确 follow_delay_ms
PlaybackTimeline
  -> 提供真实音频时长和播放时钟
WebSDK
  -> 逐帧插值控制点
  -> 乘以真实语音能量
  -> 应用 dynamics、范围限制和物理
```

当前预设为 `calm_explain`、`lively_chat`、`gentle_support` 和 `emphatic`。每个 preset 都声明按优先级排序的可用通道映射，而非假定所有模型具备完整头身轴。同一 `turn_id + message_id` 必须生成相同的通道选择、方向和控制点；不同 segment 可以改变方向或是否启用身体通道。头部立即响应，身体使用 profile 中的 `follow_delay_ms` 延后跟随；短音频只选择可在 segment 内完整回正的通道。

`voice_following_profile` 已升级为 `ag99.voice_following_profile.v2`。旧 profile 和旧 `speech_pose_cycle` 不提供兼容执行路径，入站和参数计划解析会直接拒绝。参数计划按音频时长重定时时，手势控制点随可用活动时长缩放，身体延迟保持绝对毫秒，不随长句被放大成不自然的秒级延迟。

口型值和说话能量已经拆开：真实 Web Audio RMS 同时生成两路独立信号。音频分析不再以模型存在口型参数为前置条件，因此没有口型参数的模型仍可驱动说话手势；口型分析失败后的随机开合只写嘴型参数，不得驱动头身动作。这样降级口型不会让身体误判为持续高能量讲话。

本阶段暂不包含停顿检测、重音检测、句尾语义手势和关系图逐帧复算。这些能力应在真实模型上观察四种预设后继续设计，不能通过重新引入周期振荡或随机 body energy 实现。

## 4. 实施顺序

### 阶段一：修复当前链路

阶段一的协议边界、错误反馈、统一生成方式命名和播放终态收口已经完成；以下清单用于回溯验收范围：

1. 修复 typed resource 传递和协议类型一致性。
2. 收紧 effect 数量和 segment identity。
3. 删除或合并重复的归一化、约束和广播前处理。
4. 清理非法输入和性能曲线的隐式 fallback。
5. 删除主链路 fallback pose repair，保留候选仅作 Prompt 参考。
6. 明确文本、音频、动作和 lip-sync 的失败与终态。
7. 统一生成方式和 immediate/final 阶段命名。
8. 增加修复阶段的端到端日志和测试。

### 阶段二：建立关系图基础

1. 定义 `SemanticAxisRelationGraph` profile schema。第一版 schema 已落地为 `ag99.semantic_axis_relation_graph.v1`。
2. profile 已提供 revision、source hash 和轴节点定义；`relation_graph.edges` 保存关系边，不复制一份节点数组。
3. 把当前轴值范围和头身约束迁移到关系图规则。当前已完成范围约束和 `bounded_ratio` 边接入，允许反向动作但限制极端差量。
4. 在 ModelEngine registry 中增加关系图 stage。当前 stage 已挂载在候选值收集之后、计划构建之前。
5. 输出 `MotionTransformTrace`。当前已记录资源意图、profile revision/hash、变换版本、采样区间、关系调整和完整逐边命中结果。
6. 用关系图结果替代散落的 coupling 和重复约束。前端主播放链路已完成替换，后端旧 `couplings` 仅用于一次性 profile 迁移。

### 阶段三：优化模型输出和资源能力

1. 引入九级 `axis_levels`。已完成 Persona Effect v4 主链路、前后端严格协议校验和上一动作等级摘要。
2. 增加每轴锚点和确定性转换。已完成等级区间内可复现采样、旧 profile 持久化迁移、等级边界保护和 transform trace。
3. 压缩 Prompt 和统一姿态参考。已完成 system / capability / context 三层边界；主 Prompt 不再重复 JSON 示例或暴露插件、profile 文件与候选来源信息。
4. 调整历史样本和 Motion Lab 数据结构。已完成 `rawAxisLevels / resolvedAxes / constrainedAxes / compiledParameters` 记录，SQLite schema v2 增加 transform/run/timeline outcome 投影。
5. 明确 expression/motion resource 所有权和冲突规则。已完成第一版严格 typed resource 策略。
6. 完成资源统一进入 ModelEngine 与 PlaybackTimeline 的路径。已完成，资源和普通参数动作共享当前 segment 的 motion sink 与 Timeline 终态。

### 4.1 当前完成度结论

当前可以视为已经完成的主链路：

```text
Persona Effect axis_levels
-> engine.motion_intent.v4 strict validation
-> profile level anchors
-> ModelEngine candidate stages
-> SemanticAxisRelationGraph
-> resource policy / PlanBuilder
-> PlaybackTimeline motion sink
-> Live2D runtime
-> Motion Lab trace and terminal recording
```

这条链路已经满足以下开发期约束：

- 非法输入、重复 effect、资源冲突和 profile 不匹配均显式失败。
- v4 不降级为 v3；`<@anim>` v3 只保留为 Persona Effect 注入能力不存在时的官方兼容入口。
- 后端不再执行 fallback pose repair、expressive floor 或头身语义约束。
- ModelEngine 是轴值关系、资源仲裁和参数计划编译的唯一所有者。
- Timeline 是 audio / motion / lip-sync 播放生命周期的唯一执行边界。
- Motion Lab 原始事件先进入前端 IndexedDB，后端 SQLite 持久化完成后按稳定 `event_id` 回执；WebSocket 发送成功不再被解释为持久化成功。

当前尚未完成的内容分为三类：

| 类别 | 未完成项 | 是否阻塞当前主链路 |
| --- | --- | --- |
| 必须验收 | 使用真实 AstrBot、Provider、TTS、Electron 和 Live2D 模型完成端到端回归 | 是，阻塞本轮最终验收，但不阻塞代码继续集成 |
| 工具能力 | Motion Lab 历史筛选、回放、人工评价和训练样本导出工作台 | 否 |
| 可选资源增强 | expression / motion 的 additive、overwrite、blend 图规则 | 否，当前严格冲突拒绝策略完整可用 |
| 长期研究 | 关系图在线学习或独立动作生成模型 | 否 |

完整逐边轨迹独立于 `relationAdjustments`：后者只记录实际改变最终值的规则，`relationEvaluations` 则记录 `within_limit / derived / constrained / skipped` 以及对应原因。稳定复算不会覆盖本次已经发生的派生或约束结果。

## 5. 测试与验收

### 单元测试

- 缺失或重复 effect 的拒绝。
- `turn_id + message_id` 不匹配的拒绝。
- typed resource 从后端到前端的完整保留。
- 省略轴、显式中性轴、非法轴的差异。
- 头身同向和反向动作的关系图约束。
- 关系图系数、deadzone、max_delta 和范围约束。
- 九级采样不会跨越当前等级边界，且同一 segment 可以复现。
- 速度/加速度限制在目标反转时连续减速，在离散帧到达时不会越过目标振荡。
- `neutral_target_value` 或 dynamics 缺失时整份参数计划失败。
- 参数计划帧异常会终止当前 run 而不会终止 RAF；terminal watchdog 会同步停止 SDK 计划。
- profile revision/hash 不匹配。
- fallback candidate 不参与运行时补轴、替换或错误恢复。
- 非法性能曲线不再静默改成默认曲线。
- 资源不存在、资源未暴露、资源所有权缺失和资源参数冲突的拒绝。
- 四种说话手势预设选择、segment identity 确定性和身体延迟后的时长边界。
- 直接参数计划重定时时同步缩放手势控制点。
- 真实 RMS 分别驱动口型和说话能量，随机口型降级不写说话能量。

### 集成测试

- 主模型文本和 effect_calls 进入同一 segment。
- 文本、音频、动作和 lip-sync 共享同一 Timeline。
- 音频失败不会释放 motion-only。
- lip-sync 失败能够留下明确终态。
- 动作编译失败能够让 required motion sink 失败。
- 资源动作和语义轴动作不会绕过 ModelEngine 或 Timeline。
- 资源意图不会在 ModelEngine 之外隐式触发 catalog/expression 播放。

### 端到端测试

使用真实 AstrBot、真实 Provider 和 Electron/Live2D runtime 验证：

1. 主模型一次生成文本和 `ag99live.motion` effect。
2. 后端记录 raw effect、校验结果和 transform trace。
3. 前端收到同一 `turnId + messageId` 的文本、音频、动作。
4. 音频以真实 audio clock 播放。
5. 动作在音频开始后按策略启动。
6. 口型与音频共享同一播放段。
7. 最终 SessionStore、Timeline 和 Motion Lab 终态一致。

上述单元测试和静态依赖检查已经覆盖主要失败路径，但本节真实环境端到端测试尚未执行完毕。尤其需要验证：

- TTS 音频真实到达时，动作在 duration ready 阶段完成预编译，并与字幕、口型一起响应 audio started。
- lip-sync 读取当前 `HTMLAudioElement`，不会出现有声无口型且无失败状态。
- WebSocket 在 Motion Lab 事件发送后、SQLite 回执前断开时，前端重连会用同一 `event_id` 重发且数据库只保留一条记录。
- hybrid 的多个 assistant segment 使用不同 `message_id`，互不覆盖动作和播放终态。

## 6. 当前不做的内容

- 暂不实现 `parallel_independent`。
- 暂不实现独立的 Motion Lab 历史筛选工作台。
- 暂不把关系图做成在线自学习系统。
- 暂不让模型直接选择 motion3、exp3 或文件路径。
- 暂不实现由模型实时生成任意数学曲线；当前使用独立可配置 Provider 选择预设曲线族，再由前端按真实音频时长求值。
- 暂不开放无边界随机或不可复现随机；当前只使用等级区间内的确定性采样。
- 暂不开放资源 additive/blend；当前继续使用 typed resource 和参数所有权冲突的严格拒绝策略。

这些内容可以在修复阶段和轴关系图基础稳定后重新评估。
