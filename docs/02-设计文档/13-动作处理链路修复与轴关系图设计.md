# 动作处理链路修复与轴关系图设计

> 文档状态：计划中。
>
> 本文描述动作链路的修复顺序和下一阶段优化目标。当前已经成立的 `ag99live.motion` Persona Effect、`engine.motion_intent.v3`、统一播放 Timeline 和 ModelEngine compiler stage 仍以现有权威文档为准；本文不在没有实现前把计划描述成当前行为。

## 目标

动作链路先解决确定性、可追踪性和错误暴露问题，再优化模型输出表达方式。最终目标不是继续在各层添加修正，而是建立一条明确的动作值处理管线：

```text
主模型文本 + Persona Effect
  -> 严格校验
     -> 失败：Motion Feedback / 诊断 / 不播放
     -> 成功：动作值处理
  -> 轴值关系图计算与约束
  -> engine.parameter_plan.v2
  -> PlaybackTimeline
  -> Live2D WebSDK
```

校验失败路径和成功路径共享同一份轴关系图、profile 和诊断视图，但失败路径不能伪造数值、生成默认动作或进入播放。

## 1. 首先修复的问题

本节只处理当前链路中的缺陷和边界混乱，不在修复阶段引入七级强度、资源分层等新协议。

### 1.1 动作资源在前端边界丢失

后端动作归一化会校验并写入 `resource_id`，但前端 `parseSemanticMotionIntent()` 构建 `NormalizedSemanticMotionIntent` 时没有保留这个字段。当前资源意图可能在进入 ModelEngine 前丢失。

涉及位置：

- `astrbot_plugin_ag99live_adapter/middleware/motion_payload.py`
- `frontend/src/model-engine/normalize.ts`
- `frontend/src/types/protocol.ts`

修复要求：

- `resource_id` 要么完整穿过后端、协议、前端和 ModelEngine，要么从当前主链路契约中删除。
- 不允许后端显示“资源已校验”，前端却静默丢弃。
- 在资源播放策略尚未确定前，可以只传递和记录资源意图，但必须明确它暂时不触发播放。

验收标准：同一 `turn_id + message_id` 的动作在后端、WebSocket、前端归一化结果和 Motion Lab 记录中拥有一致的资源字段。

### 1.2 effect 调用数量和 segment 身份不明确

当前 effect 提取逻辑找到第一个 `ag99live.motion` 后立即返回。如果一个结果中出现多个动作 effect，后续 effect 会被静默忽略。

修复要求：

- 一个 assistant segment 最多接受一个 `ag99live.motion`。
- 出现多个同名 effect 时直接进入 Motion Feedback，记录 `duplicate_motion_effect`，不选择第一个，也不合并未知语义。
- 文本、音频、动作和表演曲线必须使用同一个 `turn_id + message_id`。
- `turn_id` 不能替代 `message_id`。同一 turn 内的多个 assistant segment 必须可以独立播放、失败和收口。
- 兼容 `<@anim>` 仍然只在 Persona Effect 注入能力不存在时启用；主链路 effect 无效时不能切换到 `<@anim>`。

涉及位置：

- `astrbot_plugin_ag99live_adapter/middleware/interaction_motion.py`
- `astrbot_plugin_ag99live_adapter/runtime/turn_coordinator.py`
- `frontend/src/adapter-connection/inbound/inboundEvents.ts`
- `frontend/src/turn-playback/useTurnPlaybackSessionStore.ts`

### 1.3 收口重复的动作后处理

当前后端动作 payload 处理中已经存在多种调整：

- 输入轴归一化和范围限制
- fallback pose repair
- expressive floor
- 头身关系约束

动作广播前，`TurnCoordinator` 还会重新归一化并再次应用约束。进入前端后，ModelEngine 又会执行 intensity、coupling、speech pose、timing 等 stage。

这会造成三个问题：

1. 同一条规则可能被执行两次。
2. 模型原始输出和最终输出之间无法解释。
3. 任何一层都可能覆盖另一层的结果，难以确定参数所有权。

修复要求：

- 修复阶段先保留现有输出协议，但将每个变换入口收敛成单一调用点。
- 后端只负责协议级校验、有限值检查、允许轴检查和传输边界验证。
- 头身关系、派生轴、参数冲突等语义计算不能同时存在于后端和 ModelEngine。
- 现有规则迁移期间必须记录 `raw -> normalized -> constrained -> compiled` 的阶段数据。
- 不能用“再加一层 clamp”解决归因问题。

### 1.4 清理隐式 fallback，区分缺失和错误

开发初期需要暴露问题，而不是让错误看起来像正常动作。当前仍有几类需要收紧的行为：

- 非法表演曲线枚举可能被改成默认值。
- 表演曲线无法根据 Timeline 求值时，当前动作会删除曲线字段后继续播放。
- fallback pose repair 可能替换模型明确输出但接近中性的轴。
- 部分旧的方向判断代码仍保留 hash 方向 fallback。

修复原则：

| 输入状态 | 处理方式 |
| --- | --- |
| 字段不存在且该字段可选 | 正常继续，并记录未启用 |
| 字段存在但类型或枚举非法 | 进入 Motion Feedback，不播放该动作 |
| 轴不存在或不在当前 profile | 拒绝该轴并记录原因；是否允许保留其它轴由契约明确规定 |
| 轴全部缺失、非法或全中性 | 无有效动作输入，不生成默认动作 |
| 音频已声明但音频链路失败 | 记录 audio failed，不伪装成 absent |
| lip-sync 能力缺失 | 记录 lip-sync failed；是否阻断音频由明确播放策略决定 |

这里的 `Motion Feedback` 是结构化诊断，不等于自动重新调用模型，也不等于生成默认动作。

### 1.5 修复 fallback pose 的替换边界

当前 skeleton repair 的目标是补足缺失的头、身、视线骨架，这是合理的。但“轴存在且接近中性时替换”为 fallback 值，会破坏显式中性语义。

修复要求：

- 省略轴：可以在有限范围内补充。
- 显式输出中性值：必须保留，不得被 fallback pose 替换。
- 显式输出非中性值：必须保留。
- 只有在动作有效但缺少必要骨架时，才允许增加补充轴。
- 所有补充轴记录 `source=fallback_pose_repair` 和对应 candidate。
- 空动作、非法动作、全中性动作不能通过 pose repair 变成默认动作。

### 1.6 明确生成方式和回复阶段不是同一个概念

当前代码和诊断中仍有 `split_after_reply`、immediate、final 等命名。它们容易把两类概念混在一起：

- **生成方式**：主模型是否在一次回复中同时产生文本和 `effect_calls`。
- **回复阶段**：当前结果属于 immediate 还是 final segment。

当前计划是继续使用主模型一次生成文本和 effect_calls，暂不引入 `parallel_independent`。因此：

- 生成方式应明确标记为 `single_response_effect`。
- immediate/final 只能描述 segment 生命周期，不应被命名为动作生成模式。
- hybrid 如果产生两个 assistant segment，每个 segment 都必须有独立 `message_id` 和独立动作状态。
- 同一 segment 的 effect 不能因为 immediate/final 处理重复下发。

### 1.7 明确文本、音频和口型的时序语义

统一 Timeline 已经成为音频、动作和口型的播放边界，但仍需要把以下语义写死：

- `output.text` 是聊天可见文本，允许在音频前显示。
- `output.audio.caption_text` 是语音字幕候选，若要求严格同步，不能继续复用普通文本 sink 的释放时机。
- audio clock 是音频同步的唯一时间事实来源。
- motion 应在 audio started 后按既定的轻微延迟启动，而不是以文本发送时间作为动作时钟。
- lip-sync 失败必须可见，不能只让音频正常结束而不留下 segment 级状态。

此外，后端当前仍有 `cache_audio_file -> output.audio` 的步骤。它是否必须保留，需要单独确认 WAV 静态资源服务是否支持直接播放；如果支持，应作为后续首播延迟优化，而不是在动作层增加补偿。

### 1.8 修复阶段验收

修复阶段完成前，不开始七级强度迁移。必须满足：

- 一个 segment 只有一个明确的动作输入结果。
- 无效动作不会变成默认动作。
- 后端不会重复应用同一语义约束。
- 任何失败都有结构化 reason 和 segment identity。
- 资源字段不会在协议边界丢失。
- 音频失败不会被解释成无音频。
- lip-sync 失败至少会写入明确的失败状态。
- 当前动作的原始值和最终值可以在日志或 Motion Lab 中关联查看。

## 2. 轴关系图目标架构

### 2.1 关系图的定位

轴关系图不是 UI 图表，也不是运行时随机生成的动作。它是当前 Live2D 模型的一个可版本化能力 profile，描述：

- 每个轴的中性值、范围和语义等级锚点。
- 轴之间的影响方向和系数。
- 头部、身体、视线和表情之间的关系。
- 哪些轴可以派生，哪些轴只能由输入直接控制。
- 哪些参数存在互斥、比例限制或资源冲突。
- 约束的优先级和所有权。

建议将它称为 `SemanticAxisRelationGraph`，以区别于最终的 Live2D 参数计划。

### 2.2 两条处理分支

```text
raw effect arguments
        |
        v
strict validation
   |             |
 rejected        accepted
   |             |
 Motion         value resolver
 Feedback           |
   |                v
 graph diagnostic  direct axis values
 overlay           + derived candidates
                    |
                    v
             SemanticAxisRelationGraph
                    |
                    v
             constrained final values
                    |
                    v
             engine.parameter_plan.v2
```

失败分支不会向关系图注入伪造的数值。它只把被拒绝的字段、失败原因和对应轴显示在同一张诊断图上，便于观察“为什么没有进入计算”。

成功分支才会进入数值处理和图计算。这样既能在同一张图上观察成功与失败，也不会用诊断数据污染播放输入。

### 2.3 校验阶段

校验阶段只回答“这份输入能否进入计算”，不负责生成动作。

校验项目：

1. `contract_version` 和 schema 是否支持。
2. `turn_id`、`message_id` 是否完整。
3. `intent_tags` 是否满足最小要求。
4. 轴名是否存在于当前 profile。
5. 轴值是否为有限数字，或是否为合法的 `axis_levels`。
6. 资源 ID 是否来自当前模型白名单。
7. 是否存在重复 effect。
8. 当前 profile 的 `model_id`、revision 和 hash 是否匹配。
9. 是否存在空动作、全中性动作或没有任何有效轴。

输出建议：

```json
{
  "status": "accepted",
  "turn_id": "turn-123",
  "message_id": "segment-001",
  "rejected_fields": [],
  "warnings": [],
  "feedback": []
}
```

失败时 `status` 为 `rejected`，并携带稳定的 `reason_code`。失败结果不能被转换为默认 pose。

### 2.4 值处理阶段

值处理阶段把已通过校验的输入变成关系图可消费的轴值向量。

当前 `engine.motion_intent.v3` 的连续 `axes` 可以继续作为过渡输入。七级迁移后，推荐使用：

```json
{
  "intent_tags": ["轻微调侃", "疑惑"],
  "axis_levels": {
    "head_yaw": -1,
    "body_yaw": 0,
    "brow_bias": 1
  }
}
```

值处理顺序：

1. 保留原始 effect arguments。
2. 把 `axis_levels` 根据当前 profile 的锚点转换成轴值。
3. 如果仍处于过渡期，直接规范化现有 `axes`。
4. 标记每个轴是直接输入、补充输入还是派生候选。
5. 将结果送入关系图，不在入口层提前执行第二套关系计算。

### 2.5 关系图数据结构

关系图应当是 profile 的一部分，并拥有独立版本和 hash。概念结构如下：

```json
{
  "schema_version": "ag99.semantic_axis_relation_graph.v1",
  "profile_id": "mk6.semantic.v1",
  "profile_revision": 4,
  "profile_hash": "sha256:...",
  "nodes": [
    {
      "axis_id": "head_yaw",
      "neutral": 50,
      "value_range": [0, 100],
      "role": "primary",
      "owner": "semantic_intent"
    },
    {
      "axis_id": "body_yaw",
      "neutral": 50,
      "value_range": [0, 100],
      "role": "primary",
      "owner": "semantic_intent"
    }
  ],
  "edges": [
    {
      "id": "head_body_yaw_limit",
      "source_axis_id": "head_yaw",
      "target_axis_id": "body_yaw",
      "relation": "bounded_ratio",
      "coefficient": 0.5,
      "max_delta": 12,
      "allow_opposite_direction": true,
      "priority": 100
    }
  ],
  "constraints": [
    {
      "id": "body_yaw_absolute_limit",
      "kind": "range",
      "axis_ids": ["body_yaw"],
      "priority": 100
    }
  ]
}
```

### 2.6 头部和身体的关系

头部和身体允许相反方向，但不能出现两个方向都达到极端值的非自然姿态。

关系图不应强制身体和头部同向，而应使用中性值差量计算：

```text
head_delta = head_value - head_neutral
body_delta = body_value - body_neutral

允许：sign(head_delta) == sign(body_delta)
允许：sign(head_delta) != sign(body_delta)
限制：abs(body_delta) <= body_cap(abs(head_delta), profile)
```

具体约束应由 profile 配置，而不是写死在 Prompt 中。关系图需要记录每次调整：原始头身差量、目标差量、限制系数、最终差量以及调整原因。

### 2.7 关系图在 ModelEngine 中的挂载方式

ModelEngine 已经有 compiler stage registry，因此关系图应作为一个明确的可挂载 stage，而不是继续散落在多个模块：

```text
IntentValidator
  -> AxisResolver
  -> IntensityStage
  -> DerivedCandidateCollection
  -> AxisRelationGraphStage
  -> ModeResolverStage
  -> TimingStage
  -> PlanBuilder
```

其中：

- `AxisResolver` 只负责输入轴识别和基础范围校验。
- `IntensityStage` 只负责整体和单轴强度。
- `DerivedCandidateCollection` 收集 coupling、speech pose、资源层等候选值，不直接覆盖输入。
- `AxisRelationGraphStage` 统一执行轴之间的影响、比例、互斥和最终约束。
- `PlanBuilder` 只负责把最终轴值映射到 Live2D 参数。

后端可以执行协议安全校验，但不能再执行一套和 `AxisRelationGraphStage` 相同的语义耦合。这样既保留后端的输入防线，也避免前后端重复修正。

### 2.8 关系图输出和诊断

关系图每次计算都应输出：

- 直接输入轴值。
- `axis_levels` 到实际值的映射结果。
- 派生候选值。
- 被拒绝或忽略的轴。
- 每条边的实际影响。
- 每条约束的命中情况。
- 被调整的轴及调整前后值。
- 最终输出值。
- 对应的 profile revision、profile hash 和 transform version。

建议统一为 `MotionTransformTrace`：

```json
{
  "source_schema": "ag99live.motion.v2",
  "profile_revision": 4,
  "profile_hash": "sha256:...",
  "raw_arguments": {},
  "axis_levels": {},
  "resolved_axes": {},
  "derived_axes": {},
  "constraint_adjustments": [],
  "compiled_parameters": [],
  "timeline_outcome": {
    "audio": "completed",
    "motion": "completed",
    "lip_sync": "completed"
  }
}
```

Motion Lab 后续应以这份 trace 为主要训练和人工筛选依据，而不是只保存最终的 `axes`。

## 3. 后续计划的优化

本节在第 1 节修复完成后执行。

### 3.1 七级方向强度

将模型输出从连续 `0–100` 改为：

```text
-3 强负方向
-2 中等负方向
-1 轻微负方向
 0 明确回到中性
+1 轻微正方向
+2 中等正方向
+3 强正方向
```

模型负责语义方向和等级选择，adapter 或 ModelEngine 根据 profile 转换为实际轴值。前端短期仍可以继续消费 `engine.motion_intent.v3` 的 `axes`，但 `axis_levels` 必须作为原始动作事实保存下来。

### 3.2 每个模型的等级锚点和确定性转换

每个轴拥有自己的等级锚点，不使用全局固定映射：

```text
axis_value = anchor(axis_id, level, profile_revision)
           + bounded_jitter(seed, axis_id)
```

seed 至少包含：

```text
turn_id + message_id + axis_id + profile_hash + transform_version
```

建议使用稳定 hash，不使用语言运行时不保证稳定的内置 hash。训练数据默认关闭扰动，运行时如果启用扰动，必须同时记录 seed、扰动值和最终值。

头部和身体使用不同锚点和不同限制范围。头身关系仍然在中性差量上计算，不能直接比较两个绝对 `0–100` 数字。

### 3.3 Prompt 压缩和三层边界

保留三层结构：

- system：任务、选择原则、输出目标。
- capability：当前模型可用轴、七级含义、profile 风格和少量候选信息。
- context：本轮用户文本、助手文本、上一动作关键轴等级和必要的反重复提示。

Prompt 不再重复写完整 JSON 协议、相同轴说明和实现细节。Effect schema 负责结构约束，Prompt 负责语义选择。

### 3.4 删除不必要的实现信息

动作决策文本只需要告诉模型：

- 当前正在控制一个 Live2D 角色。
- 当前有哪些语义轴和每个轴的含义。
- 每个轴如何使用七级方向强度。
- 本轮需要返回哪些动作意图字段。

不应向模型暴露：

- AG99live 内部模块名。
- AstrBot 传输细节。
- WebSocket、client object、middleware 等实现名词。
- 前端 ModelEngine 的内部 stage 名称。

`<@anim>` 兼容链路可以保留自己的传输说明，但不得污染主 effect Prompt。

### 3.5 Few-shot、历史样本和 Motion Lab

样本需要同时记录：

- 原始对话和 effect arguments。
- 原始 `axis_levels`。
- profile id、revision、hash。
- 转换后的轴值。
- 关系图调整前后的值。
- 最终 parameter plan。
- 实际音频、动作、口型终态。
- 人工评价和反馈。

省略轴和显式中性轴必须在样本中保持可区分。否则后续训练会把“未控制该轴”和“要求回到中性”学成同一种标签。

### 3.6 expression 和 motion resource 分层

建议将单一 `resource_id` 演进为明确的资源意图：

```json
{
  "expression_resource_id": "expression.smile",
  "motion_resource_id": "motion.nod"
}
```

但资源不能直接绕过 ModelEngine 或 PlaybackTimeline。每个资源候选需要声明：

- 资源类型。
- 拥有的 Live2D 参数 ID。
- 优先级。
- 可叠加层级。
- 是否允许和语义轴同时播放。
- 冲突时的处理策略。

第一阶段可以采用严格拒绝冲突；后续再增加明确的 additive、overwrite 或 blend 规则。不能只依赖资源名称判断兼容性。

### 3.7 收紧 fallback pose repair

优化后 fallback pose 的职责仅为“有限姿态参考和缺失骨架补充”，不再承担错误恢复：

- 不替换有效输入。
- 不修复非法输入。
- 不把全中性输入变成动作。
- 不产生模型没有请求的强烈情绪。
- 所有补充值都写入 trace。

如果没有有效动作输入，应该明确返回失败或无动作状态，由播放编排器决定是否只播放文本或语音。

### 3.8 统一后处理所有权

目标所有权：

| 层 | 负责内容 |
| --- | --- |
| 主模型 | 文本、intent_tags、方向和七级强度、明确资源意图 |
| Adapter | effect 提取、schema 校验、协议安全检查、segment identity |
| 值处理器 | 七级到轴值的 profile 映射和来源标记 |
| ModelEngine 关系图 stage | 轴之间影响、派生、头身约束、参数冲突和最终约束 |
| ModelEngine PlanBuilder | 语义轴到 Live2D 参数的映射 |
| PlaybackTimeline | 音频、动作、口型的启动时序和统一时钟 |
| Live2D runtime | 逐帧插值、物理、口型采样和最终参数写入 |
| Motion Lab | 原始输入、trace、人工反馈和播放结果记录 |

同一类规则只能有一个主要所有者。其它层最多做输入校验或诊断，不得再次修改同一类值。

### 3.9 其它建议优化

- 为新的 effect 参数增加明确的 contract version，不在主链路长期同时接受 `axes` 和 `axis_levels` 两套语义。
- 为 profile 增加 hash，避免后端生成时和前端播放时使用不同版本的关系图。
- Motion Lab 记录时间点：effect 生成、文本到达、音频到达、音频开始、动作开始、口型开始和各自终态。
- ModelEngine 可以提前编译动作，但真正的播放启动仍由 PlaybackTimeline 决定，避免编译阻塞音频后的动作起播。
- 静态 capability Prompt 按 profile revision 缓存，动态 context 只保留本轮必要信息。
- WAV 如果可以绕过后端缓存直接提供可播放 URL，应单独优化音频首播延迟，不在动作层增加补偿逻辑。

## 4. 实施顺序

### 阶段一：修复当前链路

1. 修复 `resource_id` 传递和协议类型一致性。
2. 收紧 effect 数量和 segment identity。
3. 删除或合并重复的归一化、约束和广播前处理。
4. 清理非法输入和性能曲线的隐式 fallback。
5. 修复 fallback pose 对显式中性轴的替换。
6. 明确文本、音频、动作和 lip-sync 的失败与终态。
7. 统一生成方式和 immediate/final 阶段命名。
8. 增加修复阶段的端到端日志和测试。

### 阶段二：建立关系图基础

1. 定义 `SemanticAxisRelationGraph` profile schema。
2. 为 profile 增加 revision、hash、节点和边定义。
3. 把当前头身约束迁移到关系图规则。
4. 在 ModelEngine registry 中增加关系图 stage。
5. 输出 `MotionTransformTrace`。
6. 用关系图结果替代散落的 coupling 和重复约束。

### 阶段三：优化模型输出和资源能力

1. 引入七级 `axis_levels`。
2. 增加每轴锚点和确定性转换。
3. 压缩 Prompt 和统一 few-shot。
4. 调整历史样本和 Motion Lab 数据结构。
5. 明确 expression/motion resource 所有权和冲突规则。
6. 完成资源统一进入 ModelEngine 与 PlaybackTimeline 的路径。

## 5. 测试与验收

### 单元测试

- 缺失或重复 effect 的拒绝。
- `turn_id + message_id` 不匹配的拒绝。
- `resource_id` 从后端到前端的完整保留。
- 省略轴、显式中性轴、非法轴的差异。
- 头身同向和反向动作的关系图约束。
- 关系图系数、deadzone、max_delta 和范围约束。
- profile revision/hash 不匹配。
- fallback pose 只补充、不替换有效输入。
- 非法性能曲线不再静默改成默认曲线。

### 集成测试

- 主模型文本和 effect_calls 进入同一 segment。
- 文本、音频、动作和 lip-sync 共享同一 Timeline。
- 音频失败不会释放 motion-only。
- lip-sync 失败能够留下明确终态。
- 动作编译失败能够让 required motion sink 失败。
- 资源动作和语义轴动作不会绕过 ModelEngine 或 Timeline。

### 端到端测试

使用真实 AstrBot、真实 Provider 和 Electron/Live2D runtime 验证：

1. 主模型一次生成文本和 `ag99live.motion` effect。
2. 后端记录 raw effect、校验结果和 transform trace。
3. 前端收到同一 `turnId + messageId` 的文本、音频、动作。
4. 音频以真实 audio clock 播放。
5. 动作在音频开始后按策略启动。
6. 口型与音频共享同一播放段。
7. 最终 SessionStore、Timeline 和 Motion Lab 终态一致。
