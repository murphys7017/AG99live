# 协议 ID 契约维护规则

本文记录当前协议 ID 设计结论、运行规则与维护要求。

## 1. 当前结论

当前前后端外部协议使用两类主身份：

- `turn_id`
- `message_id`

其中：

- `turn_id` 是前后端唯一轮次主 ID。
- `message_id` 是 assistant 输出片段 ID。

当前仓库不再维护以下外部协议字段：

- `session_id`
- `orchestration_id`

AstrBot 内部 turn 身份继续存在，但只保留在后端运行时内部，不对前端暴露。

## 2. 设计前提

本设计建立在下面几个稳定事实之上：

- 用户一次输入，会触发一个前端协议 turn。
- 一个协议 turn 可以对应一条或多条 assistant 输出片段。
- `turn_id` 必须在发送文本或语音流之前就已经存在。
- 前端和后端通信只使用前端创建的 `turn_id`。
- AstrBot 返回自己的内部 turn 身份后，后端只建立内部映射，不把它透传给前端。

## 3. 当前身份模型

### 3.1 外部协议

当前外部协议信封只保留：

- `type`
- `version`
- `message_id`
- `turn_id`
- `source`
- `timestamp`
- `payload`

信封形态：

```json
{
  "type": "<消息类型>",
  "version": "v2",
  "message_id": "<非空字符串>",
  "turn_id": "<字符串 | null>",
  "source": "adapter" | "frontend" | "astrbot" | "engine",
  "timestamp": "<ISO 8601 时间戳>",
  "payload": { ... }
}
```

规则：

- 所有交互链路消息默认必须带 `turn_id`。
- 纯 `system.*` 消息允许 `turn_id = null`。
- `message_id` 只用于 segment 级关联。
- `output.text`、`output.audio`、`engine.motion_intent` 必带 `message_id`。

### 3.2 前端

前端当前职责：

- 文本发送前创建新的 `turn_id`。
- 麦克风开始采集前创建新的 `turn_id`。
- 同一段录音的 `input.audio_stream_start`、二进制音频块元数据和 `input.audio_stream_end` 共用该 `turn_id`；旧 `input.raw_audio_data` / `input.mic_audio_end` 兼容路径也必须共用同一段输入 `turn_id`。
- 播放 session、动作过滤、pending queue、completion coordinator、active audio segment 全部只按 `turn_id` 路由。

空轮次规则：

- 前端预创建的 `turn_id` 若最终 dropped、空转写或失败，立即终结。
- 已终结的 `turn_id` 不可复用。

### 3.3 后端

后端当前职责：

- 把前端 `turn_id` 视为外部协议唯一轮次主键。
- 使用 `turn_id` 进行音频缓冲分桶、turn 生命周期广播、输出回传、打断、播放完成归并。
- 内部维护前端 turn 与 AstrBot turn 的双向映射。

后端当前不对前端暴露：

- AstrBot 原生 turn 身份
- `client_uid`
- 任何 `session_id` / `orchestration_id` 形式的外部字段

## 4. 映射模型

当前后端运行时维护独立映射表：

```text
frontend_turn_id <-> astrbot_turn_id
```

映射规则：

- 前端消息进入后，以 `frontend_turn_id` 建立外部轮次上下文。
- 后端拿到 AstrBot 内部 turn 身份后立即绑定映射。
- `interrupt`、`playback_finished`、`turn_finished` 通过映射定位内部 turn。
- 轮次完成、失败、中断、空转写、dropped 后删除映射。

这一层映射属于 adapter runtime 独立职责，不挂在外部协议模型上。

## 5. 当前落地范围

### 5.1 前端

当前前端协议 ID 使用方式：

- 文本输入和麦克风输入都在开始前预创建新的 `turn_id`
- 前端运行态只保留 `turn_id` 轮次语义，不再维护额外的协议编排主键
- `TurnPlaybackSessionStore` 使用单 `turn_id` 模型
- 播放、动作、pending queue、completion coordinator 只按 `turn_id` 工作
- 文本、音频、动作 segment 聚合统一使用 `turn_id + message_id`

### 5.2 后端

当前后端协议 ID 使用方式：

- parser / builder / 协议模型当前只接受和生成 `turn_id` 单轨协议信封
- `SpeechIngressService` 的音频缓冲键是 `turn_id`
- `SessionState` 只保留当前协议 turn 语义
- `TurnCoordinator` 的广播、interrupt、synth_finished、turn_finished 全部只走协议 `turn_id`
- `TurnIdentityMap` 是独立运行时映射表

### 5.3 文档与类型

当前文档与类型：

- WebSocket 协议契约描述 `turn_id` 单轨模型
- 前端协议类型、入站事件、播放状态模型使用同一套身份规则
- 当前活跃文档只描述单轨协议，不保留旧字段并存语义

## 7. 当前运行规则

### 7.1 turn_id 规则

- 文本输入前创建新的 `turn_id`
- 麦克风开始采集前创建新的 `turn_id`
- 一次输入只使用一个 `turn_id`
- 空轮次、dropped、失败 turn 立即终结且不可复用

### 7.2 message_id 规则

- `message_id` 只用于回复片段聚合
- 同一回复片段的 `output.text`、`output.audio`、`engine.motion_intent` 必须能按 `message_id` 对齐
- 一个 turn 下可以有多个 `message_id`

### 7.3 系统消息规则

- 不属于轮次生命周期的纯 `system.*` 消息允许 `turn_id = null`
- 任何新加的交互链路消息默认必须挂到某个 `turn_id`

## 8. 当前验证关注点

协议 ID 相关变更需要持续关注的主路径：

- 文本输入 -> 单段文本输出
- 文本输入 -> 文本 + 音频 + 动作多段输出
- 麦克风输入 -> 多 chunk + mic end -> 转写 -> reply 输出
- dropped / 空转写 / 转写失败的即时清理
- `interrupt`、`synth_finished`、`playback_finished`、`turn_finished` 的轮次闭环
- 动作 payload 晚到但仍属于当前 turn 时的接受与过期过滤

当前维护判断：

- 仓库只维护最新协议。
- 不再引入旧字段兼容层。
- 如果未来再次调整协议 ID 设计，直接修改当前协议与当前文档，不保留双轨过渡叙述。

## 9. 维护规则

- 当前工作文档只描述现在真实成立的协议结构。
- 过时方案、迁移过程和阶段性计划不在仓库中长期保留。
- 新增交互链路消息时，默认先判断它属于哪个 `turn_id`。
- 不允许重新引入 `session_id`、`orchestration_id` 作为外部协议字段。
- 如果 AstrBot 内部 turn 获取点变化，只调整后端映射层，不改变前端协议主键。
