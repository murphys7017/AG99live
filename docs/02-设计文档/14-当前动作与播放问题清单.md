# 当前动作与播放问题清单

本文只记录根据当前源码确认仍然存在的问题，不保留已经修复的历史问题，也不把尚未验证的猜测写成结论。

对应的详细处理方案见 [动作表现优化实施方案](./15-动作表现优化实施方案.md)。

## 1. 当前稳定边界

当前主链路已经收口为：

```text
Persona Effect / official <@anim> wrapper
-> engine.motion_intent.v4
-> output.segment.v3
-> SessionStore 原子提交
-> PlaybackTimeline 统一 segment 时钟与 sink 终态
-> ModelEngine 语义轴编译和模型参数编译
-> engine.parameter_plan.v2
-> ParameterPresentation 逐帧解算
-> Cubism Motion / Expression / Physics
```

以下边界本身没有发现需要推翻的问题：

- 大模型输出 `-4..4` 九级语义轴，而不是直接生成 Live2D 参数值。
- `turn_id + message_id` 是一次输出段的身份，动作不建立第二套消息队列。
- 有音频时，动作、字幕和口型使用同一个 `PlaybackTimeline` 与真实 `HTMLAudioElement` 时钟。
- `ParameterPresentation` 在 Cubism Physics 之前写入头身驱动参数；物理输出参数不进入语义轴计划。
- 非法动作明确失败，不生成默认姿态，也不使用 `<@anim>` 或 speech-only 掩盖正式动作失败。
- Physics 表现倍率只放大末端物理输出，不扩大头部和身体的语义输入范围。

当前阶段的问题已经从“链路能否播放”转向“链路能否持续生成有节奏、有层次、可归因的表演”。

## 2. 已确认的动作表现问题

### 2.1 说话随动仍由四套固定模板主导

源码位置：

- `frontend/src/model-engine/compiler/stages/speechPoseStage.ts`
- `GESTURE_TEMPLATES`
- `PRESET_CHANNELS`
- `buildGestureTrack()`
- `selectGestureChannels()`

当前只有四种 preset：

```text
calm_explain
lively_chat
gentle_support
emphatic
```

每个 preset 都是一组固定的归一化控制点。`buildGestureTrack()` 将同一组控制点按整段 `durationMs` 等比拉伸，再根据 `turnId + messageId + preset + gestureGroup` 只改变一次整体方向。

普通 preset 的通道顺序也基本固定：优先选择 `head_roll`、`head_yaw`，最多两个头部通道，再选择一个身体通道。`emphatic` 才优先使用 `head_pitch`。

这会产生以下结果：

- 短句和长句具有相同的动作结构，只是播放速度不同。
- 同一 preset 内，头部和身体使用同一形状，只依赖 delay 和 amplitude 区分。
- 一段长语音仍然只有少量方向切换，不能随分句增加手势事件。
- 不同语义最终容易收敛到相似的左右摆动或固定点头节奏。

### 2.2 音频 RMS 只缩放幅度，没有表达停顿和重音事件

源码位置：

- `frontend/src/live2d/lipSyncTimelineSink.ts`
- `frontend/src/live2d/WebSDK/src/lappmodel.ts`
- `updateSpeechAudioEnvelope()`
- `resolveSpeechAudioGain()`
- `resolveSemanticBindingFrameTarget()`

当前 `AnalyserNode` 每帧计算 RMS，并产生：

```text
mouthValue
speechEnergyValue
```

`speechEnergyValue` 经 attack/release envelope 后，只作为 `speech_gesture_track` 的幅度乘数。它不会改变控制点数量、停留位置、动作方向或句尾收势。

当前头部增益还包含 `0.32` 的固定下限，身体也有固定下限。即使语音能量接近零，预设轨迹仍会继续以部分幅度执行。因此真实停顿不会自然变成“保持当前重心”，重音也只会放大当前轨迹，而不会触发一次明确的点头或前倾。

### 2.3 普通回复已有自然 sequence 参考，但仍缺少分句时间信息

源码位置：

- `astrbot_plugin_ag99live_adapter/middleware/interaction_motion.py`
- `_build_motion_decision_contract_text()`
- `astrbot_plugin_ag99live_adapter/prompts/motion_selector_examples.py`

当前 Prompt 已允许存在明确姿态转折、重心切换、追问句尾或短时夸张回收的普通回复使用 `motion_steps`。三个必选结构示例分别覆盖解释时左右换重心、疑问句尾侧倾保持、惊讶后缩后部分回收；它们都遵守 V4 的同轴集合约束，并明确禁止按逐词或语音节奏拆步。

这解决了“只有用户明确下动作命令才产生 sequence”的参考偏差，但当前 sequence 仍只表达少数语义姿态事件：

```text
一个 axis_levels 静态语义姿态
或 2 到 4 个 motion_steps 姿态事件
+ SpeechPoseStage 的通用说话轨迹
```

以下时间能力仍然不应交给 Prompt 伪造，必须由后续 segment performance context 和非周期手势规划器完成：

- 把换重心精确对齐到真实转折分句。
- 根据音频重音决定强调动作的触发时间和幅度。
- 在真实停顿处保持当前姿态，而不是继续固定轨迹。
- 根据句子长度和结构决定事件数量。
- 让语义 sequence 与持续说话手势在统一时间轴上组合，而不是互相覆盖。

### 2.4 `motion_steps` 的当前契约限制了动作组合

源码位置：

- `astrbot_plugin_ag99live_adapter/motion/motion_intent.py`
- `normalize_motion_steps()`
- `frontend/src/model-engine/compiler/compileSemanticMotion.ts`
- `frontend/src/model-engine/compiler/compileModelParameterPlan.ts`

当前序列必须满足：

- 只能有 2 到 4 步。
- 每一步必须使用完全相同的轴集合。
- 每步只有 `duration_weight=1..3`，没有步骤语义、保持策略或轴释放策略。
- 缺少显式 semantic axis 的步骤会被参数编译器视为 parameter set mismatch。

这个约束保证了每个 parameter 都能生成闭合 keyframe，但也迫使模型在每一步重复所有轴。它难以自然表达“先转头、再移动视线、最后增加笑容”这种逐步改变控制权的动作。

### 2.5 当前轴关系图只处理静态值关系

源码位置：

- `frontend/src/types/semantic-axis-profile.ts`
- `frontend/src/model-engine/compiler/stages/couplingStage.ts`
- `frontend/src/model-engine/compiler/stages/semanticAxisRelationGraphStage.ts`
- `frontend/src/model-engine/compiler/stages/modelParameterBindingStage.ts`

`ag99.semantic_axis_relation_graph.v1` 当前只有两类边：

```text
derive
bounded_ratio
```

关系图可以从头部轴派生身体轴，并限制头身比例，但它只处理一个姿态或一个序列步骤的静态值。它不能描述：

- 视线先于头部移动。
- 头部先启动、身体延迟跟随。
- 身体在头部停止后继续少量移动。
- 方向反转时身体进行有限反向平衡。
- 不同身体部位使用不同响应速度和收势方式。

`modelParameterBindingStage` 仍使用线性区间映射，把每个语义轴独立转换为模型参数。当前实现还不是完整的“语义轨道输入、关系图计算、模型轨道输出”。

### 2.6 ParameterPresentation 的运动过于干净

源码位置：

- `frontend/src/live2d/WebSDK/src/parameterpresentation.ts`
- `advanceParameterDynamics()`
- `resolveTrajectoryEnvelope()`

当前逐帧解算使用最大速度和最大加速度计算期望速度。越过目标时直接落到目标值并把速度归零；接近目标时也会精确归零。

它解决了跳变、过冲失控和帧率差异，但视觉上会表现为：

- 每个轴都以相似的“启动、制动、准确停住”方式运动。
- 头部和身体只有速度数值差异，没有不同的重量感。
- 方向反转没有独立的迟疑和惯性阶段。
- 语义动作结束后缺少受控的少量残留。

这不是 Cubism Physics 的问题。它发生在头部、身体、视线等主动驱动参数上，而 Physics 负责的是头发、衣服和饰品等被动响应。

### 2.7 Cubism Physics 目前只有一个全局末端倍率

源码位置：

- `frontend/src/live2d/WebSDK/Framework/src/physics/cubismphysics.ts`
- `setTerminalOutputResponseScale()`
- `updateOutputParameterValue()`
- `frontend/src/live2d/WebSDK/src/lappmodel.ts`
- `frontend/src/live2d-renderer/settings.ts`

当前 `physicsResponseScale` 只放大 Physics 对末端输出 parameter 造成的变化。被其他 Physics setting 继续作为输入的中间 parameter 不会被放大，这个边界是合理的。

但当前设置不能改变：

- 某一组头发、衣服或饰品的独立倍率。
- 粒子的 `Mobility`、`Delay`、`Acceleration` 和 `Radius`。
- 不同 Physics setting 的响应速度和残留时间。
- 模型实际输入幅度在 Physics 级联中从哪里开始衰减。

当前扫描只确认 Physics 文件和相关参数存在，没有形成可观测的 Physics 输入、setting、粒子和末端输出关系图。因此把全局倍率从 1 拉到 2，只能说明末端输出被放大，不能证明物理解算本身更自然。

### 2.8 Motion Lab 数据尚未真正形成生成闭环

源码位置：

- `frontend/src/playback-integrations/useMotionPlaybackRecorder.ts`
- `frontend/src/components/MotionTuningPanel.vue`
- `astrbot_plugin_ag99live_adapter/runtime/motion_state/tuning_store.py`
- `astrbot_plugin_ag99live_adapter/prompts/motion_selector_examples.py`
- `astrbot_plugin_ag99live_adapter/middleware/interaction_motion.py`

当前已经能够记录并保存 compiled semantic motion 和 parameter plan，但仍有五个缺口：

1. Motion Lab 编辑草稿仍以单一 `adjustedAxes` 为中心，不能逐步编辑 sequence。
2. 后端把已保存样本投影回 Prompt 时，无论原始动作是否为 sequence，最终都会输出单一 `axis_levels`，序列被压平。
3. 保存样本只有 `assistant_text`，没有按既定产品要求保存紧邻的用户输入与 assistant 输出对。
4. Prompt 用户样本按当前列表前 N 条选取，不根据当前用户输入、语义标签或动作族做相关性选择。
5. `useMotionPlaybackRecorder.ts` 通过 `getLastAssistantText()` 读取全局最后一条助手文本，而不是读取当前 segment 的 canonical text；连续 segment 下，历史动作可能关联到已经切换后的字幕。

动态 Prompt 目前只携带上一动作关键轴，并提示“避免机械复刻”。它无法观察最近数轮动作族分布，因此不能可靠阻止多个回合重复使用同一种头部动作。

## 3. 仍需完成的真实验证

以下内容不能由静态源码或基础输入输出 smoke 证明：

- Mk6 的九级锚点在实际窗口尺寸下是否形成可区分的视觉等级。
- 语义动作与 speech gesture 叠加后是否出现 clipping 或长时间贴边。
- 长音频、短音频、真实停顿、暂停恢复和动作尾部是否保持连续。
- `physicsResponseScale` 对 Mk6 各组头发、衣服和饰品的实际影响。
- 60 FPS 目标下，180 Hz 显示器环境中的真实帧时间和 Physics 稳定性。
- Motion Lab 中保存、重放、终态和 Prompt 引用是否能在同一真实会话中闭环。

## 4. 当前优先级

```text
P0  非周期说话手势与停顿/重音表达
P1  普通对话的语义动作序列与面部/视线层次
P1  主动参数的时间关系图与自然动力学
P2  Physics 输入/输出诊断和模型级调校
P2  Motion Lab sequence 与相关样本检索闭环
```

继续单独放大九级锚点、全局动作强度或 Physics 倍率，不能解决固定模板和时间结构问题，只会让同一种动作摆得更大。
