# 当前动作与播放问题清单

本文只记录当前动作生成、参数编译与播放链路尚未关闭的问题、已确认原因和处理边界；稳定架构以 `01`、`11`、`12`、`13` 号设计文档为准。

## 1. 当前结论

主链路已经成立：Persona Effect 生成 `ag99live.motion`，Adapter 运输原子输出段，前端排队动作意图，并在音频时长可用后编译为参数计划。

最近一次“有音频和口型、没有动作”的直接原因已确认且已修复：旧 sequence compiler 强制动作总时长不得超过音频时长，合法三段动作因最后一段的物理过渡时间不足而整体编译失败。

动作不是音频的从属物。音频提供开始基准与能量信息；动作可以略晚开始，并在音频结束后自然收势。

## 2. 已修复但需要真实链路确认

### 2.1 动作序列被音频长度错误限制

历史失败：

```text
motion_sequence_transition_budget_exceeded:2:471:427
```

第三段按权重只分到 `427ms`，但模型动力学要求至少 `471ms`。旧实现把音频时长当作动作计划硬上限，因而拒绝整个动作。

当前修复：编译器以音频时长为基准，计算每段物理过渡最小要求；不足时延长动作计划，使尾部能在音频结束后继续完成。

仍需真实 Electron + AstrBot 对话验证：三段左右动作应在音频结束后完成回正，不应被音频终态截断，也不应跳帧。

## 3. 必须优先修复的正确性问题

### 3.1 音频结束后的时钟交接可能跳变

`PlaybackTimelineRuntime` 会在音频结束后让未结束的 motion sink 继续运行，这是正确的。但 `TimelineClock` 解除真实 `HTMLAudioElement` 时钟后改用合成时钟，尚未明确从最后一个真实 audio elapsed 值重基准。

风险：播放速率、暂停或浏览器时钟抖动时，动作尾部可能跳变，导致收势突兀。

处理方式：

1. 解除音频时钟时读取并冻结最后一个真实 `currentTime`。
2. 合成延续从该精确 elapsed 值继续，不重新从 `performance.now()` 推导。
3. 时钟来源表达为“音频尾部延续”，不能误记为普通 `motion-only`。

非方案：新建独立动作计时器，或音频结束时强制截断动作。

### 3.2 动作编译失败没有唯一终态所有者

正式 motion payload 到达但编译失败时，pending payload 可能仍保留；重复 audio duration 通知会重复编译和重复记录失败。失败处理也可能由 wiring 与 timeline 分别推进。

风险：同一段重复失败、Motion Lab 重复记录，或 Timeline/SessionStore 留在非终态。

处理方式：

1. 正式 motion payload 编译失败定义为不可恢复的 segment motion failure。
2. 消费对应 pending payload，确保只终态化一次。
3. 只由 Timeline 推进 motion sink 失败终态；其他层只上报编译结果。
4. 严格区分“没有正式 motion payload”和“payload 无效/编译失败”；后者不得转为 speech-only motion。

非方案：默认动作、静默忽略、或将 sequence 重试成单轴姿态。

### 3.3 失败诊断缺少约束来源

当前错误码可表示 step、所需和可用时长，但不能直接指出限制来自哪个 `axis_id` 或 Live2D `parameter_id`。

编译失败与 Motion Lab failure record 应记录：

- `turn_id`、`message_id`、schema 版本、step 数量。
- 失败 stage、稳定 reason、受限 step index。
- 受限 axis/parameter、所需/可用时长、profile id/revision、model id。
- 已执行约束与变换轨迹摘要。

这只增强诊断，不改变有效动作结果。

### 3.4 `system.group_update` 的协议分类不清晰

前端曾将 `system.group_update` 记录为未处理消息。它尚未证明造成动作故障，但会污染排障信号。

应沿 protocol manifest 确认它是必须消费的业务消息还是可忽略系统通知：前者实现唯一处理者，后者在协议层显式分类为可忽略，不再记录为未处理。

### 3.5 无法播放调试动作

已确认根因：动作实验室从历史记录或参考动作生成 v3 preview intent 时，把 profile 中全部可控轴写入 `axes`，包括大量没有参与当前动作的中性轴。严格 compiler 会把每个出现的轴视为本次显式控制目标，导致无关轴扩大参数冲突面，也可能触发全中性或重复参数绑定失败。

处理方式：

1. 历史动作的显式轴只读取 compiler `transformTrace.rawAxes/rawAxisLevels`，不从最终 parameter plan 反推模型输入。
2. 可编辑实际值从 `constrainedAxes` 按显式轴键提取；coupling、speech pose 和 continuity 派生轴不会混入模型原始输入。
3. 用户手动操作过的轴加入显式轴集合，因此主动调回中性仍会输出中性值。
4. 缺少 transform trace 或属于多步骤 sequence 的记录明确标记为不可编辑，不生成兼容预览。
5. 保存参考动作时沿用同一稀疏轴集合，不再继续积累全轴样本。
6. 主运行时只有在本地 ModelEngine 接受并启动 preview 后才向 Adapter 记录 ingress；本地失败时输出 compiler reason 与 diagnostics，并停止发送。

后端日志中的空 `turn_id` 是 preview 协议的正常行为。修复后，下列日志表示本地预览已经启动并完成了后端登记，而不是只表示按钮被点击：

```text
[15:09:35.629] [Core] [INFO] [runtime.turn_coordinator:891]: WIRING motion_payload_ingress type=engine.motion_intent mode=preview turn_id= plan_schema=engine.motion_intent.v3 plan_mode=expressive axis_count=17 supplementary_count=0 failure_reason=
```

### 3.7 声音播放有卡顿，疑似原因为进行了分片处理

代码核查结论：AG99 前端没有把一个 WAV 分片播放。每个 `output.segment` 创建一个 `HTMLAudioElement`，并使用一个完整音频 URL。Adapter 也拒绝同一 segment 携带多个音频文件。

但 AstrBot 的普通 Pipeline 和 Interaction Core/Final 输出允许 segmented reply，并会对拆分后的每个 `Plain` 分别调用 TTS。多个逻辑音频段到达 AG99 后，会依次创建不同的 `HTMLAudioElement`；每段都要重新加载 metadata 并调用 `play()`，段间可能出现可听停顿。

因此当前应把问题表述为“多个 TTS 逻辑段之间存在播放间隙”，而不是“单个 WAV 被前端分片”。下一步需要用同一轮日志核对：

- AstrBot 是否为一句回复发起多次 `synthesize_text`。
- Adapter 是否发出多个不同 `message_id` 的 audio-present segment。
- 前端相邻段 `audio ended` 到下一段 `playing` 的实际间隔。

该问题的根因策略应优先放在 AstrBot 输出策略：AG99 桌面语音输出不启用 segmented reply，整段文本只合成一个 WAV。前端预加载下一段只能优化无法合并的多段业务输出，不能替代上游单段语音契约。

#### 3.7.1 输出分段策略缺少独立能力边界

当前 `allow_segmented_reply` 同时影响文本分段、TTS 分段和组件交付，无法表达不同平台的真实需求。这里需要区分三个策略：

```text
text_segmentation       可见文本是否按标点拆分
tts_segmentation        整段文本一次合成，或每个文本段分别合成
component_delivery      组件整体交付，或按组件/逻辑段交付
```

AG99Live 的目标策略是：同一个逻辑回复段只生成一个 WAV；`immediate_reply`、`final_reply` 等本来就独立的业务段仍分别保留。该策略应由 AstrBot 的统一输出交付层声明或传递，不能在 AG99 前端合并音频，也不能在 Adapter 中按平台名称硬编码特例。

这属于 AstrBot 输出策略边界问题，不改变 AG99 的 `output.segment` 协议和 Timeline 播放模型。


## 4. 已确认的表现质量问题

### 4.1 日常对话过度点头

这不是模型没有横向能力：Mk6 支持 `ParamAngleX/Y/Z`，映射也包含 yaw、pitch、roll。根因是多层偏置叠加：

- 默认 few-shot 与 Prompt 对 `head_pitch`、点头语义样本偏多。
- profile 建议普通说话保持 `head_yaw` 接近中性。
- `SpeechPoseStage` 为全部 audio-backed segment 叠加说话手势，`head_pitch` 在 calm、gentle、emphatic 中优先级偏高。
- 通用正负模板应用在 pitch 上，天然形成连续点头。
- 变化检测只关注 `head_yaw`、`body_yaw`，无法发现 pitch 重复。
- `gaze_y -> head_pitch` 的关系派生会进一步增加纵向运动。

点头应保留给确认、强调、句尾收束或明确的垂直语义。日常亲近、俏皮、开心回复应更偏向可读的横向重心变化。

建议方向：

1. Prompt 只写选择原则：日常亲近、调侃、开心时优先短暂侧倾、横向重心变化和自然回正；垂直头部运动只用于确认、强调、句尾或明确垂直语义。
2. `SpeechPoseStage` 按轴族使用不同曲线：pitch 只作稀疏单次强调；roll/yaw 使用保持、偏移、缓慢回收的非周期片段；身体更小且稍后跟随；视线独立变化。
3. 变化检测扩展至 `head_pitch`、`head_roll` 和主要身体轴，避免同类动作连续重复。
4. 不无限扩张示例；先由 Motion Lab 积累真实数据，再人工筛选少量高质量动作参考。

可爱左右摆动优先是 `head_roll + body_roll` 的重心转移，不应主要使用 `head_yaw`，否则容易读成否定式摇头或单纯侧看。

### 4.2 头身与 Live2D 物理反馈不足

角色动作偏“干净”，头发、衣物等缺少物理残留。语义参数计划只决定姿态目标，不能替代 Cubism Physics 的滞后和弹性。

当前代码确认：Mk6 声明并加载 `Mk6.physics3.json`，文件包含 92 个 PhysicsSetting；`LAppModel.update()` 先执行直接参数计划，再调用 `this._physics.evaluate(this._model, deltaTimeSeconds)`，最后调用 `this._model.update()`。因此“完全没有物理组件”尚未成立。

进一步静态核查确认：仓库与实际 AstrBot 部署目录中的 `Mk6.physics3.json` SHA-256 一致；其中头发占 21 组、48 个输出，衣物及饰品占 14 组、28 个输出。侧发、长发和领带均使用多粒子链，输出权重为 100，缩放值也没有表现出统一偏低。正式 semantic profile 的 primary/hint 参数与 Physics 输出参数没有交集，因此 ModelEngine 不会直接覆盖 `PhyHair*`、`PhyClothing*` 等结果；头身、视线和部分面部参数则确实作为 Physics 输入。

Physics SDK 使用模型声明的 60Hz 固定步长，在每帧 `deltaTimeSeconds` 上累积并插值。当前主循环正常更新该时间值，未发现物理被跳过或执行顺序错误的静态证据。

仍需确认的根因边界是：

1. 真实动作播放时 `ParamAngle*`、`ParamBodyAngle*`、`BodyAngleY` 的实际变化幅度和速度是否足够。
2. 级联生成的 `PhyAngle*`、`PhyBody*` 是否已经明显衰减，导致末端 `PhyHair*`、`PhyClothing*` 肉眼不可见。
3. 实际渲染帧率和 `deltaTimeSeconds` 是否稳定，是否存在后台限帧或长帧重置 Physics 累积时间。
4. 当前服装显示状态是否正好使用了具备这些 Physics 输出绑定的 ArtMesh。

下一步应基于实际 Physics 输入/输出绑定和一帧内参数读写记录定位，不应先新增随机摆动或 fallback 运动来伪造物理效果。此项属于表现质量问题，不应改变语义动作与播放协议的所有权。

系统设置现提供 `physicsResponseScale`（默认 `1.0`，范围 `0.5–2.0`）。Cubism 先按原始输出缩放、权重和范围得到本帧正常 Physics 结果，再围绕进入 Physics 前的参数值放大实际变化量：`before + (normal - before) * scale`。只有不再作为其他 Physics 输入的末端输出应用倍率，`PhyAngle*`、`PhyBody*` 等级联中间参数保持模型原始结果，因此倍率不会扩大语义头身输入，也不会移动非零参数基准。该设置用于真实观察模型既有物理表现，不替代上述运行时参数诊断。

`motionIntensityScale` 只属于 ModelEngine；`physicsResponseScale`、`renderDprCap` 和 `ambientMotionEnabled` 统一属于 `Live2dPresentationSettings`。renderer 在模型初始化前应用该配置，运行期通过 WebSDK Adapter 原子更新，不再使用定时轮询等待 Adapter。

为对照 VTube Studio 的物理流畅度，WebSDK 前台与后台渲染目标帧率暂时统一提升到 60 FPS。此阶段不启用动态降帧，先通过真实运行观察 GPU/CPU 占用、帧时间和物理连续性，再决定待机与隐藏窗口的节能策略。

## 5. 已确定的播放时序目标

```text
预开口
  -> 音频开始，真实 lip sync 跟随音频
  -> 动作略晚启动
  -> 音频结束
  -> 动作自然收势并完成
```

- 预开口是短暂 anticipatory mouth pose，不是把 RMS 口型整体提前；真实口型仍绑定 `HTMLAudioElement` 实际播放。
- 动作延迟属于 Timeline 的段内计划，不能散落为 `setTimeout`。
- 动作尾部是同一个计划的自然延续，不是第二条播放链路。
- Performance Curve 是可选的单次弹出增强，可失败或晚到；音频与正式动作已具备时，绝不能阻塞输出段、音频或基础动作。

## 6. Motion Lab 与参考数据

手动保存的参考动作应携带极短对话上下文：

```json
{
  "dialogue_context": [
    { "role": "user", "text": "当前用户输入" },
    { "role": "assistant", "text": "本段 spoken_reply" }
  ]
}
```

最多保留紧邻的一组上一轮输入/输出，总计不超过四行。不得保存 system prompt、完整历史、工具调用、内部标签、截图、音频 URL/路径或完整协议 payload。

参考记录还应保留原始 `axis_levels/motion_steps`、转换后轴值、约束后值、最终 parameter plan、profile/model 版本和人工标签，以便比较模型原意与最终表现。

## 7. 排查与验收原则

自动测试通过不是播放链路正确性的证明。最小输入输出 smoke 只用于边界防回归；动作、音频、口型和尾部时序必须通过真实 AstrBot + TTS + Electron + Live2D 对话日志验证。

排查顺序：

```text
Persona Effect 生成
-> Adapter 解析与原子输出段
-> 前端协议解析与 SessionStore 提交
-> Motion payload 排队
-> audio duration 到达后的动作编译
-> Timeline 启动与真实 audio clock
-> Live2D plan 逐帧执行
-> motion / lip-sync / audio sink 终态
```

禁止用默认姿态、伪造音频时钟、隐式 speech-only 降级或吞掉 lifecycle 错误来让链路看似可用。错误必须在真实所有者处显式终态化，并携带可定位诊断。

## 8. 建议执行顺序

1. 修复音频时钟到动作尾部的无跳变交接。
2. 收口动作编译失败的唯一终态所有权与 pending payload 消费。
3. 补全 compiler/Motion Lab 的约束来源诊断，并处理 `system.group_update` 的协议分类。
4. 实测 sequence、音频尾部、口型、动作延迟和中断场景。
5. 调整 Prompt 与 `SpeechPoseStage` 的轴族选择，降低日常点头偏置。
6. 为手动参考动作加入短对话上下文，开始积累而非扩张示例。
7. 单独评估 Cubism Physics、头发和衣物的更新链路。
