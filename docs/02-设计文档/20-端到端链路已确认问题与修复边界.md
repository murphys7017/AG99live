# 端到端链路已确认问题与修复边界

本文只记录当前源码审阅中已经确认、尚未修复的问题。它不是历史审计记录，也不改变
[一期完成边界与二期入口](../01-架构与结构/06-一期完成边界与二期入口.md) 对产品阶段的定义。
问题修复并完成源码复核后，应直接删除对应条目，不保留旧实现或迁移过程。
表演质量优化方向与实施顺序统一记录在
[二期角色表演系统总体规划](./18-二期角色表演系统总体规划.md)，不在本清单重复维护。

## 1. 当前结论

增强版主链路仍保持统一：

```text
AstrBot
-> Adapter output.segment.v3
-> TurnPlaybackSessionStore
-> PlaybackTimeline
-> ModelEngine
-> engine.parameter_plan.v3
-> ParameterPresentation
-> ActiveParameterMixer
-> Cubism Physics / model.update / draw
```

正式主链路的所有权仍然统一，没有发现需要推倒 SessionStore、PlaybackTimeline、ModelEngine、
ParameterMixer 或 WebSDK 分层的结构错误。但失败路径、异步启动和终态处理存在能够造成 Turn 挂起、
连接关闭或动作误拒的高优先级缺陷。以下问题均应按根因修改现有所有者，不新增旁路或 fallback。

## 2. 已确认问题

### R1 官方兼容模式没有 Remote Operator 完整闭环

源码事实：

- `astrbot_plugin_ag99live_adapter/main.py` 的 `on_llm_request` 在官方兼容分支注入
  `<@anim>` Prompt 后直接返回，因此不执行 Remote Operator 工具仲裁。
- `astrbot_plugin_ag99live_adapter/middleware/__init__.py` 只有在 Interaction contributor
  能力存在时才注册 Remote Operator prompt/result contributor。
- 官方兼容模式正是 contributor 能力不存在的分支，因此它同时缺少 Remote Operator result
  解析和任务调度，不能只通过移除一个 `return` 修复。

影响：官方 AstrBot 环境中，远程操作请求不会进入当前文档描述的完整委托链路；如果简单同时
注入动作 Prompt 与 Remote Operator 严格 JSON Prompt，还会制造彼此冲突的输出契约。

根因修复边界：必须先明确官方兼容模式是否承诺 Remote Operator。若不承诺，应在配置、README
和运行日志中明确能力边界；若承诺，则需提供与官方生命周期一致的 request/result 闭环，而不是
在动作兼容 Hook 上叠加局部补丁。

验收标准：官方模式对 Remote Operator 的支持状态唯一且可观察，不再出现“配置存在但运行链路
不可达”，也不存在动作标签与严格 JSON 同轮竞争。

### R2 已关闭输出队列仍接受迟到 Segment

源码事实：

- `TurnCoordinator.emit_message_chain()` 在合并输出前不检查 Turn 是否位于
  `_closing_output_turn_ids` 或 `_closed_output_turn_ids`。
- `_get_pending_output_segment()` 因而可以在队列关闭后重新创建 pending segment。
- `close_turn_output_queue()` 对 closed Turn 直接返回，不会再次 flush 新建的 segment。
- `_finish_turn()` 最终直接移除这些 pending segment。

影响：AstrBot 或插件的迟到输出会被接受进内存，却既不发送也不立即报错，最终静默丢失。这与
项目的 fail-visible 原则相反，也会把上游生命周期错误伪装成“前端没有显示回复”。

根因修复边界：输出队列状态必须成为 `emit_message_chain()` 的入口不变量。closing 或 closed 后的
输出应立即以明确原因拒绝，不能重新开放队列、补发 Segment 或在 `_finish_turn()` 中静默清理。

验收标准：队列关闭后任何迟到输出都会在产生位置显式失败；正常输出仍按
`output.segment.v3 -> control.synth_finished` 顺序一次性关闭。

### R3 动作规范化失败原因在前端边界丢失

源码事实：

- `frontend/src/model-engine/normalize.ts` 返回 `{ ok: false, reason }`，能够给出具体 schema、字段
  或值域错误。
- `frontend/src/playback-integrations/motionPayload.ts`、`inboundDispatcher.ts` 和
  `inboundOutputDispatcher.ts` 把失败类型收窄成 `{ ok: false }`。
- `inboundOutputDispatcher.ts` 最终只抛出通用的 `output_segment_motion_invalid:<message_id>`；连接层
  随后按致命入站错误关闭 WebSocket。

影响：系统执行了严格拒绝，但把最重要的根因丢在类型边界之外，日志和 UI 只能看到泛化错误，
难以判断是版本、资源、轴、sequence 还是字段结构问题。

根因修复边界：统一使用带 `reason` 的规范化结果契约，并把该原因包含进协议错误、连接错误和
Motion Lab 诊断。不能通过再次解析 payload 或增加第二套错误映射补偿。

验收标准：同一拒绝原因从 ModelEngine normalization 一直传递到连接诊断，且非法动作仍不会进入
SessionStore 或触发播放 fallback。

### R4 官方输出完成存在两个所有者

源码事实：

- 插件 `after_message_sent` Hook 主动调用 `event.complete_visible_turn()`。
- AstrBot `TurnDeliveryCoordinator.complete_visible_delivery()` 在 Hook 返回后再次调用同一完成入口。
- Adapter 当前依靠 `close_turn_output_queue()` 的幂等集合吸收第二次调用。

影响：当前通常不会产生重复 Segment，但输出完成所有权不唯一。幂等保护正在掩盖重复调用，后续
关闭失败、并发调用或生命周期调整时会增加状态判断复杂度。

根因修复边界：以目标 AstrBot 版本的 `TurnDeliveryCoordinator` 为唯一完成调用者；插件只提供平台
事件的 `complete_visible_turn()` 实现。若仍需兼容不具备该协调器的版本，应通过明确版本能力边界
决定，而不是让两个路径长期共同调用。

验收标准：每个 Turn 只有一个调用链负责触发输出队列关闭，幂等只防重复外部信号，不再承担正常
流程的权责协调。

### R5 `NormalizedMotionPayload` 的目录所有权反向

源码事实：

- 类型定义当前位于 `frontend/src/playback-integrations/motionPayload.ts`。
- ModelEngine `contracts.ts` 反向导出该类型。
- TurnPlayback、AdapterConnection 和 ModelEngine 都依赖它，而 Playback Integration 本身又依赖
  ModelEngine contracts/runtime contracts。

影响：当前依赖是 type-only，尚未形成运行时循环，但目录语义与真实所有权相反。继续扩展字段时，
容易形成 ModelEngine 与 Integration 互相定义契约的局部最优。

根因修复边界：将 `NormalizedMotionPayload` 与 normalization result 移到中立的前端动作契约模块，
例如 `frontend/src/types/motion.ts`；ModelEngine、TurnPlayback、AdapterConnection 和 Integration
只能共同消费，不再互相转发定义。

验收标准：`model-engine/` 不导入 `playback-integrations/`，Integration 也不拥有跨层共享动作 DTO。

### R6 共享运行时类型反向依赖 WebSDK 实现

源码事实：

- `frontend/src/types/live2d-runtime.d.ts` 直接从
  `frontend/src/live2d/WebSDK/src/directparameterplan.ts` 导入 Direct Plan 输入、启动选项和终态类型。
- `directparameterplan.ts` 同时包含共享 DTO 和 WebSDK 执行准备函数。

影响：应用共享类型层依赖最低层 SDK 实现目录，使 WebSDK 文件位置和实现拆分变成上层编译契约。

根因修复边界：把 Direct Plan 执行接口 DTO 移到中立类型模块；WebSDK 的
`prepareDirectParameterExecution()` 继续留在实现层，并消费同一 DTO。不得复制两套结构相同的类型。

验收标准：`frontend/src/types/` 不再导入 `live2d/WebSDK/src/`，WebSDK 与上层通过唯一共享契约连接。

### R7 动作启动入口保留 catalog fallback

源码事实：

- `startNormalizedMotionPayload()` 已分别处理 `semantic_intent` 和 `catalog_motion`。
- 最后的未知分支仍调用 `startCatalogMotionPayload()`，语义上把未知 payload 当成 catalog motion。

影响：当前联合类型下该分支不可达，但它表达了错误的未来行为，并可能在类型逃逸或协议扩展时把
schema 漂移误导为 catalog 执行错误。

根因修复边界：使用显式穷尽检查并报告未知 `kind`，不推断、不转换、不启动其他动作类型。

验收标准：增加新的 normalized payload kind 时，编译期必须要求调用方显式实现；运行时未知 kind
必须得到准确拒绝原因。

### R8 零 Segment Turn 缺少失败终态

源码事实：

- `TurnCoordinator.close_turn_output_queue()` 在既没有 pending segment、也没有已发送 segment 时抛出
  `output_segment_missing:<turn_id>`。
- `OLVPetPlatformEvent.complete_visible_turn()` 直接等待该关闭操作，没有把关闭失败转换为该 Turn 的
  `control.error` 与失败 `control.turn_finished`。
- 前端已经收到 `control.turn_started`，却收不到 `output.segment`、`control.synth_finished` 或明确失败终态。

影响：无可见输出、上游生成异常或错误完成路径可能留下永久非终态 Turn，并阻塞依赖旧 Session 收口的
后续观察与诊断。

根因修复边界：Turn 输出关闭必须是一个能够发布成功或失败结果的事务。零 Segment 仍应显式失败，但失败
必须回传给前端并清理该 Turn，不能只在 AstrBot 调用栈内抛异常，也不能伪造空 Segment。

验收标准：零 Segment 收口会产生唯一、可观察的失败终态；正常 Turn 仍严格保持
`output.segment -> synth_finished -> playback_finished -> turn_finished`。

### R9 断连清理可被单个 Event 中断

源码事实：

- `reset_turn_tracking()` 顺序停止 `_events_by_turn_id` 中的活动 Event。
- 任一 Event 缺少 `set_extra`、缺少 `stop_event`，或调用自身抛错时，函数立即终止。
- `platform_adapter._handle_transport_disconnect()` 因而不会继续执行 SessionState、TurnIdentityMap、音频流
  和媒体缓冲清理。

影响：一次防御性异常可能把连接级状态带入下一次重连，使断连清理的失败范围大于原始 Event。

根因修复边界：逐 Event 停止需要独立诊断；连接级状态清理必须在确定执行的收尾路径中完成。这里的
best-effort 只适用于资源释放，不能吞掉诊断，也不能让旧状态继续存活。

验收标准：单个 Event 停止失败会留下明确日志，但其余 Event、Turn、身份映射和音频资源仍全部清理。

### R10 TurnIdentityMap 存在反向死查询

源码事实：

- `_resolve_frontend_turn_id()` 接收前端 Turn ID，却调用按 AstrBot Turn ID 索引的
  `resolve_frontend_turn()`。
- 查询通常返回 `None`，随后依靠 `resolved or normalized` 返回原始 ID。
- 当前调用者本来就传入前端 ID，因此生产行为主要依赖回落值，而不是身份映射。

影响：当前不是直接故障，但这段代码掩盖了身份映射真实使用方向，并让未来调用者误以为发生了有效转换。

根因修复边界：按调用边界删除无意义查询，或把 API 改成明确接收后端 ID 后再执行反向解析；不能保留
“错误查询失败后刚好返回正确原值”的结构。

验收标准：每个身份解析函数的输入方向由名称和调用者共同保证，不存在依赖回落值成立的正常路径。

### R11 未开始输入 Turn 收到 `turn_finished`

源码事实：

- SpeechIngress 在 dropped、空音频、转写失败、空转写或转写过滤时调用 `_emit_terminal_turn_signal()`。
- 该函数同时发送 `control.error` 和失败 `control.turn_finished`。
- 这些输入 Turn 或 VAD 子 Turn 只有转写成功并提交 AstrBot 时才会先发送 `control.turn_started`。

影响：前端收到未知 Session 的 `turn_finished`，只能记录协议生命周期违规；错误本身可见，但终态语义
不自洽。

根因修复边界：尚未进入正式 Turn 生命周期的输入失败只发布输入错误；如果产品希望这些输入也成为 Turn，
则必须先统一发送 `turn_started` 并让它们完整进入同一状态机，不能只补一个终态。

验收标准：任何 `turn_finished` 都能对应同连接内先前已开始的 Turn；转写前失败仍有明确错误信息。

### R12 后端 Turn 完成不是幂等的

源码事实：

- `finalize_turn()` 每次收到 `control.playback_finished` 都调用 `_finish_turn()`。
- `_finish_turn()` 发送 `control.turn_finished` 后清理映射和集合，但没有保留已完成标记用于识别重复信号。
- 第二次相同 `playback_finished` 会再次使用原始前端 ID 并再次发送终态。

影响：当前正常前端通常只发送一次，但重复事件会制造两个后端终态并模糊真正的生命周期错误来源。

根因修复边界：完成入口需要明确的 keep-first 语义和重复诊断；不能重新执行清理，也不能静默把第二次
完成当成新的有效完成。

验收标准：同一 Turn 的首个完成结果唯一生效，重复完成只产生诊断，不重复广播终态。

### R13 段级拒绝错误关闭整个连接

源码事实：

- `inboundOutputDispatcher.applyOutputSegment()` 在 motion normalization 失败或音频 URL 无效时抛异常。
- 异常传播到 `useAdapterConnection` 的 fatal inbound handler，后者停止全部 Timeline、失败所有未收口
  Session 并关闭 WebSocket。
- 当前设计文档只要求非法 `output.segment` 零副作用拒绝；只有破坏连接一致性的错误才应关闭连接。

影响：单个回复段的字段错误会扩大成全局连接故障，影响其他 Turn，并把真正的段级拒绝原因埋在断连后果中。

根因修复边界：输出段应用边界必须返回带原因的接受/拒绝结果；段级错误只拒绝该段并记录协议诊断，
连接级基础设施缺失或无法继续解析的信封错误才进入 fatal handler。R3 的精确 normalization reason 应在
同一修改中贯通，不能新增第二套错误转换器。

验收标准：非法 motion/audio 段不写 SessionStore、不启动播放且连接保持；真正 fatal 的入站运行时错误
仍会关闭连接。

### R14 终态冲突处理与文档不一致

源码事实：

- `useTurnPlaybackSessionStore.rejectTerminalRewrite()` 对不同终态的二次写入直接抛异常。
- 多个调用点位于音频、动作和 Timeline 的异步回调边界。
- 当前权威文档要求“保持首个终态并记录诊断”。

影响：上游重复或竞态信号没有改写既有事实，却可能以未捕获异常扩大为播放管线故障。

根因修复边界：SessionStore 应保留首个终态，拒绝后续改写并把冲突交给统一诊断入口；不能悄悄覆盖，
也不能用 catch 包裹每个调用点。

验收标准：终态冲突不会改变首个事实、不会抛出到异步事件循环，并能定位 material、旧终态和新终态。

### R15 catalog motion 异步接受被同步误拒

源码事实：

- `startCatalogMotionPayload()` 和 `startMotionResourcePayload()` 在 `playCatalogMotion()` 返回后立即检查
  `notifiedStarted`。
- WebSDK 对未缓存 Motion 返回 `AsyncMotionAcceptedHandle`，随后异步 fetch，真正开始后才调用 `onStarted`。
- 上层因此先执行 `motion_start_without_run_id` 拒绝，而底层 Motion 稍后仍可能实际启动。

影响：Timeline 认为动作失败，Live2D 却开始播放，`run_id`、required sink 和真实模型状态彼此分裂。

根因修复边界：catalog motion 启动契约必须区分“同步拒绝”“异步已接受”“已实际开始”。接受异步请求后
保持 preparing，只有 `onStarted` 才创建 run；异步失败通过现有终态回调返回，不能设置超时动作或默认动作兜底。

验收标准：缓存与未缓存 Motion 都只在真实开始时发布唯一 run；fetch/load/start 失败均得到准确终态，
不存在先拒绝后播放。

### R16 短 idle timing 超出声明预算

源码事实：

- idle 默认 timing 固定使用 `blend_in=80ms`、`blend_out=120ms`，同时把 hold 下限设为 `220ms`。
- 当同步音频时长小于 `420ms` 时，三者之和大于 `duration_ms`。
- 后续执行层可能扩展总时长以容纳三段，从而让动作尾部超过音频声明预算。

影响：极短回复或 speech-only 计划会出现动作拖尾、终态等待增加，时间事实不再唯一。

根因修复边界：同一 timing 解析函数必须在短时长下按比例或按优先级压缩 blend/hold，并保证各段总和不
超过 `duration_ms`；不能让执行层再次修正编译器输出。

验收标准：所有合法时长都满足 `blend_in + hold + blend_out <= duration_ms`，短音频仍能平滑起止。

### R17 重复 pending motion 双向丢失

源码事实：

- `queueInboundPayload()` 发现相同 Turn/Message 已存在 pending payload 时调用
  `dropPendingPayload(existing, "duplicate_motion_payload")`。
- 随后函数返回 `false`，新 payload 也不会入队。
- 结果是先到的有效负载被删除，后到的重复负载也被拒绝。

影响：一次重复投递会把原本可执行的动作变成无动作，并错误失败原负载对应的 Timeline sink。

根因修复边界：重复语义必须与 SessionStore 的 keep-first 规则一致：保留首个 pending payload，拒绝并
诊断后到负载，不修改原负载状态。

验收标准：重复投递零副作用影响首个负载；首个负载仍能按原 Timeline 启动。

### R18 Parameter Plan 未执行未知字段检查

源码事实：

- `planParser.ts` 对顶层、timing、parameter、keyframe、modulation 和 dynamics 读取已知字段，但未检查
  额外键。
- 拼写错误字段可能被忽略，而同项目 motion intent/profile 边界使用严格字段集合。

影响：当前计划主要由内部编译器产生，因此风险有限；但 schema 漂移或手动预览数据错误可能被静默裁剪。

根因修复边界：在唯一 parser 中按各对象层级执行字段 allow-list 校验，保持准确失败原因，不在 WebSDK
再次实现一套 schema parser。

验收标准：未知字段在进入 WebSDK 前明确失败，合法 V3 计划行为不变。

### R19 零宽输出范围产生冻结动力学

源码事实：

- 后端 Profile、前端编辑器和 model-sync parser 当前允许 `output_range[0] == output_range[1]`。
- Binding Stage 按 output span 计算速度和加速度；零 span 得到零动力学。
- 映射后的 target 也始终为同一个常量，参数无法响应九级语义输入。

影响：错误 Profile 可以正常保存和同步，却在运行时表现为“动作参数完全不动”，难以区分配置错误和播放错误。

根因修复边界：可绑定参数的 output range 必须在 Profile 所有者处要求严格正宽度，并在前端编辑和入站校验
使用同一规则；不能等到动力学层将其变成零。

验收标准：零宽绑定在保存或加载边界得到明确字段错误，不进入 ModelEngine。

### R20-R21 低优先级防御与清理项

- `binary_audio.py` 读取帧头版本、类型和 metadata 长度，但未验证保留 flags 字节为零。当前前端固定写零，
  因此属于协议严格性补齐，不是现存播放故障。
- `usePushToTalkController.ts` 同时在 `document` 和 `window` 注册相同键盘处理器。浏览器事件冒泡会产生
  重复调用；`micStartPromise` 和状态检查已经避免双重采集，但监听和日志仍应收口为一个所有者。

这些项目应在对应文件被修改时顺带清理，不单独建设兼容层、去重器或第二套数值校验系统。

## 3. 建议修复批次

1. **可见故障**：先处理 R8、R13、R15，消除 Turn 挂起、段级错误扩大断连和异步动作先拒后播。
2. **生命周期一致性**：处理 R2、R3、R9、R11、R12、R14、R16、R17、R19，统一关闭、终态、时间预算
   和 keep-first 语义。
3. **能力与所有权整理**：处理 R1、R4、R5、R6、R10、R18，删除不可达能力、重复完成职责和反向依赖。
4. **穷尽性与低风险清理**：处理 R7，并在相关文件改动时收口 R20-R21。

每一批都应直接修改现有所有者，不新增第二套队列、兼容调度器、错误转换器或动作入口。自动测试只
做最基础输入输出 smoke；最终仍需用真实 AstrBot、Electron、TTS 与 Live2D 链路观察行为。
