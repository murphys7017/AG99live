## 1. 当前结论

增强版主链路仍保持统一：

```text
AstrBot
-> Adapter output.segment.v3
-> TurnPlaybackSessionStore
-> PlaybackTimeline
-> ModelEngine
-> engine.parameter_plan.v3
-> AG99 Live2D Runtime
   -> ParameterPresentation
   -> ActiveParameterMixer
-> Official Cubism Physics / model.update / draw
```

正式主链路的所有权仍然统一，没有发现需要推倒 SessionStore、PlaybackTimeline、ModelEngine、
ParameterMixer 或 AG99 Runtime 分层的结构性理由。但本轮源码复核确认了一个尚未收口的共同根因：
“新动作已提交”与“旧动作释放失败”的替换事务没有统一返回语义，此外 ModelEngine 与 Vue Scope 的
清理边界也没有完全适配可观察的停止失败。它们属于当前活动缺陷，必须先于二期表演质量调校处理。
`WebSDK/src` 与官方 Cubism `Framework/Core` 的历史目录混用仍属于架构债务，已在
[角色表演主流程与编排职责审计](./19-角色表演主流程与编排职责审计.md) 记录，但不是本轮的运行时根因。

## 2. 已确认问题

### 2.1 播放替换事务没有保持“启动结果 = 所有权结果”

`frontend/src/live2d-renderer/usePreviewMotionPlayer.ts` 的两个替换方向存在同一问题：

- Direct Parameter Plan 已经启动后，停止旧 Catalog Motion 失败，调用方收到异常，但新 Plan 可能仍在运行。
- Catalog Motion 已经通过 `onStarted` 发布运行所有权后，停止旧 Direct Plan 失败，调用方同样收到异常，
  形成“已经 started，同时又被视为 failed”的矛盾结果。

这不是单纯的异常处理遗漏，而是替换事务的提交顺序和返回契约不一致。修复目标是：

```text
停止并结算旧执行者
    -> 停止失败：替换失败，保持 failed，不启动新执行者
    -> 停止成功：启动新执行者
        -> 启动成功：发布 started 和新的 run ownership
        -> 启动失败：发布 rejected，当前没有活动执行者
```

不能通过“启动新动作后忽略旧动作停止错误”来掩盖问题，也不能让 Timeline 或 ModelEngine 依赖
回调顺序猜测当前真正的执行者。

### 2.2 ModelEngine 停止失败时本地运行所有权没有必然收口

`frontend/src/model-engine/useModelEngine.ts` 的 `stop()` 和 `interruptPlaybackSegment()` 直接调用可能
抛错的 `dependencies.stopPlan()`。停止失败时，`activePlaybackRun`、编译原因和引擎状态清理可能被跳过。

修复目标是：本地所有权必须在 `finally` 中释放；如果下游停止失败，引擎状态必须保持 `failed` 并继续
传播原始错误，不能把失败投影成 `idle`。这样既不会留下陈旧 run，也不会把实际停止失败伪装成正常停止。

### 2.3 组件销毁清理不能被单个停止失败截断

`usePreviewMotionPlayer` 的 `onScopeDispose` 直接调用可抛错的 `stopPlan()`。Vue 的 Scope cleanup 会顺序
执行回调，单个清理异常可能阻止同一 Scope 后续清理。

销毁路径应继续尝试所有已拥有的资源并记录原始错误；显式用户停止仍保持可见失败语义，生命周期销毁
不能因为一个动作停止失败而中断其他资源释放。

## 3. 当前修复批次

### 批次 1：收口播放执行所有权（当前优先）

1. 修改现有 `usePreviewMotionPlayer` 替换流程，使 Direct Plan 和 Catalog Motion 使用同一套
   “旧执行者先结算，新执行者后提交”的事务顺序。
2. 修改现有 `useModelEngine` 停止和段中断流程，在下游失败时仍收口本地所有权，并保留 `failed` 状态。
3. 修改现有销毁清理入口，使显式停止错误可见，同时不阻断同一 Scope 的其他清理。
4. 复核 ModelEngine、Timeline、Recorder 和 SessionStore 的 started/terminal 投影是否只来自真实
   run ownership，不新增队列、fallback、第二个播放器或第二套状态机。

完成标准：任何一次动作播放结果都满足“返回 `started` 才存在可追踪 run；返回 `rejected` 就没有新 run
被遗留运行；停止失败不会被写成 idle；销毁会完成所有资源清理”。

### 批次 2：恢复真实链路证据

完成批次 1 后，再用最小静态检查和一次真实 AstrBot + Electron + TTS + Live2D 对话确认：替换、
中断、自然结束和窗口销毁四种路径的状态一致。自动测试只做基础输入输出 smoke，不运行完整测试套件。

### 批次 3：继续二期表演质量

只有批次 1、2 完成后，才进入 [二期角色表演系统总体规划](./18-二期角色表演系统总体规划.md) 的
face / hesitation、运动动力学、跨 Turn 多样性和 Physics setting 诊断，不在链路状态仍不可信时调节动作常数。

新问题仍应直接修改现有所有者，不新增第二套队列、兼容调度器、错误转换器或动作入口。自动测试只
做最基础输入输出 smoke；最终仍需用真实 AstrBot、Electron、TTS 与 Live2D 链路观察行为。
