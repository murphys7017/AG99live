# N.E.K.O 功能学习与 AG99live 边界扩展

> **状态：候选功能方向，待逐项验证。**
>
> 这份文档把 N.E.K.O 当成产品功能参考，而不是要求 AG99live 复制它的架构。AG99live 的 Live2D、音频、字幕、动作、口型、Physics、播放时钟和 C++ 原生运行时已经是成熟基础；下一阶段的重点是让这具身体进入更多场景，拥有更多可感知、可互动和可持续的能力。

## 1. 先换一个问题

AG99live 现在已经能把一次 AG99 回复稳定地表现为一段 Live2D 演出。N.E.K.O 最值得借鉴的地方，是它把产品问题从“角色如何回答”扩展成了：

```text
角色如何感知当前场景
→ 角色什么时候应该主动出现
→ 角色如何记住关系和偏好
→ 角色如何在不同场景中继续存在
→ 角色如何把声音、动作、工具和内容组织成一次体验
```

因此，下一步不应继续围绕“让 Live2D 再快一点”展开，而应围绕“让已有的 Live2D 表现能力在更多时刻有意义”展开。大模型响应速度仍然是外部约束，新增功能要尽量使用事件、规则、缓存和已有表现计划，避免把每个高频状态都变成一次新的大模型请求。

## 2. N.E.K.O 的功能地图

N.E.K.O 官方仓库当前公开的功能包括主动陪伴、实时语音和视觉理解、持久记忆、多形态 Avatar、Agent 工具、插件生态、多 AI 服务商和用户创作分享。它还把模型管理、情绪映射、记忆浏览、小游戏、点歌台等能力做成了可被用户直接使用的产品功能。

| 功能方向 | N.E.K.O 的具体表现 | 对 AG99live 的价值 |
| --- | --- | --- |
| 主动陪伴 | 根据屏幕、个人动态、热搜、音乐或日常状态主动发起交流，并提供 `off / normal / focus / frequent` 等模式。 | AG99 已有主动对话能力；借鉴其体验设计，优化现有触发控制、可解释性和 AG99live 的角色表现衔接，不另建调度系统。 |
| 多模态感知 | 支持文字、实时语音、屏幕理解、鼠标点击和拖拽。 | 把屏幕、窗口、鼠标、麦克风和直播事件转成角色可理解的场景上下文。 |
| 关系与记忆 | 工作、近期、事实、反思、人格等持久记忆；用户可以浏览、修订和清理记忆。 | AG99 已有记忆模块；先厘清现有记忆混乱的来源并完善它，不在 AG99live 新建关系记忆。 |
| Avatar 表现 | Live2D、VRM、MMD、PNGTuber、桌宠等形态，配合动作捕捉、全屏追踪和情绪映射。 | AG99live 可以先把 Live2D 的情绪、凝视、触摸、闲置状态和表演包做深，再考虑增加形态。 |
| 工具与 Agent | 可以操作浏览器和电脑，也可以通过插件或外部 Agent 扩展能力。 | 让角色能查资料、打开应用、执行受控动作，但必须有明确确认和可撤销边界。 |
| 场景化陪伴 | 游戏、直播、学习、工作、观战等场景都有独立的上下文和输出方式。 | 用场景模式复用现有音频、字幕、动作和 Spout 输出，而不是为每个场景重新造一套播放器。 |
| 内容与表演库 | 点歌台把歌曲、动画和绑定关系组成可导入导出的用户库。 | 当前不作为 AG99live 新增方向；用户指出 AG99 侧已有对应能力。 |
| 创作者生态 | 角色卡、模型、语音包和 Steam 创意工坊分享。 | 可以先做本地可导入导出的角色/表演包，验证内容格式后再考虑在线分发。 |
| 多设备和多服务商 | 角色在桌面、移动端、游戏和硬件间共享记忆，也能切换多种模型服务商。 | 是长期方向，但当前主要瓶颈在模型响应，优先级低于主动陪伴和场景能力。 |

参考： [N.E.K.O README](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/README.MD)、[主动搭话 API](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/docs/zh-CN/api/rest/proactive.md)、[记忆 API](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/docs/zh-CN/api/rest/memory.md)、[Live2D API](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/docs/zh-CN/api/rest/live2d.md)、[游戏 API](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/docs/zh-CN/api/rest/game.md)、[点歌台 API](https://github.com/Project-N-E-K-O/N.E.K.O/blob/main/docs/zh-CN/api/rest/jukebox.md)。

## 3. 对 AG99live 最有价值的功能方向

### 3.1 主动对话：优化 AG99 现有能力

主动对话在 AG99 中已经存在，因此 AG99live 不应再实现一套 Companion Scheduler、主动消息策略或记忆事实源。值得做的是审查和改善现有主动对话的整体体验：触发是否合时、用户是否能理解并控制它、它是否能结合当前场景，以及它输出到 Live2D 后是否有注意、等待、说话和结束等连贯表现。

优化时优先检查 AG99 已有主动对话的触发/抑制原因、冷却和安静时段、重复内容、被打断后的收口、目标会话配置，以及用户查看最近主动行为的路径。AG99live 侧聚焦向现有流程提供必要的桌宠/场景状态，并把主动输出接入当前文本、TTS、动作和播放终态链路；不复制调度、Provider 或主动输出生命周期。

屏幕或窗口观察仍应由宿主侧明确授权并保持独立开关，不应由场景模式隐式开启。高频凝视、鼠标移动和 Physics 帧只驱动本地表现，不触发主动模型请求。

### 3.2 场景模式：第二优先级

N.E.K.O 的功能并不是一组散落的按钮，而是围绕场景改变输入和输出。AG99live 可以先定义四个场景：

1. **聊天模式**：保留当前语音、字幕、动作和历史。
2. **工作/专注模式**：角色保持陪伴和低强度闲置动作，主动对话遵循 AG99 现有的用户策略。
3. **安静模式**：保留本地待机、凝视和用户触摸反馈，不产生不合时宜的语音打断。
4. **观看/游戏模式**：用户明确开启后，角色可以使用允许的上下文和表现方式；输出仍复用现有 `output.segment.v5` 和 PlaybackTimeline。

场景模式的意义是让现有能力产生组合效果：AG99 继续负责会话、主动对话和策略，ModelEngine 负责表现，Timeline 负责同步。它应调整已有能力的行为参数和可见状态，不重新建立直播互动、音乐节目单或主动消息子系统。

### 3.3 角色与表演包：第三优先级

N.E.K.O 的角色卡和创意工坊给了一个很好的产品方向：用户分享的不只是模型文件，而是一整套角色体验。AG99live 可以先在本地实现一个可导入导出的 **Character Performance Pack**：

```text
角色身份与提示词
+ Live2D 模型引用
+ SemanticAxisProfile
+ 情绪/动作映射
+ 闲置状态与场景反应
+ 语音配置
+ 动作目录与表演样例
+ 可选的 Bilibili / 音乐 / ESP32 能力开关
```

这个包不应复制模型、音频或第三方资源本身的授权内容，而应记录安全的引用、元数据和用户配置。当前的 Profile Editor、动作样例、Motion Lab、模型扫描和语音设置已经可以成为它的基础。

它能直接解决一个长期问题：换模型时不只换一套贴图，而是换一套“角色如何说话、如何看、如何动、如何待机”的完整体验。

### 3.4 记忆与关系：审查并完善 AG99 现有模块

AG99 已有记忆模块，AG99live 不应再创建轻量关系记忆或另一套长期事实源。下一步应先和 AG99 一起厘清造成当前混乱的原因，包括记忆类型和会话历史的边界、写入来源、召回时机、重复或过期内容、相互冲突的信息，以及用户如何检查和修正。确认问题后再改现有模块或接入，不预设答案是“增加显式记住按钮”。

屏幕截图、窗口标题、鼠标坐标和调试信息不应未经用户授权进入长期记忆；具体记忆控制沿用 AG99 当前的数据管理入口。

### 3.5 触摸与闲置互动：本地优先

点击、悬停、拖动、用户回来和长时间待机都可以成为角色表现事件。优先提供可配置的本地动作/表情反馈，并保证可关闭、可打断、不会因为高频输入调用大模型。它能补足“有 Live2D 但只有说话时才动”的日常体验，适合作为桌宠侧的新增能力。

### 3.6 Agent 工具：最后再做

浏览器、桌面和外部 Agent 操作很有吸引力，但它们会带来权限、误操作、隐私和失败恢复问题。AG99live 第一阶段最多先做三类明确动作：

- 打开用户确认过的应用或网页；
- 对当前屏幕做一次用户触发的观察；
- 调用已有的搜索、直播或媒体连接器读取信息。

涉及写入、发送、删除、付款、控制硬件或改变系统状态的动作，都必须经过用户确认，并能显示“角色准备做什么”。不要把完整的电脑控制 Agent 作为扩展 Live2D 的前置条件。

## 4. 按投入和收益排序

| 优先级 | 方向 | 预期收益 | 对大模型调用的影响 | 第一件可交付的东西 |
| --- | --- | --- | --- | --- |
| P0 | 优化 AG99 主动对话体验 | 让现有主动对话更合时、可控，并与 Live2D 表现连贯衔接 | 复用 AG99 现有策略与调用路径，不增加并行调度器 | 触发/抑制原因可见，主动输出能正确表现、打断和收口 |
| P1 | 场景模式 | 让聊天、工作、安静、观看各有行为 | 组合现有设置并复用 AG99 上下文 | 工作/安静模式与桌宠状态联动 |
| P1 | 角色与表演包 | 让模型、语音、动作和人格可以整体复用 | 复用已有提示词和动作计划 | 本地导入/导出一个角色表演包 |
| P1 | 触摸与闲置状态 | 提高桌宠的日常存在感 | 高频路径完全走本地状态机 | 点击、拖拽、回归、困倦和安静待机 |
| P1 | 完善 AG99 记忆体验 | 解决已有记忆链路的边界、检索和管理混乱 | 修复现有链路，不建立新事实源 | 找出主要混乱来源并完成一个端到端修正 |
| P3 | 小游戏/观战 | 产生新的互动场景 | 只对关键事件调用模型 | 一个拥有开始、进行、结束生命周期的小游戏 |
| P3 | 受控 Agent 工具 | 扩大角色能做的事情 | 可能增加延迟和失败路径 | 搜索/打开应用/屏幕观察三种可确认动作 |
| P4 | 市场、多设备、更多 Avatar | 形成生态和跨端体验 | 会扩大部署和同步成本 | 等本地角色包和场景模式稳定后再评估 |

## 5. 建议的第一个纵向试点

建议先做 **AG99 主动对话体验优化 + AG99live 角色状态衔接**，不另建 Companion Mode 后端。先选取 AG99 已有的一种主动对话路径，核实触发、抑制、送达和用户控制，再确认 AG99live 收到输出后能表现注意、说话、打断和恢复待机。

### 输入事件

```text
existing_ag99_proactive_intent
scene_changed
pet_interaction
user_returned
```

### 本地策略

```text
AG99 现有策略是否允许主动输出
→ AG99live 提供当前场景/桌宠状态供 AG99 策略判断
→ 当前是否已有 turn 或音频播放
→ 输出送达后进入现有播放和终态链路
```

### 输出

```text
无输出（只做闲置动作）
或
短文本 + 可选 TTS + 一个动作意图 + 一个可观察原因
```

### 验收重点

- 不新增与 AG99 并行的主动调度、Provider 调用或记忆事实源；
- 主动意图的触发/抑制和送达结果可检查，问题归属清楚；
- AG99live 在输出期间正确表现说话、打断和恢复，继续走 `output.segment.v5`、PlaybackTimeline 和既有终态收口；
- 高频本地事件不直接触发大模型，用户可以控制安静/打断行为；
- 屏幕观察保持独立授权，不因主动对话或场景模式自动启用。

## 6. 暂时不要做什么

- 不要因为 N.E.K.O 支持多种 Avatar，就立即把 AG99live 的 Live2D 核心改成多渲染器平台；
- 不要先做插件市场、在线社区或跨设备同步；
- 不要复制 N.E.K.O 的完整记忆服务器或新增关系记忆，先排查 AG99 现有记忆模块的职责和混乱来源；
- 不要为每一个鼠标移动、Physics 帧或渲染状态调用大模型；
- 不要让 Agent 绕过确认直接发送消息、删除数据或控制外设；
- 不要把“主动”实现成无条件随机发言，主动行为必须有场景、冷却、隐私和可解释原因。

## 7. 当前判断

N.E.K.O 对 AG99live 的最大启发是把已有的角色表现能力放进持续运行的关系和场景中，而不是继续扩张渲染器类型。对 AG99live 最有价值的顺序是：

```text
优化 AG99 主动对话
→ 场景模式
→ 触摸与本地闲置互动
→ 角色/表演包
→ 完善 AG99 现有记忆
→ 受控 Agent 工具
```

直播互动编排和音乐节目单暂不列入本轮扩展范围。Bilibili 弹幕接入实际在 AG99live 桌面侧，通过合批文本输入交给 AG99；不能据此称 AG99 已有直播接入或完整直播编排。音乐节目单的复用方向来自用户说明，具体实现覆盖尚未在本轮核验。

这条路线能充分利用当前已经完成的 Live2D 和 C++ 工作，把开发重点从“继续压低渲染占用”转移到“让角色在更多时刻有理由出现”。
