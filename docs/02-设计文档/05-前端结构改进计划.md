# 前端结构改进计划

记录从代码审阅中发现的结构性改进项，按优先级排序。每个条目包含上下文、改进方向和预期的成本/收益，方便按进度逐个处理。

---

## P1（短期收益高，改动成本低）

### 1.1 测试基础设施统一

**现状**

`package.json` 中有 8 个独立的测试脚本，每个执行 `tsc --outDir <独立目录> && node`。全量运行需要串行编译 8 次，无覆盖率、无 watch 模式。

```
test:orchestration   → .test-out-orchestration/
test:session         → .test-out-session/
test:turn-orchestrator → .test-out-turn-orchestrator/
test:coordinator     → .test-out-coordinator/
test:inbound-protocol → .test-out-inbound-protocol/
test:inbound-events  → .test-out-inbound-events/
test:model-engine    → .test-out-model-engine/
test:adapter-connection → .test-out-adapter-connection/
```

**改进方向**

迁移到 vitest（零配置兼容 Vite 项目），或至少合并为单次 tsc 编译 + Node.js test runner。

**文件清单**

- `frontend/package.json` — scripts 中的 8 个 `test:*`
- `frontend/tsconfig.test.json`
- `frontend/tests/*.test.ts` — 迁移断言语法

**收益**

- 全量测试从 ~8 次编译变为 1 次执行
- 支持 `--watch` 开发模式
- 可配置覆盖率报告

---

### 1.2 日志分级

**现状**

全前端使用 `console.info` / `console.warn` / `console.error`，无级别区分、无命名空间。生产构建中调试日志与用户可见消息混在一起。

**关键调用点**

- `useTurnPlaybackOrchestrator.ts` — orchestrator 状态变更
- `useTurnPlaybackSessionStore.ts` — session 创建/清理
- `useAdapterConnection.ts` — 连接状态、入站事件
- `audioPlaybackActions.ts` — 音频播放声明周期
- `inboundMotion.ts` — motion 接收日志
- `model-engine/normalize.ts` — payload 拒绝原因

**改进方向**

引入日志级别函数（`debug / info / warn / error`），Electron 生产构建中过滤 `debug` 级别。不改动现有 log 调用点，只替换 `console.info` 为 `logger.info`。

## P2（中等改动，结构性改善明显）

### 2.1 `usePlaybackCompletionCoordinator` 定时器注入

**现状**

`usePlaybackCompletionCoordinator.ts` 内部直接调用 `window.setTimeout` / `window.clearTimeout`。而同一个播放链路中的 `turnPlaybackOrchestratorCore.ts` 已使用可注入的 `schedule` / `clearSchedule` 接口。两个协调器的注入策略不一致。

**文件清单**

- `frontend/src/composables/usePlaybackCompletionCoordinator.ts` — `settlementTimers` 使用 `Map<string, number>`，直接调用 `window.setTimeout` / `window.clearTimeout`

**改进方向**

Options 接口中已预留 `schedule?: (delayMs, fn) => unknown` 和 `clearSchedule?: (timer) => void`，但内部实现仍直接使用 `window.*` 全局函数。将硬编码调用替换为通过 `schedule` / `clearSchedule` 变量调用即可。

**收益**

- 测试不需要 mock `window.setTimeout`
- 与 `turnPlaybackOrchestratorCore` 风格统一

## P3（高收益但改动范围大）

### 3.1 `useAdapterConnection.ts` 拆分

**现状**

761 行的单文件，同时管理：
- WebSocket 连接生命周期（connect / disconnect / reconnect）
- 60+ 个响应式状态属性的容器
- 入站消息编排（组装 20+ callback 传入 dispatcher）
- 出站消息构建
- 6 个子适配器的初始化和管理（history / motionTuning / modelSync / sessionStore / microphone / audio）

子适配器通过模块级 `let` 变量存储：

```typescript
let historyAdapter: ReturnType<typeof useAdapterHistory> | null = null;
let motionTuningAdapter: ... = null;
let modelSyncAdapter: ... = null;
let sessionStore: ... = undefined;
```

这些模块级单例变量和当前组件 scope 的所有权混在一起，重挂载或重置时不容易判断谁负责清理。

**改进方向**

将职责拆为 2-3 个 composable：

| 候选 composable | 职责 |
|---|---|
| `useConnectionLifecycle` | WebSocket 连接、断线重连、`socket` 引用 |
| `useConnectionState` | 60+ 个响应式状态属性、`pendingAudios/pendingTexts` 队列 |
| `useAdapterOrchestration` | 子适配器注册、入站 dispatch 组装、出站接口导出 |

**风险**

- 当前模块中 60+ 个状态之间存在隐式依赖（如 `pendingAudios` 被 dispatcher 写入、被 audio runtime 读取），拆分后需要显式传递
- `state` 对象被 10+ 个内部函数和子适配器引用，拆分后需要重新组织数据流

---

### 3.2 Watcher 全量投影重建

**现状**

`useTurnPlaybackOrchestrator.ts` 中 watcher 每次触发都重建所有 session 的完整投影数组：

```typescript
watch(
  () => options.sessionStore.getSessions().flatMap((session) =>
    session.segmentOrder.map((segmentId) => { /* 15+ 字段 */ }),
  ),
  () => { /* 遍历所有 session */ },
  { deep: true },
)
```

即使只有一条 segment 的 `text.content` 变化，也会重建所有 session 的投影再遍历。

**改进方向**

- 给每个 session 建独立 watcher（`watch(() => session.segmentOrder, ...)`），只在关联 session 变化时触发
- 或改为 `watchEffect` + 手动追踪访问的响应式字段

**当前影响**

session 数量少时不是瓶颈。当多轮对话并发（2-3 个活跃 session）时可能产生可感知的抖动。
