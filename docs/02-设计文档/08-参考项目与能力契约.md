# 参考项目与能力契约

> **状态：参考原则，非实施方案。**
>
> 本文只整理四个参考项目能给 AG99live 的架构启发。两个仓库的真实边界、所有权和实施顺序，以 [AG99live 与 AG99 联合边界与扩展路线](07-AG99live与AG99联合边界与扩展路线.md) 为准；N.E.K.O 的产品功能优先级，以 [N.E.K.O 功能学习与 AG99live 边界扩展](06-N.E.K.O功能学习与AG99live边界扩展.md) 为准。

## 1. 四个项目各自值得学什么

| 参考项目 | 解决的问题 | AG99live 应吸收的原则 |
| --- | --- | --- |
| [Spatiotemporal Composability](https://arxiv.org/abs/2608.25512) | 动态组件如何加入、撤销并管理依赖。 | 副作用要有 disposer，依赖和生命周期要能检查。 |
| [Cordis](https://github.com/cordiverse/cordis) | 用 Context、Service、事件和组件生命周期组织运行时。 | 只借鉴小型 Context、Provider/Consumer、typed event 和 reconcile，不搬完整框架。 |
| [DeepSeek Harness](https://deepseek-harness.github.io/deepseek-harness/en/reference/) | 用可组合组件、Provider 和事件记录组织 Agent 运行时。 | 把事实事件和当前投影分开，诊断和 UI 读取投影。 |
| [N.E.K.O](https://project-neko.online/plugins/) | 把产品能力做成可管理、可调用、可展示的插件和功能。 | 借鉴 manifest、权限、Hosted UI、Result 和 Adapter Gateway；具体功能另见 N.E.K.O 文档。 |

它们的共同点是：扩展点必须有稳定身份、输入输出、生命周期、权限和失败语义。扩展点不应只是一个随意插入的回调。

## 2. 可迁移的五条原则

### 2.1 能力先于模块

一个能力至少要能回答：

```text
它叫什么？依赖什么？谁启动？谁停止？输入和输出是什么？失败如何观察？
```

目录、类名和 UI 名称可以变化，但能力 ID 和协议身份应稳定。

### 2.2 副作用必须可回收

监听器、定时器、后台任务、WebSocket、文件 watcher、IPC、设备句柄和缓存写入都要有 owner 和 disposer。停止能力时，先撤销副作用，再释放状态。

### 2.3 事实与投影分开

Turn、Segment、播放终态和 Companion 决策可以作为 typed fact；桌面快照、诊断页面和历史列表是投影。投影可以重建，事实不能靠多个模块各自猜测。

### 2.4 外部入口经过同一条管线

```text
Normalize → Policy → Route → Invoke → Serialize
```

协议适配器只负责规范化和序列化；能力层负责业务；UI 通过受控 action 访问能力，不直接持有 WebSocket、播放 store 或原生指针。

### 2.5 动态性建立在稳定契约之上

只有当静态能力已经具备稳定契约、生命周期和诊断后，才值得评估动态加载、热重载或第三方包。否则动态性只会扩大故障面。

## 3. 映射到 AG99live

| 现有边界 | 应保留的职责 | 后续可收敛的方向 |
| --- | --- | --- |
| AG99 `Star`、`PluginManager`、`Context` | 插件发现、生命周期、Provider、事件和 Web API | 不在 AG99live 复制第二个宿主插件系统。 |
| `OLVPetPlatformAdapter` | Adapter 实例组合、协议连接和清理 | 内部使用静态 capability registry，但保留一个顶层 owner。 |
| `TurnCoordinator`、`OutputSegmentCoordinator` | Turn/Segment 身份、输出聚合和终态 | 把事实事件与诊断/快照投影分开。 |
| `frontend/src/model-engine/` | 语义动作编译、参数计划和播放协作 | TypeScript 保持参考实现，Native 通过协议和黄金样本对齐。 |
| `usePetDesktopRuntime` | 桌面端组合 Adapter、播放、ModelEngine、音频和 bridge | 按 provider 拆分实例所有权；窗口控制通过 desktop bridge。 |
| `runtime-core` / `render-core` | Native 协议库与独立渲染宿主 | TS Desktop 和 Native 手动择一连接 Adapter，不先引入内部 IPC。 |
| AG99 Web API、插件页 bridge、desktop settings broker | 认证后的 context/action 和桌面设置同步 | 逐步补充 surface manifest，不让 UI 绕过既有边界。 |

## 4. 当前不照搬的部分

- 插件市场、在线分发和第三方包安装；
- 任意 Python/TypeScript 插件热替换；
- 为每个内部函数增加动态 entry；
- 复制 N.E.K.O 的完整 SDK、记忆服务或多 Avatar 平台；
- 让 UI 直接访问宿主对象、播放 store 或 Native 进程；
- 让多个桌面运行时同时争抢一个 Adapter 连接。

这些能力以后可以逐项评估，但都不是 Live2D 核心扩展的前置条件。

## 5. 推荐的采用顺序

1. **先复用 AG99 宿主边界。** 使用现有 owner scope、Web API、平台注册和插件清理机制；区分插件生命周期与 PlatformManager 持有的平台实例生命周期。
2. **再建立 AG99live 内部静态能力契约。** 最小包含 `CapabilityId`、`RuntimeContext`、typed event、`Effect/Disposer`、生命周期和结构化错误。
3. **先做 Companion/Scene 纵向切片。** 它能同时验证场景信号、策略、AG99 调用、Web surface 和现有 `output.segment.v5` 播放收口。MotionLab 可作为诊断 surface 使用，不再单独维护一条相竞争的架构路线。
4. **最后评估动态加载。** 只有真实用户场景要求外部扩展时，才增加目录发现、enable/disable、进程隔离或第三方 UI。

## 6. 一页式能力契约检查表

新增 capability 前，至少写清楚：

- 稳定 ID 和版本；
- 依赖的 Service 或能力；
- 启动、停止和取消入口；
- 输入、输出和结构化错误；
- 所有副作用及其 disposer；
- 事实事件和状态投影；
- UI 或外部协议所需的最小权限；
- 成功、拒绝、失败、取消的验收路径。

如果这些内容还不能用一页说明，先不要把它包装成插件。
