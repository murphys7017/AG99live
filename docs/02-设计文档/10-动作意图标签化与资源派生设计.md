# 动作意图标签化与资源派生设计

> 文档状态：当前动作生成入站契约的权威文档。
>
> 本文是 [语义动作生成链路设计](./08-语义动作生成链路设计.md) 的当前落地规格，专门修订其中模型入站字段、fallback 派生和资源引用边界。后续 prompt 构建、LLM 输出解析、middleware / inline 接收层、fallback 派生、调参样本和前端展示，都以本文为准。08 号文档中“LLM 输出 `emotion_label` / 必填 `fallback_pose_id`”的早期示例已经过时，但其语义轴主链路目标仍然成立。

## 目标

本文定义当前动作生成链路的统一入站契约。目标不是把动作再拆回情绪分类器，也不是把资源播放重新揉回语义轴生成，而是把三类职责拆清楚：

1. `intent_tags` 负责描述本轮表演意图，保持模糊、开放、可组合。
2. `axes` 负责生成可编译、可修复、可播放的语义动作骨架。
3. `resource_id` 负责明确引用受控资源文件，作为特殊表情或动画的显式标识。

系统仍然以语义轴生成为主。资源文件可以被引用，但不能替代语义轴；语义轴可以持续生成，但不要求 LLM 再输出粗粒度情绪分类。

本文落实 [语义动作生成链路设计](./08-语义动作生成链路设计.md) 的语义轴主链路目标，并修订其中关于 LLM 输出 `emotion_label + fallback_pose_id` 的早期契约。它同时与 [预录制资产层设计](./09-预录制资产层设计.md) 保持边界一致：普通自动动作继续走语义轴，资源只通过受控 `resource_id` 暴露意图，不直接成为播放指令。

## 当前状态

当前代码已经完成的部分：

- interaction middleware prompt 已切到 `intent_tags`、`resource_id`、`duration_hint_ms` 和 `axes`。
- prompt 中不再要求 LLM 输出 `emotion_label` 或 `fallback_pose_id`。
- middleware / inline 接收层可以读取 `intent_tags`，并由系统派生 `emotion_label`。
- fallback 选择已经从单一情绪标签转为基于 `intent_tags + resource_id + axes` 的候选打分。
- downstream v3 payload 仍保留 `emotion_label` 和 `fallback_pose_id` 作为兼容字段。

仍需补齐的部分：

- `resource_id` 需要接入白名单校验；未命中候选时应丢弃并写入 diagnostics，而不是无条件透传。
- inline contract 的示例 payload 需要避免全 neutral 轴值锚定，并避免要求模型输出系统生成的 `summary`。
- legacy realtime selector prompt 仍有旧 `emotion` / `fallback_pose_id` 契约残留；除非确认彻底废弃，否则需要同步到本文契约。
- 前端调参和样本存储仍需逐步把 `intent_tags` 作为主展示字段。

## 背景

当前链路已经完成了几轮拆分：

- router 与 persona reply 的 prompt 注入分离。
- inline / middleware 两条动作入口分离。
- fallback 候选从“固定 emotion 分组”转成“按轴和姿态描述挑代表样本”。
- motion summary 开始向前端暴露可见骨架、soft range 越界和姿态描述。

下一步要处理的是字段职责问题。

过去的做法里，`emotion_label` 同时承担了三个角色：

- 给人读的短摘要。
- 给 fallback 和修复层的弱线索。
- 给 LLM 的输出目标。

这会把系统重新拉回粗分类模式。现在的目标是把它拆开，让 LLM 输出多关键词语义线索，让系统自己派生兼容字段和兜底字段。

## 核心原则

### 1. 模糊层和明确层分离

模糊层只描述“像什么”：

- 情绪
- 语气
- 姿态
- 关系感
- 场景感

明确层只描述“选哪个”：

- `resource_id`

### 2. 资源文件必须有明确 ID

如果某个表情或动画资源要被显式调用，它必须拥有稳定、唯一、可校验的 `resource_id`。这个 ID 只在受控候选集合里生效。

### 3. 普通动作继续模糊

普通动作不要求 LLM 输出明确资源类型，不要求资源名，不要求文件名，不要求 `kind` 枚举。它只输出模糊语义标签和参数轴。

### 4. 兼容字段由系统派生

`emotion_label` 和 `fallback_pose_id` 不再由 LLM 直接输出，改为系统在接收结果后派生。这样 prompt 更干净，行为更稳定，旧链路也能继续跑。

### 5. 不把资源类型暴露给模型

如果 runtime 内部需要知道资源是表情还是动画，可以在本地 registry 里保留，但不要把它作为 LLM 输出契约的一部分，也不要在 prompt 中强制模型理解 `kind`。

## 字段职责

### intent_tags

主语义字段。

建议形态：

```json
["感激", "温和", "低头致谢", "轻微开心"]
```

职责：

- 描述本轮回复的语义和表演意图。
- 可以同时包含情绪词、动作词、场景词、关系词。
- 允许模糊，不要求枚举封闭。
- 用于 prompt few-shot、fallback 候选打分、调参样本聚合、前端展示。

规则：

- 保持输入顺序。
- 去空、去重。
- 不要求固定上限，但实现层应保留宽松安全上限，防止异常 payload。
- 不应包含文件名、资源 id、协议字段名。

### resource_id

明确资源引用字段。

建议形态：

```json
"resource_id": "expr_thanks_smile"
```

职责：

- 明确请求一个受控资源。
- 只能从 prompt 暴露或系统允许的候选中选择。
- 作为资源层的显式输入，而不是语义轴的替代品。

规则：

- 不命中候选就丢弃。
- 不允许靠 `emotion_label` 自动推断。
- 不允许用它替代 `axes`。
- 不允许在 prompt 中暴露“种类分类”来诱导模型只做文件选择。

### emotion_label

兼容显示字段，不再是模型输出目标。

建议形态：

```json
"emotion_label": "感激-温和-低头致谢-轻微开心"
```

职责：

- 给旧链路、日志、UI、样本存储一个短摘要。
- 作为模型输出兼容层存在。
- 由系统根据 `intent_tags` 派生。

规则：

- LLM 不再输出它。
- 派生逻辑由系统统一处理。
- 默认使用全部 `intent_tags` 以 `-` 拼接。

### fallback_pose_id

语义轴兜底字段，不再是 LLM 输出目标。

职责：

- 在 `axes` 太弱、缺骨架、软范围过多或旧输入失效时，提供一组可编译的语义姿态。
- 用于修复层补 head/body/gaze 骨架。
- 仍然服务语义轴，不直接代表资源播放。

规则：

- LLM 不再输出它。
- 系统根据 `intent_tags + resource_id + axes` 派生。
- 只有命中候选阈值时才使用候选，否则回落到默认 neutral。

## LLM 输出契约

当前自动动作输出契约收敛为：

```json
{
  "intent_tags": ["感激", "温和", "低头致谢"],
  "resource_id": "expr_thanks_smile",
  "duration_hint_ms": 1000,
  "axes": {
    "head_pitch": 42,
    "mouth_smile": 66
  }
}
```

### LLM 必须输出

- `intent_tags`
- `axes`

### LLM 可选输出

- `resource_id`
- `duration_hint_ms`

### LLM 不再输出

- `emotion_label`
- `fallback_pose_id`
- `choice`
- `motion_id`
- `motion3`
- `exp3`
- 任何明确的资源种类枚举

## 资源目录契约

`motion_catalog.json` 和资源扫描结果应支持把资源标记为“可提示给模型”的候选，但模型看到的只应是语义提示，不应看到类型分类堆叠。

建议字段：

```json
{
  "resource_id": "expr_thanks_smile",
  "label": "感谢微笑",
  "file": "Expressions/Thanks.exp3.json",
  "prompt_tags": ["感激", "感谢", "温和", "轻微开心"],
  "recommended_scenarios": ["表达感谢", "被帮助后道谢", "收到礼物"],
  "prompt_visible": true
}
```

建议规则：

- `resource_id` 稳定且唯一。
- `prompt_tags` 是暴露给 LLM 的模糊标签。
- `recommended_scenarios` 描述适用场景。
- `prompt_visible` 决定是否进入 prompt 候选池。
- 资源类型如果一定要保存，保留在运行时内部元数据，不进入 LLM 合约。

## 生成流程

### 1. Prompt 构建

系统在构建 prompt 时只注入三类信息：

- 当前语义轴。
- 当前可提示的资源候选。
- 当前风格偏好和代表性 fallback pose。

其中资源候选只暴露：

- `resource_id`
- `label`
- `prompt_tags`
- `recommended_scenarios`
- `description`
- `intensity`

不要把资源目录做成“让模型挑文件”的清单。

### 2. LLM 输出

LLM 根据当前回复生成：

- `intent_tags`
- `axes`
- 必要时的 `resource_id`

它不负责生成兼容字段，也不负责兜底选择。

### 3. 后端接收

后端在解析后做三件事：

1. 归一化 `intent_tags`。
2. 派生 `emotion_label`。
3. 派生或修复 `fallback_pose_id`。

### 4. 语义修复

`axes` 仍然走原有语义轴修复流程：

- 缺失轴补齐。
- 越界轴 clamp。
- 不合法轴丢弃。
- 头 / 身 / 视线骨架不足时使用 fallback pose。

### 5. 资源引用处理

如果 `resource_id` 被接受，系统只把它记作受控资源意图，不自动替代语义动作。

后续是否播放资源，应该由独立策略层决定，不直接混进当前语义动作主链路。

## emotion_label 派生规则

派生函数建议非常简单：

```python
emotion_label = "-".join(intent_tags)
```

规则：

- 每个 tag 先 trim。
- 过滤空字符串。
- 保持原始顺序。
- 如果结果为空，回退为 `"motion"`。
- 可以保留一个很宽松的长度上限，防止异常输入污染日志和 UI。

这个字段只用于兼容显示和旧链路，不再参与 prompt 选择。

## fallback_pose_id 派生规则

`fallback_pose_id` 由系统根据候选评分派生，不由 LLM 直接写。

### 候选来源

候选仍然来自现有 fallback pose 生成器，但排序和打分要从“情绪标签优先”转到“标签 + 姿态 + 资源线索优先”：

1. 用户手调样本。
2. 可映射到语义轴的表达式或资源提取。
3. 当前 profile 的可解释语义姿态。
4. 默认 neutral。

### 评分输入

候选评分应同时参考：

- `intent_tags`
- `resource_id`
- `axes`
- 候选的 `prompt_tags`
- 候选的 `recommended_scenarios`
- 候选的 `pose_descriptors`
- 候选的骨架覆盖度
- 候选来源优先级

### 评分建议

可以用下面的思路：

- `resource_id` 精确命中给高分。
- `intent_tags` 与 `prompt_tags` 的重合给中高分。
- `intent_tags` 与 `recommended_scenarios` 的重合给中分。
- 当前 `axes` 的姿态描述与候选 `pose_descriptors` 重合给中分。
- 候选包含完整 head/body/gaze 骨架给加分。
- 来源越接近用户手调样本，优先级越高。
- 如果当前 `axes` 和候选姿态明显冲突，减分。

### 阈值

建议保留最低命中阈值：

- 高于阈值：使用最佳候选。
- 低于阈值：回落 default neutral。

### 冲突处理

如果 `resource_id` 命中，但候选和当前 `axes` 冲突明显，不应强行选它。资源线索是加分项，不是绝对命令。

## 与旧字段的兼容策略

### 短期

短期内保留兼容字段，但它们由系统生成：

- `emotion_label`
- `fallback_pose_id`

这样可以保证：

- 旧前端不坏。
- 旧测试不需要一次性重写。
- 日志和调参样本仍可读。

### 中期

中期把所有 prompt、parser、sample store、UI 的主视图切到 `intent_tags`。

### 长期

长期可以把 `emotion_label` 彻底降级成显示字段，甚至由 UI 按 `intent_tags.join("-")` 动态渲染。

## 与资源层的关系

本文只定义“明确资源 ID 可以进入契约，但不把资源层变成动作主链路”。

也就是说：

- `resource_id` 可以被记录、校验、展示。
- `resource_id` 未来可以被策略层消费。
- `resource_id` 现在不应直接替代 `fallback_pose_id`。
- `resource_id` 不能要求 LLM 输出 `kind`。

资源层真正接入播放时，应该走独立的策略仲裁，不要重新污染语义轴主链路。

- `resource_id` 未命中候选时被拒绝。

## 推荐执行顺序

### 第 1 步：协议与兼容层

先改后端与前端协议，让系统能读 `intent_tags` 和 `resource_id`，并派生 `emotion_label`。

### 第 2 步：prompt 与样例

再改 prompt 构建，把 `emotion_label` 从模型输出契约里移除，补上 `intent_tags`。

### 第 3 步：fallback 派生

接着把 `fallback_pose_id` 的生成改成系统派生，并保留清晰的诊断原因。

### 第 4 步：资源候选

最后再扩展 `motion_catalog.json` 的可提示资源候选，让 `resource_id` 有明确的白名单来源。

### 第 5 步：调参闭环

把 `intent_tags` 和 `fallback_pose_id` 反馈到样本存储、前端调参和日志里，形成可观测的 prompt 调优闭环。

## 非目标

本文不做以下事情：

- 不把 `resource_id` 直接变成资源播放指令。
- 不把资源类型 `kind` 暴露给 LLM。
- 不把 `emotion_label` 重新变成模型分类目标。
- 不删除语义轴主链路。
- 不恢复旧的自动 catalog selector。
- 不把资源层和语义层重新混成一个协议字段。

## 预期效果

这套方案落地后，动作链路会变成：

- LLM 输出更自由的语义标签，而不是单点粗分类。
- 兼容字段由系统统一派生，prompt 更干净。
- fallback 由系统基于标签和姿态选择，更稳定。
- 明确资源文件用明确 ID，避免模糊猜测。
- 语义动作和资源动作边界更清楚，后续可以继续演进资产层而不重写主链路。
