# 项目结构优化路线图

快照日期：2026-05-13

本文是当前下一阶段的结构优化入口。

当前策略是：

```text
先把项目结构边界收稳
再继续做动作引擎细节
```

原因是文本、音频、动作主链路已经基本跑通，但前后端仍有几处边界没有完全硬化。如果此时继续堆动作能力，复杂度会再次压回 `useAdapterConnection`、`TurnCoordinator` 和 `ModelEngine`。

## 1. 当前结构判断

当前项目已经形成两个核心运行域：

```text
AstrBot Adapter
  -> 协议接入、turn 生命周期、文本/音频/动作输出

Electron Frontend
  -> TurnPlaybackSession、segment queue、起播编排、动作执行、播放完成回执
```

前端已经从旧的散装状态推进到：

```text
TurnPlaybackSession
  -> 多个 TurnPlaybackSegment
      -> text / audio / motion
```

这是一个正确方向。

当前最需要继续优化的不是动作参数算法，而是：

- 前端协议接入层边界
- 运行时 snapshot 和工具域投影边界
- 前后端协议契约治理
- 输入链路与播放链路的身份边界

## 2. 当前最终语义

当前统一语义如下：

```text
一个用户输入
-> 一个 turn
-> 多个 assistant output segment
-> 每个 segment 绑定 text / audio / motion
```

三个结束信号必须拆开：

```text
control.synth_finished
= 后端输出队列关闭
= 当前 turn 不会再追加新的 output.* / engine.motion_* segment

control.playback_finished
= 前端本地播放完成
= synth_finished 已到，且所有 segment 都 settled

control.turn_finished
= 后端确认整轮闭环收口
= 后端收到 playback_finished 后发出
```

因此：

- `synth_finished` 不是某条音频生成完成。
- `synth_finished` 不是整轮完成。
- 音频播放结束也不是整轮完成。
- 前端只有在队列关闭且所有 segment 本地 settled 后，才发送 `playback_finished`。
- 前端收到 `turn_finished` 后，才把 session 标记为 `completed`。

## 3. 已完成的关键收口

最近一批结构收口已经完成：

- 后端 `control.synth_finished` 已收口为 turn 输出队列关闭信号。
- 前端入站协议已严格要求 `version === "v2"` 和非空 `message_id`。
- 前端已移除 `legacy:*` segment fallback。
- 播放管线已经通过窄端口接入 Adapter / ModelEngine。
- `TurnPlaybackSegment.audio` 已经成为完成判定的事实来源。
- `synth_finished` 后的无音频判定已经不再依赖 adapter pending audio queue。
- motion 入站链路的 dispatcher 类型边界已经收紧，相关 `as any` 已移除。

当前播放管线端口如下：

| Port | 调用方 | 职责 |
| --- | --- | --- |
| `PlaybackReleasePort` | Orchestrator | release text / audio / motion |
| `PlaybackAckPort` | Completion Coordinator | 发送 `control.playback_finished` |
| `MotionPayloadPort` | Orchestrator / ModelEngine | 交付动作 payload |
| `RuntimeSnapshotPort` | Snapshot Publisher | 获取模块摘要投影 |

这些收口的意义是：前端播放语义已经基本从旧的 adapter 散装状态中脱离出来。

同样已经明确的一点是：麦克风输入链路不再借用当前 assistant playback orchestration。输入段现在有自己的 `input:*` identity，并且 broken audio segment 会通过 `input.mic_audio_end.dropped` 明确上报。

## 4. 已基本完成：明确音频事实来源

### 当前状态

音频状态现在同时存在于：

- adapter state
- `TurnPlaybackSegment.audio`

当前已经明确：

```text
TurnPlaybackSegment.audio
= 播放完成判定的事实来源
```

adapter state 里的 audio 字段只保留为：

- Audio IO 的当前播放缓存
- UI 投影
- 最近播放摘要

### 已完成

- Completion Coordinator 只看 session segment。
- Orchestrator 只看 session segment。
- `synth_finished` 后标记缺失音频时，只检查 segment audio 是否没有 URL、没有 release、没有 started、且仍处于 `idle`。
- 已补轻集成测试，覆盖 pending queue 已空但 segment 音频已 started 时不会误标 `absent`。

### 仍需保持

- ModelEngine 计算动作贴合音频时优先从 session segment 读取 timing。
- adapter audio fields 不再参与完成判定。

## 5. 第一优先级：继续拆薄 `useAdapterConnection`

### 当前判断

`useAdapterConnection.ts` 已经完成了重要收口：

- inbound protocol parser
- inbound event mapper
- payload runtime validation
- segment-aware session 写入

但它仍承担：

- WebSocket 连接管理
- dispatcher
- 音频 bridge
- 文本 / 音频 pending release facade
- history client
- motion tuning client
- profile save client
- UI 状态投影

### 目标

继续收成：

```text
AdapterConnectionTransport
AdapterInboundDispatcher
AdapterOutboundClient
AdapterAudioBridge
AdapterRuntimeFacade
Feature clients
```

### 验收

- `useAdapterConnection` 更像组合 facade。
- feature client 不再向主文件继续膨胀。
- 文本/音频 release 队列从协议接入逻辑中分离出来。

## 6. 第二优先级：协议契约治理

### 当前问题

前后端协议仍是双份维护：

- 后端：`protocol/constants.py`、`protocol/parser.py`、`protocol/builder.py`
- 前端：`types/protocol.ts`、`adapter-connection/protocolMessageTypes.ts`、`inboundPayloads.ts`

短期已经能工作，但长期会增加协议漂移风险。

### 短期目标

- 继续集中前端 message type 字符串。
- 为 `control.synth_finished / playback_finished / turn_finished` 建立更完整测试。
- 把三层 ID 契约写入当前有效文档。

### 中期目标

考虑用协议清单或 JSON Schema 生成 Python / TypeScript 契约。

## 7. 暂缓动作引擎细节

当前暂缓：

- 新动作参数算法
- 更复杂的动作引擎库
- 音素级口型同步
- 帧级 motion mixer

这些都应该等结构边界更稳后再做。

否则动作能力会继续把复杂度压到还没有完全收口的模块上。

## 8. 建议执行顺序

```text
1. 继续拆薄 useAdapterConnection
2. 为 snapshot publisher 引入模块级 projection
3. 补协议治理
4. 补高价值时序测试
5. 回到动作引擎细节
```

## 9. 当前不建议做的事

- 不建议继续扩大 `TurnCoordinator`。
- 不建议继续扩大 `useAdapterConnection`。
- 不建议为了减少文件行数做机械拆分。
- 不建议把动作引擎做成新的跨域中台。

## 10. 结构目标

理想结构是：

```text
边界层负责防御
协议层负责契约
Session 负责事实
Orchestrator 负责起播
Completion Coordinator 负责结束
ModelEngine 负责动作编译和调度
Avatar Runtime 负责执行
工具窗口只通过 command / snapshot 协作
```

做到这里之后，再继续做动作引擎细节会更稳。
